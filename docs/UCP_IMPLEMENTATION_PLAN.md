## 1. Summary

**What gets built.** A person asks Dina to find something; Dina searches UCP merchants' live catalogues, ranks them by PeerLens trust, opens a checkout session at the chosen merchant for exactly the items the person approved, shows the merchant's own totals, warnings and policies, and hands the person to the merchant's page to pay (Cart Handover). Dina then learns whether the purchase happened and follows the order until it closes. Later milestones add linked merchant accounts and a trust-ranked index of UCP merchants.

**What never gets built here.** Dina never calls `complete_checkout`, never sends or receives a payment credential, and never advertises a payment handler or a payment extension. The spec allows exactly this: without AP2, "the checkout has to be finalized manually by the user through a trusted UI" (checkout `index.md:23-25`), and the buyer "**MAY** use `continue_url` to hand off to business UI" at any stage (`index.md:1013`).

**What changed since the assessment.** Reading the spec in full and the code against it changes these things (details in §2 and §3):

1. **MCP comes first, not REST.** The only live UCP merchants found are Shopify stores, and they serve MCP only. REST is still built, for merchants that offer it, and tested against Dina's own mock merchant.
2. **One version only.** A merchant learns a buyer's protocol version only from the profile the buyer names, so speaking two versions would need two profile documents. Dina speaks v2026-08-25 only (D11): one profile per node, one identity, one key, no per-merchant profiles.
3. **Even catalogue search needs a hosted profile.** Shopify fetches the buyer's profile on every call and refuses with `profile_unreachable` when it cannot. The hosting therefore comes in U1, with the first search.
4. **The profile must not reveal who the person is.** A profile hosted under the person's DID, or signed with the key their DID document publishes, would tell every merchant their DID. The plan gives each node an opaque host label and a UCP key of its own, uploaded straight to the Dina-run host, so nothing in the profile links them to the DID; only the host's operator knows the link. Public servers use that host too, since their own domain is listed in the public A2A directory under their DID. This is profile-level hiding (S7): a public server's IP address, and its webhook and OAuth domain, can still link it to its DID, and the plan says so (§3.1, §3.5, D2).
5. **Request signing (RFC 9421) is new code.** Nothing in the repo does it yet.
6. **The outbound transport needs a wider contract.** A2A's transport returns no response headers, discards 401/403 bodies and refuses 304. UCP needs all three (§3.3).
7. **The phone cannot make UCP calls safely yet.** It has no outbound transport that resolves, vets and pins an address before connecting, which is why the phone runs no A2A outbound calls either. The owner chose to build that native module first (U6, right after U0), so a phone-only Dina shops from the first release (§3.4, D1).
8. **Dina must find out whether a handed-off checkout became an order.** It never completes the checkout itself, so it watches the session after the hand-off (§3.12).
9. **Orders have no overall status and no end.** Dina needs its own closed rule (§3.14).
10. **Signed order webhooks can be replayed**, and anyone can post to the webhook URL. A webhook is accepted only for a session Dina holds, and prompts a fresh fetch; where the merchant refuses Get Order, its body is shown as possibly out of date and only ids never seen before can interrupt (§3.13).
11. **Merchant strings reach Brain only as guarded text or local handles** (§3.11), and **search text Brain writes is checked by Core before it leaves** (§3.16).
12. **AppView does not fetch websites**, and the merchant index must not leak who bought what (§3.15, D4).
13. **The spec contradicts itself in many places.** §2.2 lists each and how Dina reads it.

**First steps:** U0, the pure `@dina/ucp` package (~2–3 weeks, no migrations, no routes, no network); then U6, the phone's safe-connection module (~3–4 weeks, S10); then U1 (read-only search on the phone and on servers, live against a Shopify store).

## 3. Design against the code

Each item: the finding, then **Plan**.

### 3.1 The UCP signing key

The A2A key at `m/9999'/5'/0'` is derived only when the gateway is configured (`boot.ts:709-713`; the only caller of `deriveP256SigningKey` in `src`) and is published in the DID document as `#a2a_card` (`plc_dina_update.ts:160`). There is no rotation machinery: the generation is the literal `0`, and the card config holds one key (`packages/core/src/a2a/inbound_card.ts:84-94`). Merchants MUST be able to verify ES256 (`signatures.md:95-101`); Ed25519 is optional.

**Plan (assumes D2):**
- A UCP key of its own: P-256 at `m/9999'/6'/{generation}'` (a new SLIP-0010 purpose, `6'`; `derivePathP256` already exists in `packages/core/src/crypto/slip0010.ts:304`). It is never written to the DID document, so a merchant holding the profile cannot look the person up.
- Every UCP-enabled node derives it at boot whatever its A2A configuration, and installs it through `packages/core/src/commerce/ucp/signing_key.ts`. It lives in memory only, like the A2A key.
- The JWK carries `kid` = RFC 7638 thumbprint, `alg: ES256`, `use: sig`. The profile lists it under `keys` (the v2026-08-25 name; v2026-04-08's `signing_keys` is not needed, D11).
- Generation `0` only, until U7 (key rotation, §4.8), except that a restore resumes at the generation the host has recorded (§3.5). Until U7 a lost key is recovered by hand: the owner uses "My key may be compromised", which retires the key and withdraws the profile (§3.5), and UCP stays off on that node until U7. The ordinary "Turn UCP off" switch only pauses and retires nothing.

### 3.2 RFC 9421 signing and verifying

Nothing in the repo implements HTTP message signatures. `@dina/a2a` has JWS only.

**Plan:** in `@dina/ucp` (zero dependencies, injected sign and verify functions like `JwsSignFn`):
- `contentDigest(bodyBytes)` → `sha-256=:<b64>:` over the exact bytes sent or received.
- `signatureBase(request, components, params)` per RFC 9421 §2.5, with the derived components `@method`, `@authority`, `@path`, `@query`, `@status`, and header fields lower-cased.
- `requiredRequestComponents(request)`: `@method @authority @path`, plus `@query` when there is a query, `ucp-agent` (always present), `idempotency-key` when sent, `content-digest content-type` when there is a body (`signatures.md:424-490`, `overview/index.md:2430-2444`).
- Parameters: `keyid` only; no `alg`, no required `created` (`signatures.md:124-125, 850-852`). Label `sig1`.
- ECDSA signatures in raw `r||s` (64 bytes), never DER (`signatures.md:494-499`).
- A verifier for responses and webhooks. For each candidate signature, in order: its covered components must include the required set (responses: `@status`, plus `content-digest` and `content-type` when there is a body, `signatures.md:770-776`; webhooks: §3.13 and D7), else the candidate is skipped; the `Content-Digest` header must match the SHA-256 of the received bytes (`signatures.md:778-782`), else it is skipped; the key is found by `kid` among keys that are not `use: enc` and whose `key_ops` (if any) include `verify`, with one forced profile refresh on an unknown `kid` at most once per 60 s per origin; then the signature is checked. A signed answer is accepted only if one candidate passes every step. **Policy:** a merchant API answer with no `Signature` header is accepted on the strength of the pinned TLS connection, since the spec makes response signing optional for catalogue, cart and checkout calls (`signatures.md:870-879`) and Shopify does not sign; an answer that carries a signature that fails is a transport failure, reconciled like a lost answer (§3.10); a webhook must always verify (§3.13). Vectors for each case. Negative vectors: a status-only signature on a response with a body, a digest the signature does not cover, an altered body, and two signatures where only the one with too little coverage verifies.
- An RFC 8941 dictionary encoder and parser for `UCP-Agent` (`profile="<https URL>"`) and `Signature-Input`.

Frozen vectors: the RFC 9421 Appendix B ECDSA P-256 examples, plus Dina-made vectors for each UCP request shape. A cross-check uses the official samples' Python `signing.py` as a library, with the key handed to it directly: it signs a request that Dina must verify, and verifies a request Dina signed (run where Python is available, like the A2A reference-agent tests). The samples' servers themselves are not used (S20).

### 3.3 The outbound transport

`packages/core/src/a2a/host_transport.ts` defines the policy port: `a2aFetch` runs Core's URL check (`checkOutboundUrl`: HTTPS, no credentials, no literal IP), then the installed host transport, under a Core-held deadline. The Node socket half, `createA2AHostTransport` (`packages/net-node/src/a2a_host_transport.ts:96`), resolves once, refuses if any answer is blocked, pins the socket to the vetted address, caps bytes, accepts JSON only and reports whether anything was sent. That matches the spec's fetcher rules (`overview/index.md:2283-2310`). But its request allows only `GET` and `POST` (`host_transport.ts:38`); its result carries status and decoded text and no headers (`host_transport.ts:57-68`); it refuses every 3xx, including 304; and it discards 401 and 403 bodies (`net-node/src/a2a_host_transport.ts:237-255`).

**Plan:** generalise the port into a shared `PolicyHttpRequest` / `PolicyHttpResult`, with A2A's behaviour unchanged by default:
- Request: `method: 'GET' | 'POST' | 'PUT' | 'DELETE'` (DELETE only for withdrawing a hosted profile, §3.5); `minTls` (`'TLSv1.2' | 'TLSv1.3'`); `accept` (`'json'`, or `'json-or-sse'` for MCP endpoints); `readAuthErrorBodies` (read 401/403 bodies within the byte cap); `ifNoneMatch` (send it, and treat a 304 as a result, not a redirect).
- Result: `status`, `bodyBytes` (the exact bytes, for `Content-Digest`), `signedHeaders` (for a response carrying `Signature-Input`: every header field its covered components name, such as `content-length` or `date`, kept as received, at most 32 fields and 16 KiB in all, for Core's verifier only and never passed on; a covered field that is missing or over the cap fails verification), `headers` (an allow-list for the rest of Core, each value capped at 4 KiB: `retry-after`, `cache-control`, `etag`, `last-modified`, `content-type`, `content-digest`, `signature`, `signature-input`, `mcp-session-id`, `www-authenticate`, `ucp-agent`, `webhook-id`, `webhook-timestamp`), `connectedAddress`, and `sent`.
- UCP limits, `UCP_FETCH_LIMITS`: profile 128 KiB (the spec's floor for the size cap, `overview/index.md:2305-2310`) and 10 s (Dina's choice; the spec sets no number); catalogue 2 MiB and 20 s; checkout and order 512 KiB and 20 s.
- `ucpFetch` sits beside `a2aFetch` and calls the same installed socket.
- **Packages.** Two new packages split pure policy from Node I/O, so Core gains no Node-only dependency and the phone bundle is untouched:
  - `@dina/net-policy`: zero dependencies, pure. Address classification (`isBlockedAddress`, moved from `packages/core/src/commerce/catalog_feed_policy.ts:126`), the `PolicyHttpRequest` / `PolicyHttpResult` types, and the limits. Core imports it (`catalog_feed_policy`, `catalog_ingest`, `checkOutboundUrl` and the A2A port), and so do AppView and the socket package.
  - `@dina/net-socket-node`: the Node socket half (`node:dns`, `node:https`), moved from `packages/net-node/src/a2a_host_transport.ts`, depending only on `@dina/net-policy`. `@dina/net-node` re-exports it, so A2A's wiring does not change; AppView depends on it directly.
  - Check: the mobile bundle still builds (`expo export`), and Core's `package.json` lists no Node-only dependency.
- **Complete special-use classification, before anything else in U1.** Today's filter lets through `198.18.0.0/15`, `198.51.100.0/24`, `203.0.113.0/24`, `2001:2::/48`, `2001:db8::/32`, and 6to4 addresses that wrap a blocked IPv4 address such as `2002:7f00:1::1` (each checked against `isBlockedAddress` on 2026-10-04). The spec says implementations "MUST reject URLs that resolve to special-use IP addresses" (`overview/index.md:2296-2304`). The new classifier covers every range in the IANA IPv4 and IPv6 special-purpose registries, and checks the IPv4 address wrapped inside 6to4 (`2002::/16`), Teredo (`2001::/32`), NAT64 (`64:ff9b::/96`, `64:ff9b:1::/48`) and IPv4-mapped forms. The A2A outbound transport and the catalogue-feed fetcher use the same classifier, so they get the fix too. Tests: each range answered by DNS gets no socket connection, including a mix of allowed and blocked answers.
- Tests: a signed response verified end to end, including one whose signature also covers `content-length` and `date`, one where a covered header is missing, and one over the size cap; a 401 with `WWW-Authenticate`; `Retry-After` on 429 and 503; an MCP session header echoed; a 304 on a profile refresh; every A2A transport test unchanged.

### 3.4 The phone

`packages/net-expo` has no HTTP port. `apps/mobile/src/storage/init.ts:421-431` records why the phone runs no networked connectors: React Native `fetch` cannot report or pin the connected address. A2A plan D6 kept outbound A2A off the phone for the same reason.

**Plan (D1):** U6 comes right after U0. It adds a native transport that resolves, vets and pins (iOS `Network.framework` with a custom resolver; Android OkHttp with a custom `Dns`), installed as the phone's policy socket for both `ucpFetch` and `a2aFetch`. From U1 on, the same Core UCP code runs on the phone and on servers, and every milestone's done criteria cover a phone-only Dina. A phone uses the Dina-run host for its profile, the drop-box `webhook_url` (S9), polls and watches only while the app is open, and links accounts through its own claimed link (§3.17). A phone paired to a server still sees the server's cards through the mirror (§3.9).

### 3.5 Hosting the profiles

The spec's hosting rules: HTTPS, no redirects, `Cache-Control: public, max-age>=60` and never `private`/`no-store`/`no-cache`, an `ETag` recommended, no per-session data (`overview/index.md:2232-2249`). Merchants fetch the profile before serving the buyer and cache it at least 60 s.

One document per node, at `https://<label>.ucp.dinakernel.com/.well-known/ucp`, since the OpenAPI says the `UCP-Agent` URL "MUST point to /.well-known/ucp" (`rest.openapi.json:889`). The host serves it with `Cache-Control: public, max-age=300` and an `ETag`, a lifetime Dina fixes so key rotation can be timed (§4.8).

Each lists `ucp.version`, `ucp.services["dev.ucp.shopping"]` (`mcp` and `rest` entries with `version`, `spec`, `schema`, no endpoint), `ucp.capabilities` (catalogue search and lookup, cart, checkout, fulfillment, discount, order, permalink, and identity linking from U4), `ucp.payment_handlers: {}`, and the UCP key. Dina advertises no payment extension, no AP2, no `buyer_consent` (D3), and leaves fulfillment's `supports_multi_group` false. Nothing in either document names the person, their DID or their node.

Where they are served: **every node, public servers included, uses the Dina-run host** (S7). A public server's own domain is the endpoint of its A2A card, which the public A2A directory lists under the person's DID (`appview/src/shared/a2a/card-verify.ts:147-177`), so a profile served from that domain would let any merchant look the person up.

**What this does not hide (S7).** A public server makes its UCP calls from its own IP address (`ucpFetch` connects straight from the host), usually the address its public domain resolves to, and its webhook URL (S8) and OAuth callback (§3.17) name that domain. A merchant that compares these with the A2A directory can link the label and key to the DID. Dina does not route around this (no egress proxy); the owner's UCP settings say so plainly on a public server.
- **The Dina-run host,** `<label>.ucp.dinakernel.com` (D2).
  - **The label** is 128 bits derived from the node's master seed (HKDF-SHA256, info `dina:ucp:label:v1`), written as exactly 26 characters of lower-case base32 (`[a-z2-7]`), no hyphen. Being derived, it survives a restore or a move to a new device: the node keeps its buyer identity at every merchant, so merchants keep sharing the orders it placed. It reveals nothing about the DID without the seed.
  - **Strict parsing.** The host accepts an upload only for a label matching `^[a-z2-7]{26}$`, and maps a hostname matching `^[a-z2-7]{26}$` to that label's profile; anything else is a 404, except fixed paths every label host serves: `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json` for the Dina app's claimed links (§3.17), the same bytes on every host; `POST /webhooks/orders`, the drop-box (S9), which answers `200 {"ucp":{"version":"2026-08-25"}}`, reads nothing, and is rate-limited per label; and `/oauth/callback`, which serves only the static "open this in the Dina app" page. Test: an upload whose label breaks the syntax is refused, and a hostname that is not exactly a label is a 404.
  - **Upload, not publication.** The node's Core builds the exact profile bytes and a **publication envelope** over them: `{op: upload | pause | retire, did, label, host: "ucp.dinakernel.com", epoch, instance, revision, issued_at, versions, sha256 of each document, keys: [{thumbprint, generation, phase: staged | active | retiring, not_before, retire_after}], retire: [thumbprints]}` (one schema for all three operations; `versions`, document hashes and `keys` are required for `upload`, `retire` for `retire`, and `pause` carries neither) (`issued_at` is for the record only; ordering comes from `revision`, below), signed with the node's root Ed25519 key (`dina_signing` in its DID document). It sends envelope and documents straight to the host (`PUT https://ucp.dinakernel.com/v1/profiles/<label>`). Nothing goes to the PDS, so nothing on the public firehose links the label or the UCP key to the DID.
  - **The host checks** the envelope signature against the DID document as resolved now (the way `appview/src/shared/a2a/card-verify.ts:147-177` checks A2A cards and their directory envelope), that `host` is its own name, and that each document hashes as stated. A forged upload that copies the key but changes a capability or a webhook URL fails. The host also checks that each `keys` thumbprint is a JWK listed in the documents. It keeps an unchangeable `thumbprint → generation` map per label: a known thumbprint must carry its recorded generation, and a new thumbprint must carry a generation above every one recorded. The upload's highest generation may never fall below the label's highest; older keys still registered and not retired may stay listed beside it, as a rotation's overlap needs (`signatures.md:223-228`). Retired keys are refused on their own (below). Test: publish generations 0 and 1, then a new revision with a changed webhook URL and both keys still listed (accepted), then retire generation 0, then an upload listing it again (refused).
  - **Label ownership.** The host keeps a registry, `label → did`, written in one transaction on the first valid upload for a label. Any other DID's upload for that label is refused whatever its revision.
  - **Revision, held by the host.** The host is the authority for each label's revision counter. `GET https://ucp.dinakernel.com/v1/profiles/<label>/state` (public; it names no DID, and every field is already implied by the served profile or harmless) returns: the current revision; the current publisher epoch and its instance; the highest generation; every registered key with its thumbprint, generation, `phase`, `not_before` and `retire_after`; the retired thumbprints; and whether the label is serving or paused. A test checks each field. An upload must carry exactly the current revision plus one, and the host applies it with a compare-and-set; a repeat of any already-applied revision with identical bytes is a replay: it answers success and changes nothing (the same rule as for Pause and Retire, below); anything else is refused with the current state, so the node reads it and tries again. A wrong clock on the node therefore never blocks an update. Test: an upload made while the node's clock ran a day ahead, then the clock corrected and a restore, and the next update succeeds at once.
  - **Retired keys stay retired.** When an upload removes a key, the host adds its thumbprint to the label's retired list, kept forever, and refuses any later upload that lists it.
  - **Surviving a host restore.** A restored host database could roll back the retired list and the counters. So every change to a label's security state (label binding, revision, highest generation, a retirement) is first appended to an append-only log kept off the host (a write-once object store, separate from the database backups), and the host answers the upload only after that append succeeds. A restored host replays the log over its database before serving any profile or accepting any upload, and serves nothing for a label whose log it cannot read. Test: restore a host backup taken before a retirement, with the node offline: the retired key is never served, and no counter goes back. A restored node starts unpublished (as A2A's publisher starts a restored node inactive, `packages/core/src/a2a/publication.ts:11-23`): before signing anything or uploading, it reads the label's state, which carries each key's rotation phase and times, and signs with the key in phase `active`, so an ordinary restore keeps the same key and identity. A `staged` key becomes active only at its recorded `not_before`; a `retiring` key stays listed until its `retire_after`. Tests (U7): a restore during the wait before activation, and during the seven-day overlap; no request uses the staged key early and the old key is not dropped early. Only if that key is retired does it derive the next generation, which needs U7's machinery; before U7 the node stays unpublished and tells the owner UCP is off until then. It never brings back a retired key. Test: restore a backup taken before a compromise recovery; the removed key is never accepted again. A label stays bound to its DID forever and is never reissued. Two signed operations stop serving:
    - **Pause** (`DELETE /v1/profiles/<label>`): stops serving the documents and retires nothing. A later upload with the same keys and the next revision resumes serving. The owner's "Turn UCP off" switch calls this.
    - **Retire and withdraw** (`POST /v1/profiles/<label>/retire` naming the thumbprints): appends the thumbprints to the retired list in the off-host log, then stops serving. The owner's "My key may be compromised" control calls this; afterwards that key can never be listed again, so the node stays off until it has a new generation (U7).
    - **One ordered contract for all three.** Upload, Pause and Retire are each a signed envelope naming the operation (`op: upload | pause | retire`) and the revision it claims, and each must claim exactly the current revision plus one, applied by compare-and-set and appended to the off-host log in that order. A repeat of an already-applied revision with identical bytes answers success and changes nothing; any other stale claim is refused with the current state. So a delayed upload made before a Pause, or a delayed duplicate Pause after a resume, can never undo the newer state.
    - **Publisher epoch.** Two live nodes can share a label and key: a restored copy while the old server still runs, or a node moved to a new machine. As A2A's publisher does (`packages/core/src/a2a/publication.ts:11-23`), the host records the label's current publisher `epoch` together with the `instance` that claimed it (a random id each installation draws once, carried in every envelope), and refuses any envelope from a lower epoch, or from the current epoch under another instance. The host binds an epoch to its instance in the same compare-and-set that applies the activation, so of two activations that both read epoch E and claim E+1, one wins and the other is refused; a revision retry never adopts another installation's epoch. A node claims a greater epoch only through an explicit owner activation ("Use this device for shopping"), never through a retry or the daily re-upload. A node that reads a greater epoch than its own moves to `stood_down`: it stops uploading and stops taking webhooks, and tells the owner which device now holds shopping. A restored node starts `stood_down` until the owner activates it. Test: two nodes from one seed upload in turn; only the activated node's documents stay served; an old installation uploading after the new one's activation, or after its Pause, changes nothing; and of two simultaneous activations from the same observed state, only the winner may change publication afterwards, including after its own Pause.
    - **A local fence.** On the node, the owner's switch moves a publication fencing generation (as A2A's publisher does, `packages/core/src/a2a/publication.ts:171-196, 376-385`). Every upload job binds the generation current when it began, and re-checks it, and that UCP is still on, before sending and again before rebuilding after a refused attempt; a job from an older generation stops without sending.
    - Tests: pause then resume with the same key (served again); retire then an upload listing that key (refused); an upload prepared before a Pause and delivered after it (refused, still paused); a duplicate Pause delivered after a resume (no effect); a refused upload whose rebuild meets a turned-off switch (stops).
  - **Who knows the link.** Only the host's operator (Dina's own infrastructure) holds the label-to-DID registry; it is never served or published. The DID document carries no profile URL.
  - The host runs as a route in `appview-web` with its own Postgres tables, behind the wildcard host in Caddy.
  - **Upload lifecycle.** Core uploads at boot, whenever a document changes (a capability, a key, a webhook URL), and every 24 hours. Failed uploads retry with backoff (1 min doubling to 1 hour). Every hour Core fetches both documents from the host through `ucpFetch` and compares them byte for byte with what it built. Status (`served`, `stale`, `unreachable`, `refused`) is shown in the owner's UCP settings; while it is not `served`, Dina tells the person before a search fails with `profile_unreachable`.
  - **Registry loss.** The `label → did` registry is in the shared-infra backup scope (`docs/DISASTER_RECOVERY_PLAN.md` gains it), and its bindings are in the off-host log above, so a restore never reopens a served label to a first claim. Tests: a host outage (status and retry), and a restore from an older backup followed by an upload for a known label from another DID (refused).
- **Host logs:** the wildcard host keeps no per-host access log. It keeps counts only (requests per minute, status codes), with error lines that omit the host label, for 7 days. Otherwise the host's logs would record which merchant fetched which person's profile, and when.
- Tests: two valid DIDs claiming one label, including at the same moment; a replayed older revision; an upload after a pause (accepted with the next revision) and after a retirement (refused if it lists a retired key); a copied envelope with altered documents; a pause end to end (the documents stop being served, the label stays bound, the same key resumes).

Infra cost: a wildcard DNS record and a wildcard certificate (Caddy DNS-01 with the DNS provider's plugin) on test and production.

### 3.6 Talking to a merchant

**Plan, in `@dina/ucp` (pure) and `packages/core/src/commerce/ucp/` (Core):**
1. **Discover.** Fetch `https://<merchant>/.well-known/ucp` under the policy; refuse redirects; cache by `Cache-Control` with a 60 s floor, revalidate with `If-None-Match`, serve stale while revalidating.
2. **Choose a version.** The newest date in `{ucp.version} ∪ keys(supported_versions)` that Dina speaks; fetch the leaf profile if needed and refuse it unless its `ucp.version` equals the chosen key (`overview/index.md:3510-3529`). No shared version → no UCP calls; offer the store's web page.
3. **Filter entries.** Drop any `dev.ucp.*` entry whose `version` differs from `ucp.version`. Drop any entry whose `schema` URL fails authority binding (`overview/index.md:873-969`: reversed host labels must equal the name or be a dot-aligned prefix of it; https only; no IP; at least two labels). 
4. **Intersect** capabilities the way the merchant will (`overview/index.md:1809-1833`): same name, highest shared version by exact string, prune extensions whose parent is gone, repeat until stable. Dina uses the result to predict what the merchant will echo and to refuse an operation the merchant cannot serve.
4a. **Fetch and compose schemas** (A18, S21), for the negotiated set only, after intersection:
   - **Which URL.** Each negotiated capability's and extension's `schema` URL, only after it passes authority binding; never a URL that fails it. For a `dev.ucp.*` entry the URL must also sit under the negotiated release's path (`https://ucp.dev/2026-08-25/schemas/...`), as the spec's own profiles write it.
   - **Fetching.** Through `ucpFetch` (https, no redirects, no special-use address), 256 KiB per document. Cached by URL, honouring `Cache-Control` with a 60 s floor and revalidating with `ETag`.
   - **Identity.** The root schema's `name` must equal the capability's name, or the capability is dropped; a merchant cannot point `dev.ucp.shopping.checkout` at the order schema or at another release's.
   - **References.** Every schema's base for `$ref` resolution is the URL it was fetched from, never its own `$id`: in the spec's source the `$id`s are unversioned (`checkout.json:3`), while the published files carry versioned `$id`s and absolute versioned `$ref`s, and resolving from the retrieval URL keeps relative references inside the negotiated release in either case. An absolute `$ref` must pass authority binding for the capability that named it and, for `dev.ucp.*`, sit under the same release path.
   - **Limits per merchant negotiation:** at most 64 schema documents, `$ref` depth 16, and 2 MiB in all. A cycle is resolved through the URL cache, never fetched twice. Over a limit, the capability is dropped.
   - **Composing.** Base and extension schemas with `allOf` as the spec describes (`overview/index.md:1113-1244`); each extension's `requires` checked against the chosen versions; the `ucp_request` / `ucp_response` annotations resolved per operation.
   - **Failure.** A fetch or check failure drops that capability for this merchant and shows in the owner's merchant status; Dina never sends a request it cannot validate.
   - Tests: a merchant pointing checkout at the order schema; a `$ref` loop; a schema graph over each limit; a relative `$ref` that would resolve outside the release under its `$id`.
5. **Pick a transport.** MCP if offered, REST otherwise (D9). REST joins `endpoint` and the OpenAPI path; MCP posts JSON-RPC to `endpoint`.
   5a. **The MCP session**, per endpoint, following the MCP lifecycle and Streamable HTTP transport (MCP spec 2025-11-25): `initialize` with Dina's supported protocol versions; record the negotiated version and any `Mcp-Session-Id`; send `notifications/initialized` and accept its empty 202; then send `MCP-Protocol-Version` and the session id on every later request. A 404 on a request carrying a session id means the session ended: start a new one and send the same request again with the same bytes and idempotency key (a new JSON-RPC envelope id is not allowed for a stored mutation, so the stored envelope is reused as is). Accept JSON or SSE answers. A merchant that answers `tools/call` without any of this (Shopify) still works, since the client only adds headers it was given. Tests: a mock that refuses calls before initialization, and one that expires sessions between calls.
6. **Send.** Every request carries the profile URL (`UCP-Agent` header; also `meta["ucp-agent"].profile` on MCP), a fresh `Request-Id` (REST), an `Idempotency-Key` on every state change (REST: create, update, cancel; MCP: also in `meta`), and from U2 an RFC 9421 signature.
7. **Read the answer.** A 200 may be a business failure: branch on `ucp.status == "error"` before reading resource fields; read `messages[]` first. Transport errors (400, 401, 403, 409, 422, 424, 429, 503) are keyed on the body's `code` (`error.data.code` on MCP), never on the HTTP status alone: Shopify answered `profile_unreachable` with 422, not the spec's 424. Honour `Retry-After` and `error.data.retry_after`.

Validation (A16, A18): every request is validated against the composed schema before it is sent, and every answer after it arrives. The phone runs Core on Hermes, which does not allow code generated at run time, so the validator must interpret schemas rather than compile them (ajv compiles; an interpreting JSON Schema 2020-12 validator such as `@cfworker/json-schema` does not). It is a new dependency of Core's UCP module only, never of the zero-dependency `@dina/ucp`; U1 checks, before anything else, that it runs on Hermes and the mobile bundle still builds. The schemas are open (`additionalProperties: true`), so unknown fields and enum values pass, as A16 requires. Dina's own hand-written readers in `@dina/ucp` still type the fields it acts on. The official `@ucp-js/sdk` Zod schemas (0.5.x) are a test-only dev dependency: every fixture and recorded live answer is also checked against them.

### 3.7 What the owner approves, and what that approval covers

Searching and browsing send no personal data and commit to nothing; they need no card (but see §3.16 for search text).

**Carts** are for browsing only and carry only items, quantities and units (no buyer fields, no context beyond §3.16's allowed fields). They need no card, so they do not pass the checkout permit gate; they have their own table, `ucp_carts` (Core-minted `cart_id`, `merchant_origin`, `merchant_cart_id` null until the create answer arrives, `version`, `transport`, `endpoint`, `state`: `creating | open | gone`, `expires_at`, the last full cart answer, and a dispatch slot with lease and fencing generation like a session's). Updates are full replacements built from the last answer, one at a time per cart. Cart mutations use the same request journal and retry rules as §3.10 (stored bytes, same key, a 23-hour deadline), with no permit. A cart answer of `not_found`, or one past its `expires_at`, moves it to `gone`; Dina offers to build it again. Tests: a lost cart-create answer resent; two updates queued at once (sent one after the other); a cancel; an expired cart.

**`ucp_checkout_start`** ("Start checkout at <merchant>?") is raised before anything is sent that opens a checkout. It shows the merchant, its PeerLens trust line, the exact line items (merchant variant ids shown as product names), quantities and units, any discount codes the person gave, and the exact personal-data fields to be sent (none by default, D3). Approval mints a single-use **start permit** (the A2A pattern, `packages/core/src/a2a/permits.ts`) bound to the hash of this **checkout intent**: the merchant's canonical identity (§3.12), the negotiated version, transport, exact endpoint URL and negotiated capability set, the linked-account credential reference and revision (if any, U4), line items with quantities and units, discount codes, personal-data fields and values. As A2A rejects drift in endpoint, card hash and credential revision (`packages/core/src/a2a/permits.ts:189-202`), the dispatch gate refuses a send when a profile refresh changed the endpoint, transport, version or negotiated capability set, or when the credential changed, and voids the permit: before the create the session becomes `stale` and the owner sees a new card when Brain proposes the checkout again (U2.4 does not raise one on its own: a new card needs the products read again, which only a proposal from handles does); after the create, the session stays open with nothing more to send. The gate checks this on the first send of every mutation, against the session's own endpoint and transport as well. Other profile changes (a merchant key rotation, a new policy link) do not void the permit; the hash of the profile used is recorded with the session for the record only. A U0 vector covers a key-rotation-only profile change (permit stays valid). A request already sent is never moved: its retries go to the stored endpoint, and if that endpoint is gone the request stays unsettled (§3.10).

What the permit authorises:
- One `create_checkout` at that merchant whose body carries exactly the intent's lines, codes and personal data. Dina never sends `cart_id` (§2.1 row 12): the approved lines are what the merchant receives.
- Updates to that same session, without a new card, only when they keep the lines, quantities, units, codes and personal-data set identical, and only fill in ids the merchant itself offered: line-item ids, a fulfillment option id from the merchant's `groups[].options`, a pickup location id from the merchant's own destinations. Core checks every update body against the permit before sending.
- Anything else (another item, a changed quantity, new personal data, a new code) needs a new card. A quantity the merchant revised (an increment rule) is shown on the hand-off card, never re-approved silently.
- The permit lapses when the checkout reaches a terminal status, at the session's effective expiry (§3.12), after 6 hours, or when the hand-off card is raised, whichever is first.
- **One retry deadline.** A mutation's effective retry deadline is the earlier of its permit's lapse and `first_sent_at + 23 h`. When it passes unsettled, a create moves the session to `create_unknown`, and an update to `unsettled`; both are terminal, free the slot, void the permit, and tell the person once, with the store link. A barrier that gives up after its three 409 resends moves the session to `unsettled` the same way.
- **One dispatch gate.** Every checkout mutation, first send or retry, passes the same check in Core at the moment of sending: the permit is live, the body fits the permit, and the session's state admits that operation. A create is admitted from `awaiting_approval` once approved, and the same transaction moves the session to `creating`; a resend of that same create (same stored bytes and key) is admitted while `creating`; an update or a cancel is admitted only while `open`. A queued update or retry that meets a closed gate is not sent; if an earlier attempt of it may have reached the merchant (`sent`), Dina reconciles with Get Checkout instead.
- **One mutation at a time.** Each session has one dispatch slot, a column on its `ucp_checkouts` row taken in a transaction with a lease and a fencing generation; a mutation is sent only by the holder, and the next waits. When a holder's lease expires with a mutation unsettled (it crashed after sending), a recovery holder takes the slot in one transaction, bumping the generation, and may only resend that same unsettled mutation, with its stored bytes and key; no other mutation is admitted until it settles. A late answer reaching the old holder is written only if its generation is still current, so it cannot overwrite the recovery holder's result. Tests: crash after send, takeover and settlement; a late answer to the crashed holder after takeover. The workflow lane alone does not give this (`packages/core/src/workflow/repository.ts:1090-1120` does not exclude a second running task on a lane).
- **The hand-off barrier.** The hand-off card is raised only when the slot is free and every mutation the session ever sent has a definite answer. A transport deadline does not stop a request already in flight at the merchant (`packages/core/src/a2a/host_transport.ts:101-120`), so a mutation whose answer was lost is settled by resending its stored bytes under the same key (§3.10) until the merchant answers; the merchant runs it once and returns the cached result. A 409 to these identical bytes can only mean the merchant is still running the first attempt (the spec defines 409 for a different body, `signatures.md:833-834`), so the barrier waits (`Retry-After`, or 30 s) and resends the same bytes, at most three times; this is the one case where a 409 is resent. Still unsettled after that, the session gets no hand-off card and the person is told at once. A Get Checkout alone does not settle it, since it cannot prove a late write will not arrive. If a mutation cannot be settled before its retry deadline, the session never gets a hand-off card: the person is told, and Dina opens a new session only when they ask. Tests: a mutation whose answer is lost, spanning the moment the hand-off card would be raised, with a restart in between; a mock merchant that answers 409 to a duplicate while the first is still running, then the cached result.

**`ucp_checkout_handoff`** ("Review and pay at <merchant>") is raised from the merchant's checkout answer: line items, the merchant's totals in the order given with its `display_text`, every warning, applied and provisional discounts, the fulfillment choice and its cost, `expires_at`, and the merchant's links (terms, privacy, refund, shipping). Raising it moves the session to `handed_off` in the same transaction (§3.12): from that moment no update or cancel can pass the dispatch gate, whatever happens to the card. Its action is "Open <merchant>'s checkout"; approving it opens the hand-off URL (§3.8). Denying it, or letting it lapse, changes nothing at the merchant: the session is left to expire there, and Dina says so. It is presence-gated (`PRESENCE_GATED_PAYLOAD_TYPES`, `packages/core/src/server/routes/workflow.ts:1425`): a person, not an agent, opens a payment page.

Card text comes from Core, rendered from the merchant's answer (sanitised), never from Brain. The guard in §3.11 filters what Brain reads; it does not filter what the owner reads.

Rendering rules the spec puts on any buyer (`checkout/index.md:842-886, 1296-1353`): totals in the order given, never recomputed, `display_text` when present; warnings always shown; a disclosure beside its item and never dismissible; markdown rendered safely; HTML sanitised. Where a surface cannot meet one (the phone mirror's text cannot place a disclosure beside its item), the hand-off itself is the required escalation (`index.md:850-852`): the person reads the disclosure on the merchant's page.

Core-minted card plumbing follows A2A: `ucp_checkout_start`, `ucp_checkout_handoff` and `ucp_search_review` (§3.16) all in `CORE_MINTED_PAYLOAD_TYPES` (`workflow.ts:1451`), minted in the same transaction as their session row, decided through a decision handler composed at all three roots (`apps/home-node-lite/core-server/src/boot.ts:751`, `packages/home-node/src/workflow_plane.ts:223`, `apps/mobile/src/services/bootstrap.ts:757`), rendered in `apps/mobile/src/hooks/useServiceInbox.ts` and `components/approval_inbox.tsx` and in `apps/home-node-lite/core-server/src/server/owner_console.ts`.

### 3.8 The hand-off URL

**Plan,** in order:
1. The checkout's `continue_url`, if present, https, and not expired.
2. A permalink, if the merchant advertises `dev.ucp.shopping.permalink`: `config.endpoint` + `/{id}:{qty},…`, ids outside `[A-Za-z0-9._-]` written as `~` + base64url without padding, never percent-encoded (`permalink.md:171-200`), no personal data, within 2,048 bytes. The merchant answers with a 303 and MUST NOT treat it as an order. A permalink hand-off has no session Dina can watch (§3.12).
3. The `continue_url` of an `error_response`, if no session could be created.
4. The store's home page, with a plain note that the cart could not be carried over.

The URL's host must be the merchant's profile host, a host the merchant's profile names (an MCP or REST endpoint host, the permalink endpoint), or a subdomain of them; otherwise Dina shows the full URL and says it leads elsewhere. Dina never appends parameters to `continue_url` (that is the embedded-checkout protocol, which Dina does not speak).

### 3.9 Cards on the paired phone

The phone mirror today: the server's sync worker sends each mirrored card with the source task's own `expires_at` (`apps/home-node-lite/core-server/src/approval/phone_approval_sync.ts:147`); the phone's Core refuses any proposal more than 15 minutes out (`packages/core/src/server/routes/remote_approval.ts:34`, `MAX_TTL_SECONDS = 15 * 60`), accepts only `risk_level: 'HIGH'`, carries text only, and stores it as `remote_facade_action_v1` (`remote_approval.ts:75-79`). A mirrored decision is applied on the server by `applyOwnerWorkflowDecision` (`phone_approval_sync.ts:188-190`), which does not pass through the route's presence check (`workflow.ts:433-444`).

**Plan:**
- `proposalForTask` gains builders for `ucp_checkout_start` and `ucp_checkout_handoff`, with titles and details inside the mirror's limits (`packages/core/src/approval/mirror_text.ts`). The hand-off detail carries the merchant, the total with its `display_text`, the item count, the expiry and every warning's text; when it does not fit, it carries the total and "N more details on the merchant's page", which is honest because the hand-off itself shows them.
- **Rolling window.** Each window is a stored row: `(source task, window number, wire source id = <task id>:w<n>, exact payload, fixed expires_at = min(source expires_at, window start + 15 min), receipt)`, written before its first POST. The phone derives the mirror id and idempotency key from the wire source id (`remote_approval.ts:74, 125`), so each window is its own proposal and never collides with an earlier one (`remote_approval.ts:85-93`). The server computes the expected mirror id per window, keeps one receipt per window, and maps a decision on any window back to the source task. A window is POSTed once. After any POST whose outcome is uncertain (no answer, or a lost answer), the server reads the window by its stored expected mirror id through the phone's status GET (`remote_approval.ts:139-153`, which has no expiry check, unlike the POST's at `:234-240`), and POSTs again only when the phone answers that the proposal does not exist and the window's expiry is still at least 15 seconds away. Once the window exists, its state is read only through that GET, which returns the stored decision and its error, so a decision made just before a window expired is still read after a server outage, and an undecided lapsed window reads as `expired`, not as a denial. In the last minute of a window, while the source is pending and its own expiry is later, the worker opens the next window. A window the phone reports `expired` retires that window only; today's mapping of a phone `expired` to a source denial (`phone_approval_sync.ts:192-197`) applies only once the source's own expiry has passed. An explicit approval or denial in any window settles the source, and the open windows are withdrawn.
- **`link_url`.** An optional field on the proposal: https only, at most 2,048 bytes, checked on both ends, shown as its host before the tap.
- **Presence.** A new `presence_required: true` field on the proposal. The phone stores such a mirror with a presence-gated payload type, so its own route demands presence before the decision; it opens `link_url` only after that check; and its signed decision response carries `presence_verified: true`. The server refuses to apply a mirrored decision for a presence-gated source type without it, and `applyOwnerWorkflowDecision` gets the same check, so neither path can skip presence.
- **Opening the link before the server knows.** The phone may open `link_url` as soon as its own presence check passes; the server learns of the approval on a later tick. That is safe because of the hand-off barrier (§3.7): the card exists only after every mutation of the session was settled, and the fence stops any new one.
- Tests: a 6-hour hand-off card reaches the phone and is decided in its third window; window 2's POST is accepted after window 1 lapsed; a create that succeeds with its answer lost, an owner decision inside that window, and a server that reconnects after the window's end but before the source's: the original decision settles the source; window 1 lapsing with no decision leaves the source pending and reads as `expired`; an approval just before a window's end, read after the server reconnects past that end; repeated ticks and a restart within one window resend identical bytes; an approval on the phone whose sync is delayed past the card's expiry cancels nothing; a mirrored approval without presence is refused on the server; the direct route without presence is refused.

### 3.10 Idempotency and retries

**Plan:** before sending any state change, Core writes to `ucp_requests`: the 128-bit key (UUID v4), the operation, the merchant, the session, the **exact request bytes** (for MCP, the whole JSON-RPC envelope, including its `id`), their SHA-256, `first_sent_at`, and a `retry_deadline`: for a cart, `first_sent_at + 23 h` (inside the 24 hours a merchant must keep keys, `signatures.md:826-834`); for a checkout mutation, the earlier of that and its permit's lapse (§3.7).
- A retry before the deadline resends the stored bytes with the same key, but only through the dispatch gate (§3.7): a retry whose permit has lapsed, or whose session's state no longer admits that operation, is never sent. A changed body always takes a new key (`signatures.md:844-848`).
- After the deadline, after the gate closes, or if the stored bytes are lost, Dina does not resend. It reconciles: Get Checkout (or Get Cart) by id when the id is known. A create whose answer was lost and whose id is unknown is marked "unknown at the merchant"; the person is told, and Dina opens a new session only when they ask.
- A 409 to a request whose bytes Dina has not sent before means Dina broke its own rule: it is logged as a defect and reconciled, never resent. A 409 to identical resent bytes during the hand-off barrier follows §3.7.
- The `sent` flag from the transport separates "never left" (safe to send again) from "left, answer lost" (resend the same bytes before the deadline).
- Rows are deleted 48 hours after a terminal answer.
- Tests: a first create admitted and moved to `creating`; a lost create answer resent while `creating` after a restart; crash after send and before answer, then restart and retry; retry after the merchant has dropped the key at 24 hours (the mock merchant expires keys); a lost create answer.

### 3.11 Merchant data and Brain

Product titles, descriptions, message text and policy text are written by merchants, and so are ids, units and URLs: `item.id` is an unrestricted string (`source/schemas/shopping/types/item.json:12-14`). The assessment notes the "whisper" attack: text that reads as an instruction to the agent. A2A's guard is fail-closed and Core-owned (`packages/core/src/a2a/guard_jobs.ts`, worker `packages/brain/src/a2a/guard_worker.ts`), and judges every string and key of a remote value (`guard_worker.ts:63-77, 100-112`). It is bound to A2A operation rows, and its lease allows up to 3 minutes (`guard_jobs.ts:43`).

**Plan:**
- **Handles for opaque values.** Core keeps merchant ids, variant ids, URLs, permalink tokens and unit codes it does not recognise, and gives Brain local handles (`m1`, `p3`, `v3.2`, `u1`). Brain proposes actions in handles; Core maps them back for every protocol call. Brain never sees a merchant-chosen id or URL.
- **Checked structured fields.** Prices, quantities, scales, increments, known Rec 20 codes, known statuses and booleans pass to Brain after type checks.
- **Guarded text.** Every other merchant string Brain may read (titles, descriptions, option labels, message text, `display_text` of unknown units, policy text) goes through the guard before Brain sees it. Only these fields are guarded, each cut to a fixed length (title 200 characters, description 1,000, others 300).
- **Granularity.** The guard gives one `passed | blocked` verdict per job (`packages/core/src/a2a/guard_jobs.ts:127`). A merchant answer is therefore split into **one job per product** (or per checkout message, or per policy), each at most 8 KiB after cutting. A blocked job withholds that product's text from Brain behind a fixed "merchant text withheld" marker; other products are unaffected; the owner still sees the real text. Test: one hostile title among clean products withholds only that product.
- **The queue.** A UCP twin of the A2A guard store, `ucp_guard_jobs` (migration in U1), reusing the pure guard logic; the Brain guard worker claims from both queues and runs a search's jobs in parallel.
- **Latency and a hard budget.** A merchant decides how many products it returns (`catalog_search.json` sets no maximum), so Core bounds the work before queueing anything: at most 20 products per merchant answer and 40 per search are guarded, in the merchant's order; the rest reach Brain as handles and structured fields only. The Brain worker runs at most 4 guard calls at a time across A2A and UCP, taking jobs in turn from each search so one search cannot starve another. A search's jobs share a 10-second budget; jobs not started by then are abandoned, not dispatched, and a call already in flight is left to finish but its result is used only if it arrives within the budget (the timeout does not stop the call, `packages/brain/src/a2a/guard_worker.ts:125-136`). After a restart, abandoned jobs stay abandoned. Test: a response near the byte cap with thousands of small products queues at most 40 jobs and never more than 4 calls at once; every other product's text stays withheld.
- **What the owner sees** is never filtered by the guard (§3.7).
- **Images.** Loading a merchant-chosen image URL on the phone or the console would tell the merchant the person's address and when they looked, and fetching it on the server outside `ucpFetch` would be an SSRF path. Through U2, Dina loads no merchant images: cards and results show a placeholder, and a disclosure warning that carries an `image_url`, which the spec says must be rendered (`checkout/index.md:842-844`), makes the hand-off the required escalation (`index.md:850-852`). A later step may fetch images on the server through `ucpFetch` with size and type caps and serve them to the UI by handle.
- Tests: adversarial fixtures with instructions in ids, units, URL paths, query strings, option labels and message text; none reaches Brain unguarded.

### 3.12 After the hand-off

Dina never completes the checkout, so it never receives the completed checkout that carries `order.id` and `permalink_url` (`checkout.json:137-141`). Get Order needs that id (`order/index.md:565-567`) and is answered only for orders from checkouts this buyer created (`rest.openapi.json:659`). Get Checkout after completion or cancellation may answer `not_found` once the merchant's own retention ends (`checkout/index.md:1065-1069`).

**Plan:** a session row `ucp_checkouts` and a `UcpHandoffWatcher`.
- **Columns:** `session_id` (Core-minted, primary key, minted with the start card); `merchant_origin` (the canonical identity: the origin of the merchant's root `/.well-known/ucp`); `leaf_profile_url` (the negotiated version's profile, which may differ); `version`, `transport`, `endpoint`; `merchant_checkout_id` (null until the create answer arrives); `state`; `dispatch_slot` (holder and lease expiry); `permit_id`; `effective_expires_at`; `created_at`. A unique index on `(merchant_origin, merchant_checkout_id)` applies once the id is known. `ucp_requests` and the permit reference `session_id`.
- **States:** `awaiting_approval` (card raised) → `creating` (create sent, no id yet) → `open` (id attached, in the same transaction that stores the create answer) → `handed_off` → `completed | canceled | not_completed | unknown`; also `declined` (start card denied or lapsed), `stale` (the merchant's negotiation changed after the yes and before the create, §3.7), `lapsed` (the permit ran out before the create was sent: nothing reached the merchant), `create_unknown` (create answer lost past its effective retry deadline), `unsettled` (an update or a barrier resend unsettled past its deadline, §3.7) and `create_failed` (the merchant answered the create with a definite `error_response`, such as `out_of_stock`; entered in the same transaction that stores that answer, it frees the slot, voids the permit, and offers the person the answer's `continue_url` or the store link, §3.8 step 3). A crash while `creating` resumes by resending the stored create bytes under the same key (§3.10); a lapsed slot lease is retaken by the next holder after the stored request has settled.
- The `open` → `handed_off` move happens when the hand-off card is raised (§3.7). From then on no update and no cancel passes the dispatch gate, including queued retries.
- **Effective expiry** = the checkout's `expires_at`, or creation + 6 hours when the merchant omitted it (`checkout.json:117-122`).
- The watcher calls Get Checkout at hand-off + 2 min, + 10 min, + 30 min, then hourly (phones: while the app is open). It stops at the effective expiry while the status is `complete_in_progress`, as the spec requires (`checkout/index.md:444-450`), and otherwise at the effective expiry + 1 hour.
- `completed`: record `order.id` and `permalink_url`, create the `ucp_orders` row (§3.14), close the permit.
- `canceled`: record it; tell the person only if they open the session.
- Still `complete_in_progress` at the effective expiry: `unknown`. Any other status still not terminal at the effective expiry + 1 hour: `not_completed`. Polling deadlines stop automatic polling; they do not end recovery. When a phone reopens, or the owner opens the purchase, within 7 days of the hand-off, Core makes one Get Checkout for each session still unsettled, except a session last seen `complete_in_progress` past its effective expiry, which the spec says must not be asked again (`checkout/index.md:444-450`). A terminal answer settles the session (and `completed` starts order tracking); anything else, or no read allowed, leaves `unknown`. Test: payment made while the phone is closed, and the app reopened the next day.
- `not_found` before any terminal answer: `unknown`: "Dina can't see whether you bought this at <merchant>; check your email from them." The store link stays on the record.
- A webhook naming this `checkout_id` (§3.13) settles the session at once.
- A permalink hand-off has no session to watch: the record says Dina cannot follow it.
- If the person paid on a different session the merchant created, Dina cannot see it; the outcome is `not_completed` or `unknown`, and the wording never claims the purchase did not happen.
- Tests: each outcome, a restart between polls, a webhook arriving before the first poll, a cancel attempted after hand-off, a crash while `creating`, a create whose answer is lost, and a create the mock merchant refuses with `out_of_stock`.

### 3.13 Order webhooks

A server node with a public domain lists `config.webhook_url` (`https://<public-origin>/ucp/webhooks/orders`) by default (S4, S8); the owner can turn it off in UCP settings, which show that the domain links to the node's DID through the A2A directory. Every other node lists the drop-box (A7). Anyone can POST to it, and its `UCP-Agent` header is chosen by the sender.

**Plan:**
1. The gateway applies its per-IP edge limit and a 512 KiB body cap, and passes the raw bytes and headers to Core.
2. Core parses the body within the cap and reads `checkout_id` and `id`. A business's `UCP-Agent` always names its root `/.well-known/ucp` (`signatures.md:620-621`), so lookups use the origin of that URL, the session's `merchant_origin` (§3.12), plus the merchant's id, never the id alone (two merchants may both issue `order_1`), and never the leaf profile URL a session negotiated (a merchant whose current version is newer lists v2026-08-25 under `supported_versions` at another URL). **If no session or order is held under that pair, the webhook is dropped unfetched, with a 200** (an unknown sender learns nothing). When both ids are known to Dina, they must name the same session.
3. Core writes the raw delivery to a durable inbox row (`ucp_webhook_inbox`) and only then does the gateway answer `200 {"ucp":{"version":"<v>"}}` (`order/index.md:801-802`). If Core cannot store it within 2 seconds, the gateway answers 503, so the merchant retries (`order/index.md:812`).
4. A worker verifies `Content-Digest` and the RFC 9421 signature with the keys of the root profile `UCP-Agent` names (§3.2; coverage per D7). A failure deletes the inbox row and records nothing, so it cannot suppress a later valid delivery.
5. On success, in one transaction: the `Webhook-Id` is recorded (keyed by `merchant_origin` plus `Webhook-Id`, kept 7 days) and a reconciliation request is queued for the resource (§3.14). A repeat of a recorded id adds nothing. The reconciliation is retried until it succeeds; the dedupe record says only that the event was taken, not that it was processed.
6. The webhook is a prompt: reconciliation fetches the order with Get Order (or the checkout with Get Checkout). Under Get Order, an old body replayed under a new `Webhook-Id` changes nothing, since only the fetched order is stored. When the merchant does not share the order through Get Order (§3.14), the verified webhook body is all Dina gets, and nothing orders those bodies: the signature covers the body (through `Content-Digest`) but not `Webhook-Id` or `Webhook-Timestamp`, the order carries no timestamp, merchants may redact optional fields such as `events` (`order/index.md:601-605`), and lines and adjustments may change in place (`order/index.md:33-35, 47-50`). So for such a **webhook-only order** Dina does not claim to know the current state:
   - **Seen ids, kept for good.** The id of every fulfillment event and every adjustment ever seen, with each adjustment's settled status (`completed` or `failed`) once seen, is kept for as long as the order record exists, survives the snapshot being dropped at close, and travels in the archive (§3.14). Events are a union by id: an event in any body really happened.
   - **Interruptions** come only from an id never seen before: a new fulfillment event of type `failed_attempt`, `canceled`, `undeliverable` or `returned_to_sender`; a new adjustment of type `dispute` or `cancellation`; or the first settled status seen for a `dispute` or `cancellation` adjustment, or a first `failed` status for any adjustment. Every other first settlement (a refund or credit completing, say) is recorded quietly in My Orders, as on a polled order (Silence First). A replayed body, an older body, or a body under an altered `Webhook-Id` adds no unseen id and so interrupts nothing.
   - **Lines, totals and expectations** are shown from the most recently received body, labelled "as last sent by <merchant>; may be out of date — check at <merchant>" with the `permalink_url`. They never drive the closed rule or an interruption.
   - **Closing:** a webhook-only order closes only by the 180-day rule or when the owner marks it done. A body for a closed order adds any unseen ids to its record (and may interrupt by the rule above) without reopening polling.
   - Tests: Get Order refused, then a newer body with redacted events and a different total, then an older body with an unseen event (the event is added; the total shown is labelled possibly stale; nothing closes); a quantity edited up after a line was fulfilled (shown as sent, not used to close); a same-id refund settling (recorded, no interruption); a dispute settling (one interruption, once); the same body under an altered `Webhook-Id`; a replay after the order closed, after body records expired, and after a restore of the closed order (no repeat interruption). Test: a mock merchant that refuses Get Order but sends signed webhooks; the order updates and closes by the rule.
- Tests: an unknown profile URL causes no fetch; a flood is limited at the edge; a replayed body; a valid webhook before the watcher's first poll; two merchants using the same order and event ids; an invalid delivery followed by a valid one with the same `Webhook-Id`; Core unavailable (503, then redelivery); a crash after the inbox write and after verification; a failed Get Order retried; a session negotiated through a `supported_versions` leaf, settled by a webhook whose `UCP-Agent` is the root URL.

### 3.14 Orders: polling, the closed rule, records

There is no polling guidance in the spec beyond `Retry-After`. Phones have no background execution (`apps/mobile/src/hooks/useRelayWake.ts`), so phone polling happens only while the app is open.

**Plan:**
- `ucp_orders` (migration in U3): `merchant_origin` (as §3.12), `order_id`, `checkout_id`, `session_id` (the local session it came from), the leaf profile URL used, `permalink_url`, version and transport, a derived summary (per-line status counts, latest fulfillment event, adjustments with their status), `last_change_at`, `next_poll_at`, `closed_at`, with a unique index on `(merchant_origin, order_id)`; webhook lookups by order id use that pair (§3.13). The full snapshot is kept only while the order is open.
- **One reconciler per resource.** Polling and webhook prompts both queue a request on the order's (or session's) single reconciliation job, a lease with a fencing generation. Only the holder of the current generation may write a snapshot, and it writes the snapshot, the derived summary and any notification in one transaction. Events are append-only (`order/index.md:95-101`), but a merchant may leave out or redact optional fields (`order/index.md:601-605`; `fulfillment.events` is optional in `order.json`). So event count is never used to judge a whole answer stale. Reads of one resource are serialised by the reconciler's lease, so answers are applied in the order they were asked for, and each part merges on its own: fulfillment events are a union by event `id` (a stored event is never dropped because a later answer leaves it out or redacts it); adjustments merge by `id`, a later status replacing an earlier one; line statuses, totals and expectations take the latest answer. Tests: two answers arriving in reverse order; a lease taken over after a crash; a stored shipment followed by a valid answer with `events: []` and a new pending dispute: the shipment stays, and the dispute is recorded and interrupts.
- A `UcpOrderPollSweeper` beside `ReconcilePollSweeper` in `startCommerceSweepers` (`packages/core/src/commerce/sweepers.ts:130`) queues requests on that job: every 15 minutes on the first day, hourly in the first week, every 6 hours after, with jitter; daily on a node that also takes webhooks.
- **Order capability not negotiated.** A Get Order answered `capabilities_incompatible` is treated like a merchant that does not share the order (below). U3's mock merchant enforces the platform config schema.
- **A merchant that will not share the order.** Platform access to an order is a MAY, for orders "the platform originated" (`order/index.md:576-598`), and in a hand-off the merchant took the buyer and payment details itself. A 401 or 403 carrying a Bearer challenge is handled first, as §3.17 says: `invalid_token` refreshes once, `insufficient_scope` or `identity_required` suspends polling and asks the owner to authorise or link, and polling resumes after they do. Until U4 builds linking, Dina cannot do that, so such a challenge counts as "does not share this order" (below); U3 tests a merchant answering Get Order with 401 `identity_required`. Only a business-level `unauthorized` (an HTTP 200 with that message, `order/index.md:635-653`), or a 401 or 403 with no challenge Dina can act on, stops polling and records "<merchant> does not share this order with Dina"; My Orders shows the order with "Track or return at <merchant>" (`permalink_url`), and from U4 offers to link an account, which gives buyer-level access.
- **Closed rule (Dina's own):** every line is `fulfilled` or `removed`, no adjustment is `pending`, and nothing has changed for 30 days; or the merchant answers `not_found`; or the merchant does not share the order (as just defined, never a suspended one) on a node that takes no real webhooks; on a node that does (S8), such an order instead becomes a webhook-only order and closes by §3.13's rule; or 180 days have passed. A closed order drops its snapshot and keeps the summary.
- The order appears in My Orders beside D2D orders (a projection into `listPlacedOrders`, `packages/core/src/commerce/placed_orders.ts:151`), with "Track or return at <merchant>" opening `permalink_url`. Only a failure (a failed delivery, or a failed refund or other adjustment), a cancellation or a dispute interrupts (Silence First).
- A minimal `purchase_decision` vault item (the type exists, unused: `packages/core/src/vault/validation.ts:42`) records what was bought, where, when and for how much, once the order is known (D5).
- **Backup and restore.** The node's label needs no backup: it is derived from the seed (§3.5), and a restored node re-uploads its profiles under the same label. The archive (`packages/core/src/export/archive.ts:118-180`, an explicit table allow-list) gains `ucp_orders` and `ucp_checkouts` (history and identity needed for reconciliation, including a webhook-only order's seen ids, §3.13), and leaves out `ucp_requests`, permits, guard jobs, the webhook inbox, link tokens and the dispatch slot. On restore, every session not in a terminal state becomes `unknown` and any permit is void, so a restored node never sends a mutation from an old backup; open orders resume polling. Tests: an archive round trip; a restore from a backup older than a hand-off; a restore onto a new device after which Get Order on an existing order still succeeds.

### 3.15 The merchant index (U5)

AppView makes no outbound fetches today except DID resolution. Its A2A directory is built from PDS records over Jetstream (`appview/src/ingester/a2a-directory.ts`), with ranking that keeps trust and text apart (`appview/src/api/xrpc/a2a-directory.ts:143-196`). PeerLens has no web-domain subject type; the closest fit is `{type: 'organization', uri: 'https://merchant.example'}` (`appview/src/db/queries/subject_identifier.ts:53`).

**Plan:**
- **Which merchants.** Origins that already appear as `organization` subjects with a `uri` in PeerLens attestations (D4). Nothing about anyone's purchases is published.
- **Fetching.** A new AppView job, `ucp-merchant-crawler`, fetches each origin's `/.well-known/ucp` under the rules of §3.6, using `@dina/net-policy` (§3.3), at most once per origin per day, honouring cache headers, and records the version, transports and capabilities it validates. A profile that fails validation is recorded as unusable with the reason.
- **Serving.** `com.dinakernel.ucp.searchMerchants` (by capability, by text over the merchant's name and categories) and `getMerchant`, ordered the A2A directory's way: valid profiles first, then trust, then text. A merchant with no PeerLens record is shown as unverified.
- **Packaging.** AppView gains a dependency on `@dina/net-policy` and `@dina/ucp` (and through it `@dina/a2a`, already synced for the A2A directory); `deploy/managed/infra/deploy_shared_infra.sh` syncs them into the AppView build, and the AppView version and release manifest move together (the `scripts/release/component_version.sh` check).
- **Brain.** A `search_ucp_merchants` tool; merchant choice in the comparison card comes from trust, never from the merchant's own text (Verified Truth).

### 3.16 Personal data and search text

Search sends text Brain wrote. A2A Lane 1 already treats Brain-written outgoing text as untrusted: it scrubs strings and keys (`packages/core/src/a2a/proposal.ts:252-281`), checks that the text traces to the owner's live turn (`proposal.ts:491-497`), and carries restricted-persona taint (`proposal.ts:504-517`).

**Plan:**
- Every search and lookup request is projected by Core before it leaves, with the A2A machinery and the A2A release log for the owner's chat session (`A2AReleaseLog`):
  - **PII scrub** of every string and key (`proposal.ts:252-281`).
  - **Persona taint:** a query is refused when Brain read a sensitive or locked persona anywhere in this conversation, since Brain keeps what it read from one turn to the next. The A2A read-set (`packages/core/src/a2a/provenance.ts:221-235`, `release_log.ts:137-143`) expires after 24 hours (`RELEASE_LOG_TTL_MS`, `release_log.ts:29`), while the conversation itself is kept with no age limit (`packages/core/src/chat/repository.ts:84-96`). So Core also keeps a durable record, `conversation_taint` (conversation id, persona, first read), written in the same transaction as the read's release-log entry, kept until the conversation's messages are deleted, and carried in the archive with the chat history. The search check reads both.
  - **Coverage.** A missing taint record must not read as "clean". Each conversation carries `taint_covered_since`, set when its first message is written on a node that has the record. A conversation with any message older than that mark (one begun before this feature, or restored from an archive without taint data) is uncovered: a search from it always needs a `ucp_search_review` card, unless the person starts a new conversation. Tests: an upgrade after an old read's release-log entry expired; a restore from an archive made before this feature.
  - **Provenance** is recorded, not required: Brain may rephrase. A query is labelled `quoted` when the release log proves it came from the owner's own words (`proposal.ts:491-497`), otherwise `derived`. Neither label blocks it.
  - **What raises a card:** only a query the scrub changed or the taint refused. It is not sent; Brain gets the reason; if the owner wants it sent anyway, Core raises one **`ucp_search_review`** card showing the exact query and every merchant it goes to, and an approval is bound to the hash of the query and the sorted set of merchant origins. A changed query, or an added merchant, needs a new card.
  - `ucp_search_review` is Core-minted like the checkout cards (§3.7): in `CORE_MINTED_PAYLOAD_TYPES`, so Brain can neither create nor decide it (`workflow.ts:1391-1405`); rendered on the phone, the console and the mirror; its ids under the reserved `ucp-` namespace (§3.18).
- `context` carries only what the owner allows in settings: country, region and language by default; postal code only on opt-in; never coordinates.
- `signals` are not sent: a server cannot report a buyer's IP or user agent honestly, and the spec forbids buyer-asserted signals.
- Logs carry merchant origin, operation, version, transport, status and latency, never queries, product text, buyer fields or tokens.
- Tests: a query carrying a phone number, and one built after a restricted-persona read, reach the transport only after an owner-approved card, including a search two turns after the restricted read with no read in between, and one 25 hours later; a paraphrased query with no PII is sent, labelled `derived`; a three-merchant search from a tainted conversation raises one card; Brain cannot create or approve `ucp_search_review`; a changed query or merchant after approval is refused.

### 3.17 Linked accounts (U4)

Following `common/identity-linking/index.md`:
- **Discovery:** RFC 9728 protected-resource metadata → issuer (404 means "the merchant's own origin"; any other failure aborts); RFC 8414 with path insertion, then OIDC on 404 only; the metadata `issuer` must match byte for byte; refuse to link, before any redirect and with the reason shown to the owner, unless `S256`, `authorization_response_iss_parameter_supported` and `none` in `token_endpoint_auth_methods_supported` are all advertised (a public client must use `none`, and a merchant only MAY support it, `identity-linking/index.md:226-229, 976-980`).
- **Flow:** authorization code with PKCE S256, `state`, RFC 9207 `iss` check, only the scopes derived from the merchant's `config.scopes` and the capabilities Dina uses.
- **Pending records** in Core: `state`, PKCE verifier, issuer, exact `redirect_uri`, expiry 10 minutes, consumed once. A callback with an unknown, expired or used `state`, or a wrong `iss`, is discarded.
- **Callbacks by kind of node:**
  - Server with a public domain: `redirect_uri` = `https://<public-origin>/ucp/oauth/callback` on the gateway, which passes `code`, `state` and `iss` to Core. This gives that merchant the server's domain, and through the A2A directory its DID (S7). The person is signing in to that merchant at that moment, so the merchant learns who they are anyway; the cost is stated on the link screen.
  - Server behind NAT, with a paired phone: the authorization URL always opens on the paired phone, sent as a presence-gated mirror card with `link_url` (§3.9); linking started from the console or a laptop browser hands off to the phone with that card. `redirect_uri` = `https://<label>.ucp.dinakernel.com/oauth/callback`, a link claimed by the Dina app (iOS associated domains `*.ucp.dinakernel.com`; Android app links). The OS hands the callback to the app without the request reaching the host. The phone-approval channel runs one way (the server calls the phone, `remote_approval.ts:1-8, 182-193`), so the phone's Core stores the callback as a phone-owned row keyed by `state`, and the server pulls it through a new route under `/v1/agent/approval-sync/v1/oauth-callbacks`, with the same device authentication. A pull does not remove the row: the server records the callback durably against its pending record, then sends an authenticated, idempotent acknowledgement that deletes it. A lost answer or a crash before the acknowledgement means the server simply pulls again; the server's pending record is consumed once, so a callback pulled twice is processed once. While a link is pending, the server's sync tick runs every 5 seconds, well inside the 10-minute expiry. If the app is not installed, the host serves a static page that says so and records nothing.
  - Phone-only node (U4): the same claimed link, handled by the phone's own Core.
- **Tokens** in `ucp_merchant_links` on the A2A credential pattern (`packages/core/src/a2a/credentials.ts`: versioned, revocable refs; one door out). They never reach Brain, and are sent as `Authorization: Bearer` only to the resource server whose issuer minted them, alongside Dina's signature.
- **Challenges:** 401 `identity_required` → offer to link; 403 `insufficient_scope` → ask only for the missing scopes (`index.md:932-936`); `invalid_token` → refresh, then ask to re-link if that fails.
- **One refresh at a time.** Merchants may rotate refresh tokens and revoke a link when an old one is reused (RFC 9700 §4.14.2). So each link has one refresh owner at a time (a lease on its `ucp_merchant_links` row with a token generation); other callers that meet `invalid_token` wait and use the winner's new access token. New tokens replace the old in one transaction that checks the generation. If a refresh's answer is lost, the owner retries once with the same refresh token; an `invalid_grant` then marks the link as needing re-link. Tests: two simultaneous challenges (one refresh), a restart during refresh, a rotated token persisted, unlink during refresh.
- **Unlink.** In one transaction the link moves to `revoking`, which no request, refresh or polling job may use, and in-memory token caches are cleared. Revocation (RFC 7009) is then retried with backoff until the merchant answers. A refresh already in flight when `revoking` began may still answer; its tokens never reactivate the link, but are first written to the revocation queue (a merchant may have rotated the refresh token, so revoking only the old one would leave the new one valid, RFC 6749 §6), and the unlink completes only when every token in the queue has been revoked. Only then, or after 7 days of failure (shown to the owner), are the tokens deleted. Tests: unlink while offline; a refresh racing the unlink whose answer carries a rotated refresh token, which is revoked too; a restart after revoking the old token and before revoking the new one.
- How Dina gets a `client_id`, and the public-client choice, are D6.
- Tests per kind of node: link, a merchant without `none` (refused before redirect), restart mid-flow, callback replay, wrong `state`, wrong `iss`; on a NAT'd server, linking started from the console and finished on the phone; a callback stored while the server is unreachable and pulled when it returns (inside the expiry, and after it); a pull whose answer is lost; a server crash before the acknowledgement; the same callback pulled twice.

### 3.18 Namespaces, migrations, routes

**Plan:**
- Task ids and idempotency keys under `ucp-` are reserved in `createTask` like the A2A namespaces (`workflow.ts:471-480`); UCP checkout steps run on a reserved `ucp:<merchant-hash>` lane, claimable only by Core's own UCP runner.
- Identity migrations start at v64 (the last is v63, `a2a_publication_retry_operation`); re-check before writing.
- Owner routes under `/v1/owner/ucp/*` (merchant settings, linked accounts, profile status); Brain routes under `/v1/ucp/*` with exact-path, Brain-only authz entries (`packages/core/src/auth/authz.ts`), `CoreClient` methods on both transports, and test-harness mocks.

### 3.19 Testing

No official suite tests a buyer. The official `conformance` suite tests merchants; the official `samples` are merchants, but speak only v2026-04-08, which Dina does not (D11), so they are not a test target.

**Plan, as a ladder:**
0. **A recorded schema source for tests.** The published v2026-08-25 schemas, recorded once with their URLs and hashes, are served to the resolver through an injected test fetcher that keeps the real `https://ucp.dev/2026-08-25/...` URLs and every authority and path check, so tests never depend on the live site. The fetcher exists only in test builds. The manual live run (step 3) adds one live fetch from ucp.dev.
1. **Fixtures.** Every JSON example under `docs/specification/**` that carries `ucp` (indented ones inside tabs included, MCP answers unwrapped) and every response scaffold that carries `ucp` are harvested at the pinned commit into `packages/ucp/__tests__/fixtures/`, with their source commit and the spec's example markers recorded, and read by Dina's readers and the official Zod schemas. The request scaffolds are not used: Dina's own request bodies are checked against the SDK's request schemas instead (amended after the U0 review, 2026-10-04).
2. **An in-repo mock merchant** (`packages/test-harness/src/ucp_merchant/`, Fastify, REST and MCP, v2026-08-25, signing its responses and webhooks, expiring idempotency keys at 24 hours, and able to complete a checkout "in the browser" so the watcher has something to find), itself run against the official `conformance` suite.
3. **A live Shopify store** over MCP from the test server node, with its profile hosted: search, lookup, product, cart create/update/cancel, checkout create/update and hand-off on one session (never cancelled), and create then cancel on a second session that is never handed off. Never complete. Run by hand with the owner's go-ahead, since it talks to a real merchant.
4. **Cross-checks:** Dina's RFC 9421 output against the samples' Python signer, used as a library (§3.2); recorded live answers checked against the Zod schemas.

The detailed scenario plan goes into `docs/UCP_TEST_PLAN.md` before each milestone's code, as for A2A.

## 4. Milestones

Sizes are rough, for one engineer who knows the codebase, and exclude review rounds. **Order:** U0 → U6 → U1 → U2 → U3 → U4 → U5 → U7 (D1 puts U6 second; it keeps its number so references stay stable).

### 4.1 U0 — the pure package (~2–3 weeks)

No migrations, no routes, no network.

- `packages/ucp/` (`@dina/ucp`), copying `packages/commerce-protocol`'s scaffolding and dependency-hygiene test: types and validators for v2026-08-25 (profiles, catalogue, cart, checkout with fulfillment and discount, order, messages, errors, MCP envelopes, REST paths); version choice; entry filtering; authority binding with the spec's own table as vectors; capability intersection; RFC 8941 for `UCP-Agent` and `Signature-Input`; RFC 9421 base, sign and verify with injected crypto; `Content-Digest`; the permalink builder; money as `bigint`; units with scale and increment, and the Rec 20 map to Dina's vocabulary (each↔C62, g↔GRM, kg↔KGM, ml↔MLT, l↔LTR; case and pallet refused); the checkout-intent hash and the update check against it (§3.7); the profile publication envelope (§3.5).
- Fixtures harvested as in §3.19 step 1.
- The P-256 derivation at `m/9999'/6'/{generation}'` with a frozen vector.

**Done when:** every fixture parses or is refused for the right reason; signature and envelope vectors pass; the intent check accepts the allowed updates and refuses every other change; the package has no runtime dependency except `@dina/a2a`, itself dependency-free (amended after the U0 review, 2026-10-04: its canonical JSON, base64 and strict JSON are shared, not copied).

### 4.2 U1 — read: search, on the phone and on servers (~6–7 weeks)

- The complete special-use address classification (§3.3) arrives with U6, which uses it; U1 wires it into the A2A and catalogue-feed fetchers too.
- **The phone as a UCP node:** the UCP Core module and its migrations in the mobile bootstrap (`apps/mobile/src/services/bootstrap.ts`); the phone's profile upload and status; the guard worker on the phone; foreground-only discovery and polling.
- The shared policy transport (§3.3), the `@dina/net-policy` and `@dina/net-socket-node` packages, a mobile bundle check; `ucpFetch`.
- The UCP key on every UCP-enabled node (§3.1).
- Profile documents and the publication envelope built by Core, served for every node, public servers included, from the Dina-run host (§3.5): the upload route, the envelope check, the label registry, the wildcard host on test infra, its logging rule.
- The merchant client (§3.6): discovery cache, version choice, filtering, intersection, MCP and REST; the schema resolver of step 4a (fetch, cache, identity, references, limits, composition, annotations); and the interpreting JSON Schema validator in Core's UCP module, first checked to run on Hermes and in the mobile bundle.
- Catalogue search, lookup and get product; handles and the guard queue (§3.11); the search projection (§3.16).
- Brain tool `search_ucp_catalog` and the comparison card with a PeerLens trust line per merchant (organization subject by origin).
- Owner settings: which merchants Dina may use, and the `context` fields allowed.
- The mock merchant (§3.19 step 2); a live read-only run against a Shopify store.

**Done when:** a person on a phone-only Dina, and on a server node (or its paired phone), asks for a product and gets ranked results from a live UCP merchant; no merchant string reaches Brain unguarded; no query leaves without passing the projection; the profile any node sends names nothing about the person; nothing in the profile, its URL or its key links to the person's DID (a public server's IP address and webhook domain still can, as S7 accepts, and its settings screen says so); the classifier refuses every IANA special-purpose range; every request is validated against the composed schema before sending and every answer after arriving; a schema fetch or check failure drops that capability and shows in the merchant status; schema fetches stay within step 4a's limits.

### 4.3 U2 — checkout to hand-off (~5–6 weeks)

- Request signing on every call; `ucp_requests` (§3.10) and `ucp_checkouts` (§3.12) in migration v64+.
- Cart create/update/cancel for browsing; checkout create from the approved intent, update within the permit, cancel only while `open`; full replacement (A13); fulfillment choice; discount codes.
- The two cards (§3.7), their decision handlers at all three roots, phone and console rendering with the spec's display rules; the mirror changes (§3.9).
- The hand-off chain (§3.8).
- If D3's opt-in is accepted: per-merchant "fill in my details", with the exact fields on the start card.
- REST against the mock merchant (checked by the official conformance suite); a live run against a Shopify store over MCP as in §3.19 step 4.

**Done when:** a person goes from "buy this" to the merchant's own payment page with the merchant's real totals in front of them, approving on their phone with presence checked; the merchant received exactly the approved lines; Dina never touched payment and never cancelled a handed-off session.

### 4.4 U3 — after the hand-off, and orders (~3 weeks)

- The hand-off watcher (§3.12), `ucp_orders`, the poll sweeper, the closed rule (§3.14).
- The webhook receiver on the gateway and its checks in Core (§3.13).
- My Orders projection, the `purchase_decision` vault item, interruptions only for failures, cancellations and disputes.

**Done when:** on a phone-only Dina (polling while the app is open, drop-box webhook) and on a NAT'd server with no webhook, after a hand-off a purchase made in the browser at the mock merchant shows up in My Orders within the watcher's schedule, updates by polling, and closes by the rule; on a public server a webhook settles it at once; a mock merchant that refuses Get Order (`unauthorized`) leaves the order in My Orders with the merchant's tracking link and no further polling; every watcher outcome in §3.12 has a test; an archive round trip keeps the order. Whether real merchants share hand-off orders with a buyer platform is unverified until a live purchase is made with the owner's go-ahead; the plan says so in the U3 notes.

### 4.5 U4 — linked accounts (~3–4 weeks)

As §3.17, within whatever D6 decides. **Done when:** a person can link and unlink an account at a merchant that supports it, on a phone-only Dina through its own claimed link, on a public server, and on a NAT'd server through its paired phone, and Dina asks for exactly the scopes it needs.

### 4.6 U5 — the merchant index (~3 weeks)

As §3.15. **Done when:** Brain can find UCP merchants for a need, ranked by trust, from AppView, without anyone's purchases being published, and AppView builds and deploys with its new dependencies.

### 4.7 U6 — the phone's safe-connection module (~3–4 weeks; second, after U0, by D1)

The native policy transport for iOS and Android (§3.4): resolve once, refuse if any answer is a special-use address (using `@dina/net-policy`'s classifier, so U6 also takes the classifier work from U1), connect to the vetted address only, no redirects, byte and time caps, the widened result contract of §3.3 (`bodyBytes`, `signedHeaders`, allowed headers, `sent`), and TLS floors. Installed as the phone's socket for `ucpFetch` and `a2aFetch`. **Done when:** the transport passes the same test suite as the Node socket on both platforms, including the special-use ranges, mixed DNS answers, a refused redirect and a lost answer reported as `sent`; the mobile bundle builds; and A2A's outbound lane can use it on the phone (A2A plan D6). From U1 on, every milestone's done criteria include a phone-only Dina.

### 4.8 U7 — key rotation (~1–2 weeks; shared with A2A)

A persisted generation counter per key purpose (A2A `5'`, UCP `6'`); active and retiring keys listed together; publication order (upload the new profiles listing both keys; once the hourly compare, run at once, confirms the host serves them, wait the served `max-age` of 300 seconds plus a minute, so every merchant that honours the header has refetched; only then sign with the new key; keep the old key listed for 7 days, then remove it); compromise recovery (remove at once, re-publish). **Done when:** a rotation survives a restart; a mock merchant that keeps the old profile for its full served `max-age` and never force-refreshes still verifies every request; and A2A's card rotates through the same mechanism.

## 7. Four Laws check

| Law | Effect |
|---|---|
| Silence First | Search, carts and checkouts happen only when asked. Order events wait in My Orders; only a failure, cancellation or dispute interrupts. |
| Verified Truth | Merchant order comes from PeerLens trust, never from merchant text or placement; merchants with no record are shown as unverified; catalogue prices are never shown as final. |
| Absolute Loyalty | Keys stay in Core. A merchant learns neither the person's DID nor their node from the profile, its URL or its key (D2, S7); only Dina's host operator holds the label-to-DID link, and the host keeps no record of who fetched whose profile. On a public server, the IP address its calls come from, its webhook URL (S8) and its OAuth callback name its domain, which leads to its DID through the A2A directory; Dina accepts this (S7) and the owner's settings say so. Merchant images are not loaded on the person's devices. No personal data leaves without the person seeing the exact fields; search text is checked by Core before it leaves. Merchant strings reach Brain only as guarded text or handles. Talking to merchants directly keeps a platform out of the middle. |
| Never Replace a Human | Unaffected. |
| Cart Handover | Every checkout ends on the merchant's page, opened by a person; Dina never completes and never touches payment. |
