Cross-cutting decisions

Deviation Schema: ALTER-TABLE in new migration versions, not editing the original CREATE TABLE. The spec (Phase 2) says "Greenfield release: no compatibility migration complexity is required beyond normal schema initialization," implying we could just add the column to the original CREATE TABLE. But this codebase treats applied migrations as immutable (see schemas.ts "applied migrations are immutable; this v8 supersedes it"). Editing v1's CREATE TABLE would leave every already-migrated dev DB without the column. So data_scope is added via new migration versions using ALTER TABLE … ADD COLUMN data_scope TEXT NOT NULL DEFAULT 'user', which is correct for both fresh and existing DBs and respects the immutability convention.
Decision Run-id factory is injectable. newGuidedDemoScope() keeps the spec's no-arg signature but delegates id generation to a swappable factory (setGuidedDemoIdFactory) so tests are deterministic. The default produces a url/file-safe hex id; the run id is not a secret, so cryptographic randomness isn't required — uniqueness across a single local demo run is the only requirement.
Decision runInDataScope is synchronous (matches the spec signature). The guided demo sets a persistent scope via setCurrentDataScope for the whole run, so async remember/ask/reminder operations inherit demo scope without wrapping. runInDataScope is a utility for short synchronous critical sections + tests. Singleton runtime scope is sound for V1 because the mobile app is local, single-user, and the demo is exclusive while active (per the spec's own guidance).
Decision Scope is validated at the boundary. setCurrentDataScope and newGuidedDemoScope reject malformed scopes (isValidDataScope). Because scope drives data isolation, a malformed scope is a correctness/security risk, so it fails loud rather than silently isolating to a garbage container.

Decision deleteDataScope is pure data deletion; runtime-state teardown is the orchestrator's job. The spec lists "clear active demo state and set scope to user" under Cleanup. I kept deleteDataScope(scope) as only row deletion (registry-driven, refuses user, idempotent, per-table error isolation) and will have the finish/skip/recover flows (Phase 4) call deleteDataScope → clearActiveDemo → setCurrentDataScope('user') → reset in-memory caches. Rationale: keeps the data API single-responsibility and independently testable, and crash-recovery can delete a leftover scope while the runtime is already on user without the API forcing a redundant scope switch. Tradeoff considered: folding everything into deleteDataScope would match the spec's wording literally but couples data deletion to global runtime mutation, which is harder to reason about and test.
Decision Cleanup is a registry, not a hardcoded table list. Each scoped repository registers a ScopedCleanup {table, order, deleteScope}. deleteDataScope runs them sorted by order (child tables low, parents high) so referential order holds even without FK cascades, and a newly-scoped table can't be silently forgotten by cleanup. Sequential (not parallel) execution is intentional — ordering matters.
