Design decisions worth flagging

Opaque envelope is the only accepted cursor shape — no plaintext fallback. The pre-existing ${ISO}::${uri} plaintext code paths in search.ts and get-attestations.ts were removed in this lift (project is greenfield, no users → no migration concern). A naive plaintext string sent today gets a 400 InvalidRequest because it isn't a valid base64url envelope. Forward-looking benefit: when a future ranking-strategy change requires a CURSOR_VERSION bump, the same rejection path catches v=1 cursors held mid-pagination by then- current clients.
Cursor shape is per-endpoint via a Zod schema. Single encodeCursor<T>(payload) / decodeCursor<T>(raw, schema) pair in util/cursor.ts. service-search passes a {bucket, uri} schema; peerlens endpoints pass {ts, uri}. The envelope v is owned by the helper, not the call site — so a single bump in the helper invalidates every endpoint's cursors at once if we ever need to re-shape the envelope itself (separate from a per-endpoint payload swap, which doesn't need a v-bump as long as the schema rejects the old payload).
Acknowledged hack — InvalidCursorError names itself ZodError. The class subclasses Error with override name = 'ZodError' purely to feed web/server.ts's string-based 400 dispatch (if (err?.name === 'ZodError') {...}). Mirrors the existing Object.assign(new Error(...), { name: 'ZodError' }) spread throughout api/xrpc/* — centralising it into a class is an improvement, but the underlying pattern is still a workaround. Follow-up: introduce a typed error protocol (e.g. instanceof InvalidRequestError) in web/server.ts and migrate all xRPC throws + this class onto it.
Redaction filter on subjectGet hides reviewers entirely from BOTH the roster and the live count. Mirror of the service-search stance — "hidden, not counted-but-masked" prevents the "5 reviewers" header showing above a list of 4. The scoreRow.totalAttestations field would lie post- redaction (it's a scorer materialisation that doesn't filter), which is why subjectGet was already doing its own COUNT(*); that count now carries the same filter as the row projection.
CHECK constraints are added straight, not NOT VALID + VALIDATE. Same stance as the services 0017 migration: pre-launch tables are expected to be clean, so a blocking constraint fail-fast is the desired signal. Drizzle's __drizzle_migrations ledger guards re-runs at the file level, so intra-file idempotency wasn't needed (no DO $$ EXCEPTION wrapper).
Transaction wrapper uses { ...ctx, db: tx } for helpers that take a ctx. addTrustEdge(ctx, params) reads ctx.db internally. Cleanest way to keep its writes inside the parent transaction without changing its signature: shallow-clone ctx with tx-scoped db. Tests use a __role: 'tx' | 'outer' tag on the stub db so per-test assertions can prove "ran through the tx" without depending on the helper's internal structure.
readCachedTrustV1Params stays OUTSIDE the transaction. 60s module-local cache → most calls don't touch the DB at all; treating it as a tx-internal read would force every handler call into the same lock window. A slightly-stale HOT_SUBJECT_THRESHOLD only affects whether the dirty flag flips synchronously vs deferring to the nightly batch — both paths converge to the same score, so reading from a stale snapshot is safe.
Open question — RANKING_VERSION → cursor-version policy. Stance taken: a RANKING_VERSION bump should also bump the shared CURSOR_VERSION. Cursors encode a pagination state implicitly tied to the row ordering — if the ordering changes mid-pagination, the cursor's "next page" claim is wrong. Coupling them keeps the contract honest. The two versions are independent in code (services-side's RANKING_VERSION in service-search.ts; shared CURSOR_VERSION in util/cursor.ts) — a future maintainer needs to remember to bump both. Documented inline in both files.

Scope-drift disclosures + follow-up gaps

Scope drift — get-attestations.ts received the redaction filter too. The handover named only subject-get.ts, search.ts, and network-feed.ts for Item 2 (did_redactions). I added the same LEFT JOIN + IS NULL filter to get-attestations.ts because (a) the cursor lift already touched the file, and (b) leaving one read path emitting redacted-author rows while siblings filter them felt inconsistent with the handover's "no read path consults it today" framing. Surfacing the judgment call here so it's reversible. Roll back: remove the LEFT JOIN + the isNull(didRedactions.did) condition + the didRedactions import.
Other peerlens read paths NOT covered by the redaction filter. get-graph.ts, get-alternatives.ts, get-negative-space.ts, get-profile.ts, resolve.ts all surface DID-linked data and were left untouched (handover didn't name them). If "redacted authors are hidden entirely" is meant to be a uniform property of the read surface, these are gaps worth a follow-up sweep. Each needs its own analysis — e.g., get-profile.ts presumably should 404 on a redacted DID, not "return profile but hide attestations."
Score staleness post-redaction (not introduced by this lift — exposed by it). After a redaction lands, subjectScores.weightedScore still reflects the redacted reviewer's prior contribution. We hide the reviewer from roster + count, but the aggregate score is stale until the scorer recomputes. Three follow-up options: (a) have the moderation CLI markDirty on every subject the redacted DID ever attested to, (b) add a "score is stale" freshness flag on the subjectGet response, (c) accept it as eventually-consistent (current behaviour). Option (a) is probably right but needs a query to enumerate affected subjects.
CHECK constraint gap on subject_scores sibling columns. Added weighted_score ∈ [0, 1] per the handover. Did NOT add equivalents for confidence, authenticity_confidence, or would_recommend_rate — all real columns on the same table and likely also bounded reals. If the principle is "DB-level guards catch direct SQL writes," it should apply uniformly. Trivial follow-up: three more check() calls + three more lines in a new migration (or amend 0018 since it isn't deployed yet — see below).
Out of scope: cosig-list.ts still has a plaintext ${ts}::${id} cursor. Different payload shape (id is a BigInt, not a uri), and the handover scoped this lift to search.ts / network-feed.ts / get-attestations.ts. Worth a separate small follow-up to bring it onto the shared helper with a {ts, id} Zod schema for consistency.
Greenfield framing — 0018 hasn't deployed. Working tree is held for review at the user's request. The migration file + journal entry are committed-style (incremental numbering, mirroring 0000–0017 convention), not collapsed into the initial schema. If the project intends to collapse all pre-launch migrations into a single setup script before first prod deploy, 0018's content lives in db/schema/{attestations,subject-scores}.ts as check() calls already — collapsing it amounts to dropping the .sql file + journal entry and re-generating the initial migration.
