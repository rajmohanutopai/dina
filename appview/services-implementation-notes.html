Design decisions worth flagging

Capability normalization runs at BOTH write and read. Read-side alone would mean re-indexing a misspelled capability after a fix. Write-side alone would mean queries with mixed casing miss. Doing both costs a few CPU cycles per insert/query and makes the invariant easier to reason about. The price of a drift between the two layers is silent zero-match queries, so the symmetry is load-bearing.
Cursor is base64url JSON, not opaque ciphertext. A future signing layer could HMAC the envelope so callers can't craft cursors. For launch the cost (signing key management, error paths) outweighs the value — the cursor doesn't authorize anything, it just points at a pagination position. Bumping v to 2 later if we add HMAC is forward-compat by design.
GDPR redaction = exclude, not anonymize. When a DID is in did_redactions, the LEFT JOIN's IS NULL gate drops the entire row from search results. Considered substituting operatorDid with a sentinel + leaving the service in results, but service identity IS the operator on this surface — anonymising it would mislead callers about who provides what. Dropping is cleaner.
One profile per operator, enforced at the indexer. An operator who publishes two service.profile records (at any rkey) only ever has the most-recent one indexed. The earlier rows still exist on their PDS. Alternative was to allow many profiles per operator (upsert by URI, no operator-wide DELETE) — rejected because the AppView's search assumes one row per operator for capability aggregation, and there's no client today that uses multi-profile-per-operator semantics. Doc + comment make the invariant explicit.
handleDelete is unconditional by URI. After C2's DELETE-then-INSERT, the URI in the index may not match the operator's most-recent publish (if they re-published under a different rkey). A delete event for the stale URI is a no-op (nothing to delete). Documented in the handler — no code change needed, but the behaviour is now explicit instead of accidental.
C5 resolved — flat matched-fields on AppView, lite-client reads camelCase. The previous lite-client parser looked for capability + schema + schema_hash + distance_km + trust_score at the top of each service row, which meant every search returned an empty list. AppView now ALSO emits flat matchedCapability + matchedSchema + matchedSchemaHash + distanceKm fields (the array + record shapes stay for callers that want them); the lite client's parseResponse picks the flat fields and translates camelCase → the snake_case ServiceMatch shape its callers already consume. schema + schema_hash are nullable since an operator can publish a service.profile without a capability schema.
Open question — score formula version policy. Bumping RANKING_VERSION requires re-emitting cursors (because scoreBucket shifts under new weights). Should a version bump also force a cursor-version bump? For now: yes, in lockstep — but the two versions are independent in code, so a future maintainer might not realise.

Items deferred (with rationale)

  • M1 (tsvector FTS): requires a generated column + GIN index + tokenizer choice. ILIKE works at launch scale (<100k rows). When search latency creeps past 50ms p99, swap in.
  • M2 (rate-limit hint on isDiscoverable): the endpoint is currently uncapped at the application layer; the web server's middleware already enforces per-IP / per-DID limits uniformly. A per-endpoint freshness hint can land when callers ask for one.
  • M8 (structured search telemetry): standard pino logging is in place; a dedicated search-query stream needs privacy review (what we log about q matters) before shipping.
