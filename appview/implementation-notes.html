Item 1 — URI normalization in resolver done

What changed: Added normalizeUriForHash() in appview/src/db/queries/subjects.ts and wired it into the Tier 1 URI branch of generateDeterministicId. Added 11 unit tests covering scheme case, host case, default ports (http/https/ftp), non-default port preservation, trailing-slash root folding, trailing-slash non-root preservation, query preservation, path case preservation, malformed-URI fallback, IPv6 brackets, and userinfo.

Trade-off — conservative vs aggressive normalization. RFC 3986 only mandates that scheme + host be case-insensitive and that default ports be optional. Other folding (percent-encoding, trailing slash on paths, query-parameter reordering) is technically legal in some contexts and not others. I picked the conservative superset: only fold what RFC 3986 explicitly considers equivalent, plus the universally-agreed trailing-slash-on-empty-path rule. Aggressive normalization (e.g. reordering query params) would collapse semantically-distinct URLs and is a bigger source of bugs than the fragmentation it would prevent.
Trade-off — verbatim fallback on parse failure. An alternative was to throw on malformed URIs and let the lexicon validator catch them upstream. I picked verbatim fallback because the URL parser is stricter than the lexicon (it'd reject some weird-but-arguably-valid AT-Proto URIs the lexicon accepts). Verbatim hashing keeps the resolver robust: garbage in, deterministic hash out.
Design decision — URL parser as the canonicalization primitive. The Node URL class already implements the RFC 3986 case-folding rules. Re-implementing that by hand would diverge from spec; using the parser keeps us spec-faithful.
Iteration 1 (initial pass): 9 tests added covering scheme, host, default ports, non-default ports, trailing slash (both cases), query, path case, malformed fallback.
Test result: all 53 resolver tests green.
Next: review uncovered: IPv6 + userinfo.
Iteration 2 (review-driven): Added IPv6 host case test (URL parser lowercases hex inside brackets) and userinfo passthrough test (treat distinct userinfo as distinct resources).
Test result: 55 resolver tests green. Full suite: 1583 tests passing.
Deep review:
  1. Absolute-correct way? Yes — using new URL() is spec-aligned (uses WHATWG URL standard which is RFC 3986 compatible for the parts we touch); hand-rolling regex would diverge.
  2. Code smells? None found. URI_DEFAULT_PORTS is a frozen module constant. The function is pure, deterministic, O(URL-length). No allocations on the hot path beyond the URL parse.
  3. Test issues? None. Coverage now spans all RFC-equivalent cases plus negative tests for case/order/percent-encoding to lock in what we DON'T normalize.
Open question: Should we also strip the URL fragment (#section) from the hash input? Fragments are client-side anchors and don't change the resource. Today we preserve them (different fragment → different subject). The conservative choice is to preserve, but if the same article with two different anchors shouldn't fragment into separate subjects, we'd want to strip. Defer; document.

Item 2 — subjects.tombstoned_at + tombstone_reason done

What changed: Two nullable columns + partial b-tree index on tombstoned_at IS NOT NULL. Migration 0012_subjects_tombstone.sql.

Design decision — soft-tombstone vs hard-delete. When an operator removes a subject for ToS / abuse, the row stays so cached URLs and indexed subject_ids still resolve to something. Hard delete would 404 every old reference and corrupt the audit trail. The companion admin_audit_log carries who/when/why.
Trade-off — inline reason vs join. Could have stored the reason only in admin_audit_log and joined on read. I picked an inline column so read paths can render "removed by moderator" with the reason in one round trip, without joining the (larger, append-only) audit log on every request.
Iteration 1: Added schema + migration + partial index. Tests: full suite 1583 still green (schema-only addition; behavior tested via Item 5).
Deep review:
  1. Correct? Yes — distinct from canonical_subject_id (merge), distinct from orphan-GC (hard delete), distinct from attestation revocation (author-initiated). Partial index correct for rare-event column.
  2. Smells? None.
  3. Test issues? Behavior tested in Item 5 once the response field landed.

Item 3 — subjects.resolver_version done

What changed: Nullable text column stamped 'v2' by the resolver's RESOLVER_VERSION constant at INSERT. ON CONFLICT DO UPDATE deliberately does NOT touch this column (the original formula stamp is what we want to query). Test asserts 'v2' appears in the SQL params.

Design decision — stamp at INSERT only. Considered also writing to the column on UPDATE, but the column's purpose is "which formula minted this row". A re-ingest of the same attestation should not flip the stamp.
Iteration 1: Added column + insert clause + test assertion. Tests: inline-enrich tests 6/6 green; full suite 1583 green.
Deep review:
  1. Correct? Yes — stamped once, never overwritten. Nullable so legacy rows degrade cleanly.
  2. Smells? None.
  3. Test issues? The test pins the literal 'v2' — if we bump to v3, the test updates with the formula. Right coupling, not a smell.

Item 4 — subject_scores.score_version done

Item 5 — subjectGet response forward-compat fields done

What changed: Added three optional fields to the SubjectGetResponse interface: cursor: string | null, tombstoned: boolean, scoreVersion: string | null. Wired through all 3 return paths in appview/src/api/xrpc/subject-get.ts (not-found, no-atts, populated). Early short-circuit for tombstoned subjects returns empty reviewer roster + subject metadata + score (for "removed by moderator" rendering).

Design decision — short-circuit on tombstone after subject load but before attestation queries. Avoids the expensive Phase 3 graph + Phase 4 profile fetch when the response will be empty anyway. Subject metadata still flows so clients can render the canonical title in a "removed" state.
Trade-off — cursor on every response vs paginated-only endpoints. The cursor field returns null today on every response, always. An alternative was to only emit it when pagination is active. I picked always-present so clients learn the field is there and don't need to handle "field appears when N > X" later. Wire-format compat over wire-format brevity.
Iteration 1: Added fields, wired all return paths. Tests broke: 10/17 subject_get tests failed because the test stub's subjectRow didn't include tombstonedAt, my !== null check evaluated undefined !== null as true → short-circuit fired → empty reviewers.
Fix: changed to != null (catches both null and undefined).
Tests after fix: 19/19 green (added two new tests: "every return path carries the forward-compat fields" + "tombstoned subject returns empty reviewers + tombstoned: true + metadata preserved").
Deep review:
  1. Correct? Yes — != null is the right defensive check; short-circuit ordering correct.
  2. Smells? None. The tombstone block reuses subject / score / scoreVersion already computed; no duplication.
  3. Test issues? Caught + fixed in iteration. New tests cover both the field presence (all 3 paths) and the tombstone semantic.

Item 6 — attestations.is_takedown_by_moderator + reason done

What changed: Three columns — is_takedown_by_moderator (boolean, default false), takedown_reason (text, nullable), takedown_at (timestamp, nullable). Partial b-tree index on takedown_at with WHERE is_takedown_by_moderator = true. subjectGet reviewer query now AND-filters both isRevoked = false AND isTakedownByModerator = false.

Design decision — distinct from isRevoked. isRevoked is author-initiated (the reviewer retracted). isTakedownByModerator is operator-initiated. Both hide the attestation from reads, but they're semantically distinct for audit + appeal. Without the separation, moderation actions would falsify the author's intent.
Deep review:
  1. Correct? Yes — boolean NOT NULL with default; partial index keyed on the boolean flag.
  2. Smells? None. Filter combinator on read path is the obvious extension of the existing isRevoked exclusion.
  3. Test issues? Stub-based tests don't exercise SQL predicates; integration tests will when the moderator endpoint ships.

Item 7 — admin_audit_log table done

What changed: New table with id (BIGSERIAL PK), actor_did, action, target_id, reason, context_json, performed_at. Four b-tree indexes (target, actor, performed_at, action). Migration 0015_admin_audit_log.sql. Exported from schema index.

Trade-off — action as free text vs Postgres ENUM. ENUM gives type safety but requires a migration every time a new admin action is added. Free text (validated in code) lets new action verbs ship without schema churn. Picked free text + documented enum identifiers (see the schema doc comment) for forward-compat velocity.
Trade-off — JSONB context vs fixed columns per action. Different actions carry different context (a merge has {from, to}, a takedown has {original_text_hash}). Fixed columns would explode and most rows would have most columns NULL. JSONB stays sparse + flexible.
Design decision — append-only. No UPDATE / DELETE from application code. Postgres-level retention policies (e.g. archive rows older than 7 years) are an ops concern, not an application concern.
Deep review:
  1. Correct? Yes — schema sound, indexes match operator query patterns, BIGSERIAL handles append volume.
  2. Smells? None.
  3. Test issues? No tests yet — schema-only addition; admin endpoints + tests land in a follow-up.

Item 8 — did_redactions table done

What changed: New table with did (PK), redacted_at (NOT NULL DEFAULT NOW), reason (nullable), audit_log_id (nullable, links to admin_audit_log). Index on redacted_at. Migration 0016_did_redactions.sql.

  2. Smells? audit_log_id as text is loose. Flagged in open question.
  3. Test issues? Schema-only; tests land with the redaction flow.

Item 9 — Error response shape audit + doc done

What changed: Wrote appview/docs/API_ERRORS.md documenting the wire-format contract: {error: 'PascalName', message: '...'}, the closed set of error names, band-enum stability, reserved names for forward-compat. New unit test tests/unit/api_error_contract.test.ts scans the entire src/ tree for inline error: 'Name' literals and asserts each is in the documented public set. Three tests pass.

Trade-off — filesystem scan vs shared constant. An alternative was to extract the error name set into a shared constant and have every call site import it. I picked the filesystem scan because (a) it catches inline literals anywhere, not just at expected call sites; (b) call sites are sparse + obvious in server.ts + test-inject.ts; (c) the test is a one-shot "did anyone sneak a new name in" guard, not part of the hot path.
Deep review:
  1. Correct? Yes — scan catches additions, regex tight enough to not false-positive on unrelated fields named error.
  2. Smells? Filesystem-reading in a test is unusual but justified (see trade-off).
  3. Test issues? None.

Item 10 — SUBJECT_ID.md federation spec done

What changed: Wrote packages/protocol/docs/features/subject-id.md following the same format as the other feature specs. Documents Tier 1a/1b/1c/2 priority, normalization rules, the v2: version prefix, disambiguation policy, canonical-chain resolution, and concrete examples. Linked from packages/protocol/docs/features/README.md.

Design decision — disambiguation as publisher responsibility. Spec explicitly states that implementations MUST NOT silently fork name-collided subjects. If "Python the language" and "Python the snake" both publish as {type:product, name:Python}, they collide into one subject. Disambiguation via a Tier 1 identifier (DID / URI / namespaced identifier) is the publisher's choice — not the AppView's.

Deep review:

  2. Smells? None.
  3. Test issues? Spec doc only; resolver tests already lock every rule it describes.

Admin CLI — deep-review iteration

Audit of the freshly-shipped CLI surfaced 5 real bugs + 3 design choices. All 8 addressed in-place; full suite now 1644 passing (+20 net from the original CLI ship).

Bug / ChoiceFix
Bug 1: audit + mutation were sequential. Crash between them = audit row without state change. Wrap every state-changing command in db.transaction(). The audit-log INSERT and the target-table UPDATE either both land or both roll back. The recordAdminAction wrapper now accepts either DrizzleDB or a tx executor.
Bug 2: process.exit(0) lived inside parseArgs on the --help branch. Side effect in a pure function; help path untestable. Return a HELP_SENTINEL constant. The dispatcher handles printing + the main wrapper handles exit. Help path now has unit-test coverage.
Bug 3: tombstoneSubject did a SELECT-after-UPDATE (race window with concurrent writers, one extra round trip, inconsistent with the other 3 commands). Use Drizzle's .returning() on all four state-changing commands. Atomic read-back, one round trip, uniform across commands.
Bug 4: !!before.isTakedown was a dead double-bang on a non-nullable boolean. Removed; the column is boolean.notNull() so the value is always boolean.
Bug 5: The "audit BEFORE mutation" test asserted both calls happened, NOT the ordering. A regression that swapped them would have PASSED. Stub now records every event into a shared captured.events timeline. The test asserts indexOf('audit:recorded') < indexOf('tx:update:subjects') — actual happens-before.
Choice 1: --reason required on tombstone + takedown but NOT on untombstone + restore. Asymmetric audit trail. Now required on ALL four state-changing commands. Knowing why a moderation action was REVERSED matters as much as why it was applied (was it a mistake? did the user appeal? did the content change?).
Choice 2: listAuditLog lived in the CLI; reads went direct to the schema while writes went through the wrapper. Inconsistent. Moved to queryAuditLog in the wrapper module. The wrapper is now the single chokepoint for ALL admin_audit_log access — reads and writes. Constants (AUDIT_LOG_DEFAULT_LIMIT, AUDIT_LOG_MAX_LIMIT) co-locate with the query.
Choice 3: --actor accepted any string. Operator typos (did:plc:, plc:abc) would land in the audit log forever. Added requireDidFlag with regex ^did:[a-z]+:[A-Za-z0-9._%-]+$. STRICTER than the production lexicon (which accepts did:plc:) on purpose — admin DIDs are permanent + audit-trail-bearing, so cheap to validate. The env-var fallback (DINA_ADMIN_ACTOR_DID) is validated too.
Live verification (round 2, 14/14 checks against test-appview.dinakernel.com):
  • untombstone without --reason rejected; with reason succeeds
  • restore without --reason rejected; with reason succeeds
  • Malformed actor DIDs rejected: not-a-did, did:plc:, did:, plc:abc
  • Well-formed DIDs accepted (did:plc:abc, did:web:example.com)
  • tx rollback verified: tombstoning a nonexistent subject surfaces an error AND leaves zero rows in admin_audit_log for that target
  • --help renders + documents the new reason policy
  • audit-log query via the wrapper returns expected rows

Post-launch: minimal admin CLI shipped

What changed: Added appview/src/admin/peerlens-moderation-cli.ts — a 470-LOC tsx-invoked CLI matching the existing peerlens-flag-cli.ts / peerlens-enrich-cli.ts sibling pattern. Five commands:

  • subject tombstone <id> --actor <DID> --reason <text>
  • subject untombstone <id> --actor <DID>
  • attestation takedown <at://uri> --actor <DID> --reason <text>
  • attestation restore <at://uri> --actor <DID>
  • audit-log [--actor X] [--target Y] [--action verb] [--limit N]

Every state-changing command routes through recordAdminAction() — the wrapper finally has live callers. The chokepoint enforcement test (admin_audit_log.test.ts) still passes because the CLI goes through the wrapper, not a direct insert.

Design decision — CLI not xRPC. A public admin xRPC needs auth (operator allow-list / bearer / OAuth), per- action permissions, rate limits, audit-aware undo. None designed for launch. SSH + container-exec access IS the auth gate: if you can docker compose exec appview-web, you're an operator. When v0.1 designs xRPC admin properly, it reuses the same wrapper.
Trade-off — audit BEFORE mutation, no transaction. Each command writes the audit log row, then mutates the target table — two separate statements. A crash between them leaves an audit row with no corresponding state change. Acceptable because (a) the wrong direction (state change without audit) would be worse, (b) operators can spot dangling audit entries trivially via audit-log --target X + cross-check, (c) wrapping in a transaction would require lifting the wrapper to accept an explicit tx parameter, which is API churn for a low-frequency edge case. Revisit if we ever see this in practice.
Design decision — env-var fallback for --actor. Operators run many commands in sequence; typing the DID every time invites typos. Fallback: DINA_ADMIN_ACTOR_DID env var. The flag still overrides when set, so the explicit form wins.
Live verification (14/14 checks against test-appview.dinakernel.com):
  • --help renders
  • subject tombstone via CLI → subjectGet reflects tombstoned: true + score hidden
  • audit-log shows the tombstone entry with correct actor + reason
  • subject untombstone via CLI → subjectGet reverts
  • attestation takedown via CLI → drops from roster + reviewCount
  • attestation restore via CLI → returns to roster
  • Missing --reason rejected
  • Non-at:// URI rejected
  • Unknown --action verb rejected
  • audit-log --target filter works (≥2 entries for the test subject)
  • audit-log --action filter works (returns restore_attestation)
