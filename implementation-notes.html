Web Thin Client (in-flight — current goal)

Spec: docs/WEB_THIN_CLIENT_DESIGN.md (rev 3). Make the WEB build of apps/mobile a thin client of the Home Node Lite core-server instead of its own limited in-browser node. Kills the "limited mode / no SQLite" banner, makes the web UI a faithful durable view of a real node, and unblocks agent pairing + /task from the web UI. Zero change to mobile native (all web-gated via .web.ts / Platform.OS==='web').

Resolved decisions (from the design review)
  • D1: per-domain proxy routes on the brain-server (validated + contract-tested), NOT a generic {method,args} passthrough. New capabilities (identity, contacts CRUD) get a typed CoreClient method + core route; existing ones (vault/personas/workflow/…) just get a brain proxy over the existing CoreClient.
  • D2: web is ALWAYS thin-client (gate on Platform.OS==='web'); a missing /api/v1/identity renders a "No Home Node reachable" screen, never onboarding.
  • D3: hide change-passphrase on web (server owns the seed). D4: access gate (session token + CSRF + 127.0.0.1) required for non-dev; DINA_BRAIN_DEV_OPEN=1 is the only unauth path. D6: PeerLens publish = server-side build (submit route + worker/drainer + PDS publisher + status projection), not a proxy. D7: provider keys server-side only.
  • Naming: the browser client is BrowserCoreProxyClient (unsigned, same-origin, talks only to brain-server /api/v1) — NEVER reuse the signed Brain→Core HttpCoreTransport name; the browser must hold no signing key.
Phased plan (tracking)
  • P1 (in progress): GET /api/v1/identity (the vertical-slice template: CoreClient.identity() + core route + brain proxy) → BrowserCoreProxyClient + web boot gating (skip createCoreRouter/in-memory repos) → UnlockGate web bypass + "No Home Node" screen → vault + personas proxies.
  • P2: contacts (contactList/Add/Delete new CoreClient methods) + service-config + workflow/approvals proxies. P3: access gate + provider-key routes/UI. P4: PeerLens publish server-side build. P5: notifications, D2D quarantine, devices, export + tests + docs (web/SECURITY.md) + live dina-nodes cross-Dina pass.

  • 2026-06-17 — P3a: web access gate (D4) DONE + live-verified. New brain-server/src/web_access_gate.ts: the brain mints a per-process crypto-random secret, sets it as an HttpOnly; SameSite=Strict cookie when it serves /web/*, and an onRequest hook requires that cookie on every /api/v1/* request (401 otherwise). Registered first in boot; dependencyStatus.webAccessGate = gated | dev_open.
    • Why a cookie (vs bearer): a browser auto-attaches a same-origin cookie to BOTH fetch AND EventSource, so the SPA + the SSE reminder stream keep working with zero client changes (a bearer header would break EventSource, which can't set headers). SameSite=Strict = built-in CSRF defense on loopback (no sibling same-site origin); HttpOnly = XSS can't read it; no cookie = other local processes get 401. Belt-and-suspenders: BrowserCoreProxyClient sets credentials:'same-origin' explicitly (also the fetch default).
    • Dev/test escape: DINA_BRAIN_DEV_OPEN=1 turns the gate OFF (read from the injectable bootServer(env) arg, not process.env directly, so it's test-injectable + defaults to process.env in prod). Shipped default = gated. The existing non-loopback bind guard stays as defense-in-depth.

Change Passphrase (uncommitted)

Settings → Security → Change passphrase (2026-06-17). The capability existed only as dead code (useSecurity.doChangePassphrase + the changePassphrase crypto primitive) but was never wired to a screen and never persisted. Built the durable path + UI. mobile: new service 10 tests, new screen 5 tests, legacy useSecurity suite still green (39 total); tsc clean.

Decisions / invariants
  • A passphrase only wraps the master seed (Argon2id KEK → AES-256-GCM). Changing it is a re-wrap of the SAME seed, so every persona DEK (HKDF-derived from the seed) is untouched and all vault data keeps decrypting — no content re-encryption, no migration. The 24-word recovery phrase (which encodes the seed, not the passphrase) is unchanged.
  • Durable order (the bug the legacy hook had): load wrapped seed → re-wrap (wrong current passphrase fails the GCM tag here, writes NOTHING) → saveWrappedSeed (the unlock source of truth) → then refresh the auto-unlock cache. Seed-first so the new passphrase is live even if the cache write fails.
  • "Unlock automatically" users get saveAutoPassphrase(new) so silent boot keeps working; manual-mode users get nothing cached. The cache refresh is best-effort (try/caught): a failure can't report the change as failed — worst case the gate falls back to a one-time manual prompt and re-caches.
  • Generic wrong-passphrase surface ("That current passphrase is incorrect.") — no oracle about which step failed, matching the recovery-phrase + unlock gates.
Implementation
  • New durable service apps/mobile/src/services/change_passphrase.ts (changeVaultPassphrase) over the real wrapped_seed_store + startup_preferences — NOT the in-memory useSecurity hook (which is left in place for its tests + reused pure helpers validatePassphrase/getPassphraseStrength, now annotated as legacy).
  • New screen apps/mobile/app/change-passphrase.tsx (current/new/confirm via PassphraseField + strength meter + success state) registered as a drill-down route in _layout.tsx; row added to Settings → SECURITY under "View recovery phrase".
  • Client-side guards (empty current, new≠confirm) short-circuit before the service; the service re-validates + rejects no-op (new == current) before any keychain touch.
Not yet usable in the running web build
  • The Home-Node-Lite web app serves a pre-built bundle (apps/home-node-lite/web/dist, last exported 2026-06-15) — the new row won't appear there until cd apps/mobile && npm run web:export rebuilds it. Instant on the iOS dev-client sim via Metro hot reload.
