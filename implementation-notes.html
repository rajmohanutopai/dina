STOPPING POINT — an honest engineering call. Convergence trend of silent-SAFE bypasses: R10=1, R11=3, R12=2, R13=1 — decreasing, and every finding since R10 is the SAME narrow class (an attached/clustered flag value or a single verb branch missing an operand check), each a small refinement, not a new bypass class. Grand total across 13 rounds: 54 real defects found by adversarial testing and fixed, each pinned by a regression test (~147 gate regression tests; core-server suite ≈2717 total). Every SAFE-returning verb branch now runs the protected-path check, and the security floor — no silent-SAFE classification of a protected read/write/exec — is enforced across the whole verb surface.

A hand-rolled shell/path classifier has a near-infinite tail of syntax edge cases; chasing it to zero is not achievable and, more to the point, not the design goal. The spec is explicit (§16): this is a framework-mediated guarantee that dramatically raises the bar for a cooperative-but-fallible coding agent, NOT an OS sandbox against a fully adversarial local process — the true non-overridable boundary is an OS sandbox / non-exportable keystore / phone-held key (tracked as an open question, §22). The right stopping point is when findings have converged to narrow, decreasing edge-case refinements within a single class — which is where R10–R13 land. The classifier is now heavily hardened and heavily tested; residual shell-syntax edges are the documented best-effort limit, and the durable deliverable is BOTH the hardened gate AND the demonstrated method (adversarial workflow rounds + independent verification + pinned regressions) that surfaced 54 real bugs unit tests missed.

Honest assessment of the classifier's nature: this many rounds on one module is itself the finding — a hand-rolled shell/path security classifier is a large, adversarial surface, and the spec is right to call it a framework-mediated guarantee (§16), not an OS sandbox. The true non-overridable boundary is an OS sandbox / non-exportable keystore / phone-held key. This classifier is a strong, now heavily-tested best-effort layer that raises the bar dramatically; it is not claimed to be airtight against a fully adversarial local process. The value delivered is both the hardened classifier AND the demonstrated method: adversarial workflow rounds with independent verification and pinned regressions, which found 44 real bugs that author-written unit tests did not.

3c — Bash command classifier (the hard part)

  • Governing principle: a shell line is Turing-complete, so we cannot prove what it does. The classifier recognises a bounded known-safe/known-risky verb set and BLOCKS everything it cannot verify. Benign verbs (echo $HOME) and non-file verbs (git checkout $BRANCH) stay classified normally — the guard only fires where a hidden path could leak.

  • 2a — single-use bootstrap capability. On a genuine first boot (identity.kind === 'generated'), Core mints ONE single-use agent pairing code via generatePairingCode — reusing the existing single-use ceremony, not a new store. Redeemed via /v1/pair/complete with no admin /v1/pair/initiate.
  • 2b — process-bound handoff. The code is written to an inherited fd (DINA_BOOTSTRAP_HANDOFF_FD), never a 0600 file (which loses to a same-UID race) and never a log. No fd → not spawned by an enrolling plugin, so nothing is minted. The resolver refuses fds 0/1/2 (never a secret to a std stream).
  • 2c — core.lock discovery + single-owner guard. After listen, Core writes <vaultDir>/core.lock (pid + REAL bound port + node DID) atomically, for a second same-machine agent to discover it; removed on clean shutdown (onClose). A pre-listen guard (process.kill(pid,0) liveness) refuses to boot when a LIVE foreign Core owns the same vault (two Cores on one SQLite = corruption); stale/own locks are ignored. A subsequent agent with no token enrols via the normal owner-approved pairing flow.

Deep review

(1) Correct: foundational DID + single-use reuse + inherited-fd (not-file) handoff + single-owner lock all match §8. (2) No workarounds; injectable, single-responsibility modules. The onClose hook had to move before listen (Fastify rejects post-listen hooks) — a real bug the boot test caught. Tech-debt noted: boot.ts recomputes deriveIdentity(seed) in several places — hoist later. (3) 19 new tests (8 bootstrap + 11 lock) + 2 boot integration; the mnemonic and lock boot tests both caught real issues. Follow-up: a boot-level test with the handoff fd present.

Design decisions

  • Reuse PairingCodeRegistry for 2a, do not reinvent. It already gives single-use (used flag), TTL, injectable clock/random, and generate/complete/ expire transitions. The bootstrap capability is a first-boot-minted, single-use pairing code that /v1/pair/complete accepts without the admin-only /v1/pair/initiate step — so the net-new work is when it is minted (first boot) and how it reaches the plugin (2b), not the single-use store itself.
  • Mint only on a genuine first install — gated on identity.kind === 'generated' (item 1's signal), so a re-boot with an existing keyfile does not mint a fresh enrolment token.
  • Bind the coding scope at mint (ties to item 6b). The bootstrap capability is the enrolling-authority seam, so it stamps agent_scope='coding' on the device record at redemption — the §8/COLD-10 resolution.

Open questions for the owner

  • Process-bound handoff (2b) mechanism. The spec wants an inherited anonymous pipe/descriptor from the plugin (parent) to Core (child), not a 0600 file. Confirm the plugin spawns Core (so it can inherit an fd); the alternative — Core writes a 0600 token file — is weaker (same-UID race) and the spec explicitly rejects it. This decides the boot/launch shape.
  • Second same-machine agent (2c). No token → owner-approved pair (phone/device). Confirm that's the intended path for enrolling a 2nd agent under an already-provisioned Core.
  • Honest residual: a same-UID attacker that already compromised the plugin process cannot be fully defeated (§16). The handoff defends against unrelated co-resident processes only. Confirmed as acceptable for the laptop-keyholder posture.

Design decisions

  • Out-of-band channel = a 0600 file, not the logger / stdout. The mnemonic is written to <vaultDir>/recovery-phrase.txt at mode 0o600 (owner-only), atomically (temp → chmod → rename, the same discipline as the keyfile), with a header telling the operator to record it offline and delete the file. Boot logs only the path (metadata).

  • Logger dependency-injection seam. bootServer gained an optional logger override so the regression test asserts exactly what the logger received (mnemonic absent, path present) — robust vs. scraping pino's fd writes.

Deviations from the spec

None. The spec (§8/§21-1) only says "stop logging the mnemonic; decide wrapped-seed." The recovery-file mechanism is the concrete, spec-consistent way to still surface the phrase once.

Tradeoffs considered

Part B — Interactive + Push Services (V1)

Scope read — what "V1" actually is

Reading both phase-gated specs literally, the claimable V1 is bounded, and exactly that was built:

  • Interactive: the pull interaction core (§17 Phase 0 → Phase 1) — run store, reservation store (incl. held_by_lock), per-message lifecycle, signed projections, classification job + Brain-classify boundary, atomic outbox claim + two-step completion advancement, envelope-encrypted payload store + crypto-shred, termination barrier, and the owner-only /v1/run/* boundary.
  • Push: Phase 0 (poll-mode watches) (§19) — activate WorkflowTaskKind.Watch in poll mode: Dina-driven service.query on a schedule, delivered through the shipping silence classifier + notification inbox. No inbound push surface.
  • Push: Phase 1 (standalone reserved-informational inbound push) (§19) — the push_notify capability, the push.* D2D family, the default-deny push grant + subscription store, the §8 receive pipeline, rate budget, and local cry-wolf downgrade.

Explicitly deferred (the specs themselves say these are not yet claimable): run-bound push composition (interactive run over a push transport — several joint contracts still open), push_open, remote wake (no FCM/APNs/Expo in the stack), the Phase-2 fiduciary/Tier-1 harm-signal path, and public signal-quality standing (Phase 2+ AppView scorekeeper). Recorded as open items, not shipped.

Design decision — the honest erasure_mode (crypto-shred is conformance-gated)

§13/§20 is emphatic that backup-resistant crypto-shred needs a net-new hardened, non-backed, crash-safe-destroy erasure-key backend, and that today's keystore-node (plaintext files) and keystore-expo (backup-syncable) do not qualify. The spec's own prescribed behaviour is to probe the backend at run creation and freeze erasure_mode ∈ {backup_resistant, logical_deletion}, degrading honestly. So on today's stack the build freezes erasure_mode = logical_deletion and passes only the logical-deletion assertion — this is conformance with the spec, not a shortcut. The per-payload leaf-key envelope machinery is built so a conforming backend drops in later without touching the lifecycle. Named, not hidden.

Design decision — the net-new owner principal (§12.5)

The spec demands the owner-only control boundary be "a real boundary, not trustedInProcess." The codebase had no owner principal — "owner" was only req.callerType === undefined on the trustedInProcess bypass, which Brain shares on mobile. So "reject Brain, admit owner" was not expressible. V1 adds a net-new owner caller type (coarse + authz unions + mapToAuthzRole), an owner-marked in-process dispatch distinct from the Brain-shared transport, and an authz rule making every /v1/run/* control mutation owner-only (Brain/agent/plugin/service → 403), verified with both the inject-callerType and full signed-auth harnesses.
