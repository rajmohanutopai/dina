Design decisions

D1 — testID: one wrapper, existing kind-testIDs

Single chat-row wrapper at renderItem (no per-branch edits across 14 render branches). Kind/role/status/entityId derive from displayType + metadata.lifecycle.

D2 — dataSet for data-*, cast localized

RN-Web dataSet → kebab data-*. Not in RN core ViewProps; cast localized to chatRowProps. Native ignores it.

D3 — Card text = per-kind body testIDs

row-primary-text only on plain bubbles; cards use *-card-body-*. Uniforming all cards deferred.

D4 — Judge: opt-in, injection-hardened, floor-gated

DINA_E2E_LIVE_JUDGE=1 data-safety gate; untrusted-evidence rule; strict verdict validation; pass && confidence >= floor; calibration is a hard pre-gate.

D5 — Chat-ready via onboarding autopilot

Build SPA with EXPO_PUBLIC_DINA_DEV_PASSPHRASE → auto-onboard → auto-unlock → Chat. PDS-first (needs test-pds, reachable). Alternative (seed IndexedDB+vault) rejected for P0 (fragile, Playwright-version-dependent). Verified working.

D6 — the guided-demo first-run gate is disabled under autopilot

Autopilot lands on the guided-demo GATE ("See Dina in action / Start demo / Start empty"), not Chat. Clicking "Start empty" reaches Chat, but the gate re-appears on every boot-state flip: its "seen" flag (guided_demo.entry_seen, packages/core/src/scope/guided_demo.ts) lives in a KV store that is ephemeral in the limited-mode web thin-client, so hasSeenGuidedDemoEntry() keeps returning false and the gate blocks a clean Chat (verified: after send, the app reset to the gate with 0 chat rows). Fix: disable the gate when the E2E autopilot passphrase is set (apps/mobile/app/_layout.tsx: enabled &&= EXPO_PUBLIC_DINA_DEV_PASSPHRASE === '') — the same dev/e2e hook the onboarding autopilot already uses; production (passphrase unset) is unchanged. Considered + rejected: seeding the KV via backstage (the browser KV isn't Core-backed in limited mode, so it wouldn't reach it); defensive re-dismiss in the test (racy — the gate flaps with boot state and the send was lost).

Deviations from the spec

X4 — MRS-07 tests the agent vault-access PERIMETER, not the delegation grant flow

The spec's MRS-07 is "agent reads a locked vault → approval card → owner approves → agent reads". Building it surfaced the real architecture: a paired agent is not on the /v1/vault/* allowlist at all — it only reaches /v1/agent/*, /v1/workflow/tasks/*, /v1/session/*. So an agent NEVER reads the vault directly (a genuine safety perimeter — it can't bypass the persona gate); the fuller vault-read GRANT happens when the agent claims a DELEGATION task whose execution requests a vault_read_request, the owner approves, and a scoped grant is issued. MRS-07 faithfully tests the perimeter (real paired agent, real signed RPC, real 403-at-authorization for every persona; owner reads freely). The delegation-grant path needs a runner/execution harness (shared with MRS-06) — tracked as an open item. The persona gate's pure logic is unit-tested in packages/core (persona_wall). Net: the agent-safety BOUNDARY is tested; the multi-step grant ceremony is deferred, not faked.

X3 — MRS-08 owner decision drives the real route, not a UI card tap

The spec's MRS-08 has the human approve/deny an agent's action in-app. In the limited-mode web thin-client the approval inbox does not surface an externally-staged Core task (F4), so the human-TAP can't be driven there yet. MRS-08 instead drives the owner decision through the EXACT route the tap invokes (/v1/workflow/tasks/:id/approve|cancel, owner-decision guarded) and asserts the state machine + that the Activity surface renders. The full card-tap approval is covered by Maestro on the mobile full node. Faithful to the safety behaviour; the UI-tap wiring is the only untested seam, and it's documented, not hidden.

X2 — composer testIDs are chat-input/send-button/index-mode-chip-<mode>, not the doc's composer-*

Spec §5.2 aspirationally listed composer-input/composer-send/composer-mode-<mode>. The real testIDs (already used by the Maestro suite) are chat-input, send-button, index-mode-chip-<ask|remember|services|reviews> (task hidden without a paired agent). The Composer page object uses the real ones; doc §5.2 reconciled. Also: the composer is mode-first — the text input mounts only after a mode chip is tapped, so every message is chip → type → send. And RN-Web's fill() does not reliably fire onChangeText → use pressSequentially.

X1 — debug-dispatch returns the route body directly, not {status, body}

The spec (and the handler's own doc header) say POST /v1/debug/dispatch returns { status, body }. Verified against the live handler (debug_dispatch.ts:123: reply.code(res.status).send(res.body)) it actually sets the outer HTTP status to the wrapped route's status and returns the route body directly. backstage.ts follows the real behavior (status = res.status, body = parsed response). The handler's header comment is stale; not changing product code for a test note, but flagged.

Findings that constrain later items (verified against a live Core)

wireWorkflowPlane is gated on pdsIdentity !== undefined (boot.ts:510). Without DINA_PDS_PROVISION=1, /v1/workflow/tasks (and /v1/service/*) return 503 "workflow service not wired". Impact: MRS-01/02/03 (owner remember/ask create no workflow tasks) are fine without it; but MRS-06/07/08 (agent/approvals) and the backstage pendingApprovals() helper require the playwright Core to boot with PDS provisioning + DINA_BRAIN_URL pointing at the real brain port. Deferred to the P1 agent items; the MRS-01 "no approval card" assertion will lean on the UI (card absence), not pendingApprovals().

F2 — sensitive-persona vault/list returned empty in the standalone probe

Direct vault/store into general then vault/list shows the item; the same into health (sensitive tier) listed empty — even though all personas report isOpen:true. Also, direct-store items land with an empty body field (the store body shape isn't {content}). Not blocking: real seeding is through the UI /remember path (staging → drain), not backstage store. To verify when wiring MRS-01 against the full stack: that a health/finance fact stored via real /remember is listable via listVault; if sensitive personas need explicit unlock for list, the routing assertion will use the audit log or a query instead.

F5 — the scripted PR-tier honesty rule conflicts with the agentic architecture

Spec §4.4 says the every-PR scripted tier must "stub only the LLM synthesis step; keep every deterministic non-LLM subsystem real (… persona routing, the reminder create/no-create decision …)". But in the shipped brain, persona ROUTING and the reminder create/no-create decision are NOT deterministic subsystems — they're produced by the agentic drain (an LLM loop emitting route_to_persona / schedule_reminder tool calls, "method: agentic" in the logs). So a scripted product LLM would necessarily stub the routing + reminder decision too — the exact behaviours the scripted MRS-01/02/03 are supposed to prove REAL. The spec's honesty rule and the agentic implementation are in tension: you can't both script the LLM and keep agentic routing real.

What I did instead (honest + valuable): the AGENT-safety flows (MRS-06/07/08) genuinely touch no product LLM — they're the deterministic gatekeeper + workflow state machine + signed-agent perimeter. So they run as a truly hermetic PR gate (test:e2e:pr, Brain in noLlm mode, NO Gemini, NO judge, direct assertions, 20s) — verified by running with the Gemini keys explicitly unset. That IS "the functional gate the repo lacked" for the safety-critical flows. The LLM-driven MRS-01/02/03 stay on the live+judge nightly tier. Open question: to give MRS-01/02/03 a scripted PR variant that satisfies the honesty rule, the brain would need a deterministic (non-LLM) routing/reminder-decision path to keep "real" while only the final synthesis is scripted — a product change, or the spec's honesty rule should be relaxed to "scripting also fixes routing; the vault write + retrieval-planner target selection stay real". Needs a product call.

F4 — limited-mode web approval inbox doesn't surface externally-staged Core tasks

MRS-08 stages an agent intent via /v1/agent/validate on Core (the real endpoint), which creates a pending_approval workflow task — backstage (owner-bypass) confirms it exists, and the owner approve/deny routes flip its state correctly. BUT the browser's Activity → "Needs action" inbox shows All caught up: the limited-mode-web thin-client's inbox (useApprovalInbox → listWorkflowTasks) does NOT surface that task, even though the inbox client is wired (no config error) and the browser's vault writes DO reach the same Core (MRS-01/13). Root cause not fully pinned — likely the browser's authed workflow read is scoped/planed differently from the owner-bypass backstage read, or the web thin-client runs a separate in-process workflow plane from core-server. Impact: the full human-TAP card approval can't be driven in the web tier yet; it's a real architecture question (can a limited-mode web user even see agent approvals?). Handled: MRS-08 tests the agent-safety ESSENCE faithfully — the risk ladder + the approval state machine via the real routes — and confirms the Activity surface renders; the UI-tap card approval is covered by Maestro on the mobile full node (in-process inbox against the real store). Flagged as an open question for product review.

F4 — RESOLVED (root cause pinned; web-parity build, user-directed)

Root cause (definitive): the web thin-client only wired FOUR subsystems to the server (chat, ask, reminders, capability — each has a brain /api/v1/* endpoint + a *.web.ts transport). Contacts, approvals, Talk-messages, and quarantine were never wired, so their hooks (useApprovalInbox, useContacts, useD2DChat, quarantine) read the EMPTY in-browser store. The whole point of the thin-client is to surface this, so the fix is to replicate the reminders pattern per surface.
