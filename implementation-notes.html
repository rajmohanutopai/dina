Design decisions

  • One canonical form: RFC 8785. Card signatures need JCS (spec §8.4.1); Dina uses the same canonicalize for every A2A digest and signed contract (card pin, result digest, consent hash, Lane 3 envelope and fence, attempted-record digest).
  • Every JSON text from a peer goes through a strict I-JSON parser (parseStrictJson, RFC 7493): duplicate members, __proto__ members, lone surrogates and out-of-range numbers are refused, and depth is capped where canonicalize caps it. JSON.parse reads duplicates last-wins and turns a later copy of a __proto__ key into a prototype change.
  • Card canonical form follows the proto field by field (spec §8.4.1, §5.7): REQUIRED fields are kept at their default and restored when an emitter left them out, null (ProtoJSON "unset") is dropped, unknown members are kept verbatim, and Struct contents are never stripped. The rule table was checked against specification/a2a.proto: capabilities and OAuth2 flows are REQUIRED messages; the implicit and password flows have distinct fields.
  • The card pin covers content and who vouches for it, not signature bytes: sha256 over RFC 8785 of {content, signers}, where signers are the identities of the keys that verified (a verifier may return an RFC 7638 thumbprint; otherwise jku#kid). A publisher that re-signs unchanged content with randomized ECDSA keeps its pin; changed content, a new key, or a lost signature changes it.
  • JWS: ES256 and EdDSA; alg must be one of them; kid required; any crit fails; typ other than JOSE is tolerated and reported as written. A signature that is not exactly 64 bytes is refused before the verifier runs, and a verifier that throws counts as a failed signature. A malformed signatures member makes the card invalid, not unsigned.
  • Required arrays need at least one element (spec §5.7) when a card is validated; canonicalization itself restores a missing one as empty (see open questions).
  • JSON-RPC: no null id, no members beyond the four the spec names, params must be an object. A request with no id member is a notification: neither executed nor answered (JSON-RPC 2.0 §4.1); the HTTP layer answers 204.
  • Version: Major.Minor 1.0 in canonical digits; a patch number is ignored (spec §3.6: negotiation matches Major.Minor), 01.0 and 1.00 are refused, an empty value means 0.3 and is refused, and the request parameter is read when the header is absent.
  • Every gateway→Core ingress route is a POST, so the client's signed body and client_auth always reach Core; the signed query may carry only A2A-Version. Design §4.3 now says so.
  • Skill ids on the card are always rkey-qualified and use the canonical name. A skill id that a capability and its alias would both claim on one listing is ambiguous and left off the card (ambiguousSkillIds; invocation must refuse it the same way).
  • The invocation envelope is strict: exactly one data part; text ignored; raw/url refused; unknown members refused; params carrying __proto__ or nested too deep to hash refused. Every envelope reason is a typed list.
  • Every ingress failure has a class (INGRESS_OUTCOME_CLASS, total by type): envelope failures are protocol errors naming their reason; registry and normalization refusals are the one collapsed REJECTED.
  • schema_hash is optional on A2A (D2D requires it). A caller that ignores the optional extension never saw one; params are validated either way, and a hash that is sent must match.
  • The call contract rides standard fields too: inputModes application/json, a JSON-text examples[] sample, and prose naming the required params. The sampler satisfies only a fixed keyword list and gives up on anything else, so it never emits an example the validator rejects.
  • Sanitation works by code point and removes every invisible or reordering character: C0/C1 controls except tab, LF, CR; every format character (Cf), including the bidi controls, zero-width characters and the tag block that can spell hidden ASCII; the line and paragraph separators; variation selectors; blank fillers. The table is written out (no \p{Cf}, so Hermes and V8 agree) and a test checks it covers every Cf code point the runtime knows. Data nested deeper than the released envelope can be canonicalized, and __proto__ keys, are refused. The same stripper will clean the outgoing text the owner approves (M1a).
  • A pinned result schema validates the single data part's value; the default envelope validates {version, parts}. A schema whose hash equals the default's IS the default, at binding and at ingest.
  • One schema audit, two keyword sets. @dina/protocol exports pinnedSchemaProblems(schema, profile): the plugin-manifest profile is the wire contract and is unchanged; the pinned-runtime profile is exactly what Core's validator enforces (now also pattern and the exclusive bounds), with value-shape checks, boolean subschemas, unsatisfiable pairs, any $ref and the depth cap. A2A refuses a result schema or a listing params schema it flags.
  • The action registry is a pure decision plus a lookup (decideInboundClass / shippedCapabilityFacts), and ACTION_REGISTRY_REVISION digests every fact the decision reads, for snapshots to pin.
  • P-256 derivation follows SLIP-0010 exactly and matches the official nist256p1 vectors. Path indices must be canonical decimal below 2^31 (on every curve), and a key generation must be a safe integer in range.
  • Service-key indices are one table (core 0, brain 1, phoneApproval 2, a2aGateway 3), and a test scans the sources for any deriveServiceKey call that does not name a SERVICE_INDEX member.
  • Lane 3 golden vectors use the RFC 8032 test key. Besides the positive values they freeze 15 envelope and 7 fence refusals with expected reasons, five RFC 8785 cases (non-ASCII, astral, U+2028, keys whose UTF-16 and code-point orders differ, numbers), a card with that text, a signature over non-canonical bytes and a malleated (S + L) signature. The refusals' reasons and the RFC 8785 cases are written by hand. Every positive value (card texts and hashes, signing texts, signatures, record digests) was derived by code that is not Dina's: conformance/derive_independent.py, using the a2a-sdk's own RFC 8785 canonicalizer, hashlib and the cryptography package's Ed25519. The generator checks every value against that derivation and refuses to write a file the code disagrees with. Verification policy: RFC 8032 with canonical encodings.
  • Reserved a2a: lanes (M1a): a generic claim never takes one, an a2a: filter matches exactly, the claim route refuses one from every HTTP caller, and POST /v1/workflow/tasks refuses plugin:* and a2a:*; dina.local stays creatable until the ingress move.
  • A2A state is SQLite-only and shares the workflow repository's connection (M1a). Lane 1's invariants span both stores (a consent card and its staged operation, a permit and its dispatch child, a consumed permit and the move to transmitting), and only one connection can make those one commit. createA2AOutboundRuntime refuses a pair that is not on one connection. Tests use real SQLCipher files.
  • Lane 1 follows the current workflow service. A host installs the store once (installA2ALane1); getA2AOutboundRuntime() pairs it with whichever service is set, so the server's swap from its early service to the full workflow plane during boot carries Lane 1 with it. The runner reads the runtime each tick. A service on another connection is a wiring fault: the getter throws, and core-server calls it once after its final service is in place, so the fault stops boot instead of silently failing every approval.
  • Operation states (outbound): pending_decision → queued → running → quarantined → completed | blocked, ending otherwise in failed, cancelled, refused, expired, stale_authority or outcome_unknown. The column has no CHECK: inbound states arrive in M2, and a CHECK cannot be widened without a rebuild.
  • Timings: consent card 15 minutes (the facade-card and phone-mirror limit), permit 1 hour, dispatch child 2 hours, polling deadline 30 minutes after sending, guard lease 3 minutes (60 seconds until the sixth cold audit, C6-5), held-result notice after 2 minutes.
  • The outgoing message is a text part and/or a data part, cleaned of invisible characters, PII replaced by placeholders numbered across the whole message (one value, one placeholder). Data keys are scrubbed like values, and a number is judged by its decimal text: a phone or card number sent as a JSON number becomes its placeholder string. No original is kept anywhere (D7); a test searches every stored byte of an operation for the originals, and another checks what the runner is handed. Labels are always unverified and may_contain_sensitive, plus placeholders when any were made.
  • The consent payload is exactly A2A-I10's fields; its hash keys the card, the permit, and the dispatch re-check. The snapshot also pins the binding's result schema as it stood at consent, because bindings are updated in place.
  • Minting completes the consent card in the same commit (queued → running → completed), so "approved but not minted" is exactly "card still queued", which is what the sweeper looks for. Drift between proposal and approval ends the operation stale_authority and fails the card.
  • Every report is claim-bound. Completing or failing a task on an a2a: lane needs the claim token (as on plugin lanes), and the operation row and its dispatch child change in one transaction.
  • "Sent" means the TLS handshake finished. The host transport reports sent: false only for failures before that point; such a failure ends the operation failed (remote_unreachable: nothing reached the remote), any later one outcome_unknown. When a name resolves to several vetted addresses, the transport tries the next one only after a connection that never opened. A JSON-RPC error to SendMessage is read by Core from its code and the action class: a code saying the request itself was refused (parse, request, method, params, unsupported operation, content type, extension, version) ends failed/remote_rejected; any other code may follow a side effect, so it ends failed only for read and quote and outcome_unknown for write, booking and agentic (A2A-I8). An unreadable GetTask answer is retried until the deadline. The runner renews its claim before every remote call, and refuses a lease no longer than one call's timeout plus its longest sleep, so a second runner never polls the same task.
  • Registration fetches the live card under the policy, strictly parsed; picks the first JSON-RPC interface speaking 1.0 at a URL the policy accepts (recording its tenant); verifies JWS signatures against keys from jku (fetched under the policy; a key whose use is not sig or whose alg differs is not used; ES256 accepts high S); names a verified key by its RFC 7638 thumbprint. A signature with no jku cannot verify. One live registration per card URL. The card text the owner sees is cleaned and bounded.
  • Credentials: M1a creates only none references, and refuses one for a card that declares security requirements (such an agent waits for M1b). Activation needs at least one live binding on the current pin. A card may carry at most 8 signatures, verification fetches at most 2 distinct jku key sets, a set may hold at most 32 keys, and at most 4 keys are tried under one kid, so a hostile card cannot hold registration up. a2aFetch holds its own deadline, so the runner's lease check does not depend on a host transport keeping to it.
  • The guard (Brain): everything the remote wrote (its name, its skill, its result) is judged together. Blatant instruction patterns block without a model; otherwise the routed LLM (the guard_scan tier, PII-scrubbed egress) judges it as one JSON value between a random marker, with nothing remote outside the fence; an unreadable answer is retried once, then blocks. A model or transport failure posts no verdict: the claim lapses and the result stays held for the next try (an outage holds; it never condemns). Every verdict carries a reason code (instruction_pattern, model_pass, model_block, guard_unparseable) that Core checks against the verdict and records. With no model the worker is not started, results stay held, and Core tells the conversation once that the answer has not been checked yet. A verdict for an operation that stopped waiting closes its job and says nothing.
  • Delivery: one ending, one event. Every way an operation ends (refused, lapsed, stale, cancelled, failed, unknown, released, blocked) appends exactly one A2A event in the same transaction (operation_end.ts), on the dispatch child when there is one, else on the consent card. Brain delivers A2A outcomes from those events only; the workflow's own events on A2A tasks say nothing. Brain quotes only a released result read back from Core and words every other ending itself from Core's state and reason code. On the server, Core's consumer forwards to Brain's /api/v1/chat/a2a-result, idempotent by event id.
  • Only Core moves an A2A dispatch child. No HTTP caller (Brain, an agent, or the owner console) may approve, cancel, fail, complete, heartbeat or report progress on a task on an a2a: lane; the owner cancels through the operation route, which keeps the operation and its child in step. a2a_dispatch joins the Core-minted payload types, and task ids and idempotency keys starting a2a- are Core's alone.
  • The sweeper repairs each operation on its own: one that throws is counted and retried next time; the rest still run. Each runner tick runs the sweep, the held-notice sweep and the purge separately, and a tick never rejects.
  • Retention: an ended operation is deleted, children first, 30 days after it ended, together with its permit, guard job, cancel request, child links, any blocked result held in quarantine (design §9), and its two workflow tasks with their events: the consent card's payload is the approved message. The workflow plane has no retention of its own, so this is the one place workflow rows are deleted (a repository method kept for callers that own a task's whole life). The design leaves the windows open (§13).
  • An ending never commits without its event. The event rides a task that exists; with none, the ending throws and rolls back. The only exception is an operation whose consent card was never written: nobody can be told, so it ends untold.
  • Input that already looks like a placeholder is refused (placeholder_in_input), in text, values and keys: the owner could not tell it from a real placeholder, and the card's counts would be wrong.
  • Proposal bounds: 10 pending cards per agent, 50 in all, and 30 proposals per rolling hour whatever became of them (429), so a looping or compromised Brain cannot raise a fresh card the moment the owner clears one.
  • The paired phone receives a consent card as a facade-style mirror when the full message fits its 4,000-character detail and passes its character rules (one shared module, approval/mirror_text.ts); otherwise the owner decides on the console.
  • Brain's tools (list_a2a_agents, delegate_to_a2a_agent) exist only where the host passes an A2A client (the server). Remote names and descriptions reach the model labelled as data.

Design decisions — M1b (provenance and credentials)

  • The release context lives in the vault read functions. Search, get, list, browse and subject recall take an optional {session_id, audience} (vault/release.ts); a read with one records every item it returns in a2a_disclosures before returning, with the persona's tier and a digest of the released text fields. The server's routes pass release_session down (Brain, or in-process, only — anyone else naming a session gets 403); the phone's direct calls pass it straight in. A read asked to record that cannot is a failed read: taint is never under-counted. The log (A2AReleaseLog) is installed on both boots, beside the other identity repositories.
  • A conversation is the session. An ask from chat releases into chat:<thread>; any other ask into ask:<id>. A thread name Core's session pattern refuses is digested. The conversation rides the ask record, so a resume after an approval pause releases into the same one, and an A2A result returns to the thread it came from (the M1a main-only open question is closed).
  • The owner's words are recorded where chat enters (handleChat, shared by both boots), before any model sees the turn, through POST /v1/a2a/turns. The first record of a turn stands. A failure to record only means the turn's words cannot be proven; chat goes on.
  • Provenance is whole units, proven by Core or refused. Brain's tool may name parts of its message as sources: a WHOLE message the owner sent in this conversation (owner), word for word, which Core checks by digest; or the WHOLE body of a vault item Core released into this conversation (vault), still holding what was released, re-read by Core (a locked persona cannot prove), and written before the conversation began (Core stamps every write; an item written during the conversation could be anything Brain was just shown). Nothing smaller proves, and model-written summaries never do. Two reviews broke every rule that cut sentences out of a unit (abbreviations, ellipses, "a.m.", list numbers, a "!" inside a name, reported speech): a cut can always drop the words that govern the rest, and a whole unit cannot. A quote is at least 12 characters and 3 words, occurs once in the message, sits on word boundaries, overlaps no other; only one or two spaces or new lines may sit between units (a mark could join or change them), and anything else in the message is derived. A quote whose edge falls inside a personal detail is refused, and the card shows each quote cut from the scrubbed message by offset. Any claim that fails refuses the whole proposal, and refusals count toward the hourly cap. The card says exactly what a proof shows ("a message you sent in this conversation, word for word"; "the full text of an item in your health vault, saved before this conversation"). It proves where text came from, not what the owner meant: a sentence split across two sends proves its first half as a whole message, and the owner still reads the whole message. Against compromised Brain code it proves nothing on the server, where Brain records the owner's words and can write vault items (see the deviations).
  • Topic lists are releases too. The intent classifier reads the working-memory ToC (topic names from every open persona) and its matches reach the model, so the memory service logs each persona whose topics it returns into a conversation, under the reserved id #topics: it taints the read set and can never prove a quote. (On the server Brain has no memory service, so its classifier sees no topics at all; that gap predates A2A.)
  • Labels. Text no proven quote covers, and any data part, is derived: unverified and may_contain_sensitive, because Core still cannot see chat history or briefings that reached the model. restricted_source marks a proven quote from a sensitive or locked persona, or derived text in a conversation that read one; the card names those personas. A fully proven message carries neither doubt label. The consent payload records the proven sources (scrubbed with the message's own numbering), so the owner approves them as shown and the hash covers them.
  • Session-bound proposals. A proposal needs a recorded owner turn in its conversation within the last 30 minutes (no_owner_turn otherwise). Asks that did not come from the owner's chat cannot propose.
  • Originals (A2A-I9). A placeholder keeps its original only when every occurrence of the value lies inside proven quotes of ONE source and the value is not in the (never proven) data part. A vault original is sealed under a key derived from the source persona's live DEK for this purpose alone (HKDF, dina:a2a:entities:v1) with the operation and placeholder as associated data, so a copied blob does not open; no DEK, no original. The owner's own words stay in the identity file under its SQLCipher key. Core never writes an original into the remote's text (the remote chose where its placeholders sit — inside a link, say — and the guard judged the text with placeholders): the owner's operation view carries a legend beside the answer, while the persona is open, and the console shows it; Brain's view carries no originals. Originals go 7 days after their operation ends and at 30 days in any case; a deleted persona takes its originals and releases with it first (a new persona of the same name would derive the same DEK), and a failure there stops the delete.
  • Real credentials (§5.3). api_key (the card names the header; only in a header, never a transport-owned one), bearer, and oauth2_client (client-credentials grant at the card's own token URL, scopes chosen from the card's, form-posted with RFC 6749 Basic auth, tokens cached in memory). A credential must match a scheme the pinned card declares. Header-borne secrets are visible ASCII without spaces; client ids and secrets may hold spaces (RFC 6749 VSCHAR). The material sits in a2a_credential_secrets and leaves through one door; views never carry it. Rotation makes a new reference, moves the bindings (bumping their revisions, so an approval under the old one voids at dispatch), revokes the old one and deletes its material; revocation deletes the material, and removing an agent revokes all its credentials and deletes their material. Binding refuses a credential that no longer fits the agent's current card. The runner builds the send's headers (an OAuth token may take a round trip) BEFORE the dispatch transaction consumes the permit; a credential that cannot be used settles the operation failed/credential_unusable with nothing sent. Reads after the send (GetTask, CancelTask) follow the credential through a rotation, so replacing a secret mid-task does not strand the result. The lease check now counts a token fetch. HTTP 401/403 ends a send remote_auth_refused (refused before acting). During polling an OAuth client's 401/403 drops the cached token and polls again, once for each read that went through; a static key or bearer refused while polling ends the operation outcome_unknown, since the same secret would be refused again (cold audit C5-3 put this here; it once said every credential polled again). The card says what the credential allows and that the agent can use all of it (§1.3). The console offers one form per supported scheme, and a replace-secret row.
  • Release log hygiene. A list page records only the items it returns (not its look-ahead), and its offset is capped at 1,000, so both boots log the same rows. The log sweeps expired rows at boot and at most once a minute while it records. Subject recall reads through Core's read function, not the repository below it. A registry built with no conversation offers no A2A tools.
  • Browse on the server was empty. browse_vault and list_personas called the in-process vault, which Brain does not hold on the server; both now read through Core's HTTP surface there, like search and get. Found while threading the release session.

Design decisions — the ingress move (plan §4.2a)

  • One Core module, wired once for both hosts. service/query_ingress.ts (ServiceQueryIngress) does everything after the receive pipeline admits a query: the body check, the listing config, the "can it run at all" check, the schema hash, params, stripping, and the choice of review card, plugin hand-off, reasoning lane or delegation task; and, after the owner approves a card, the same choice for the approved query. @dina/home-node's service runtime registers it as the dispatcher's service.query handler and as the target of approved events, for both hosts, so no host can forget it. Brain's handler already ran inside Core's process on both hosts (core-server built it in-process; the phone is one process). What moved is ownership: Core's code decides, and Core's workflow service creates the tasks directly.
  • Core alone judges an approved card, against the live listing. executeApproved(id) takes only the card's id, reads the card from Core's store, and starts nothing unless it is an approval card with a service payload in queued or running, the only states the owner's approve can produce (approve and its event commit together). It then runs the card only against the listing as it is now: still live, naming no reserved lane, with the same published schema as the card snapshotted, and the card's params valid under it (and stripped again). The lane and tool come from the live listing, never from the card. The event consumer only routes by payload type; it no longer checks the card's state or parses it, so the two can never disagree. Only Core's ingress mints service_query_execution payloads: the create route refuses them to every caller (CORE_CREATED_PAYLOAD_TYPES), while Brain may still answer the cards (/service_approve).
  • Reserved lanes are refused everywhere. service/reserved_lanes.ts names them: dina.local, plugin:*, a2a:*, reasoning:*. A listing whose mcpServer names one cannot be saved (reserved_runner_lane), never runs at admission or after approval (capability_not_executable), and the task builder refuses one as a last check.
  • The workflow-event consumer stays the trigger. It already delivers at least once, backs off, and survives a restart. A Core approvalDecisionHandler runs synchronously after the commit and swallows its errors, so an async step there would need a new sweeper. The consumer runs in Core's process on both hosts, and Core re-checks the card, so the trigger carries no authority.
  • The rules moved with their text. The params validator (service/capabilities/schema.ts, now serviceSchemaError) and the first-party capability registry moved into Core with unchanged behaviour, because their error text reaches the requester. Core's stricter plugin validator stays separate: folding them is a wire change of its own (open question).
  • One schema-hash recipe. Core's capabilitySchemaHash (RFC 8785) is now what every publisher and every check uses: Brain's publisher and requester check, the server's publisher and profile builder, the phone's listing editor and seeds, the demo scripts. Brain's canonicalJSON/computeSchemaHash and core-server's appview/schema_hash.ts are gone. The hash pinned across stacks (2886d1f8…, shared with Python and Go) passes on Core's recipe. A schema with no canonical form is refused at publish as a config error, never hashed.
  • The runtime takes the workflow service as an input, never the global: the phone installs the global at start(), after it builds the runtime.
  • The brain-server has no service runtime. Its optional serviceRuntime was a scaffold only its own test used; D2D reaches Core's relay, never Brain's process. Removed, with its /readyz entry.
  • dina.local is reserved at creation. The create route refuses it, with plugin:* and a2a:*, to every caller; Core's ingress fills it through the workflow service.

Design decisions — M2 (inbound gateway, Lane 2)

  • Core speaks JSON-RPC; the gateway carries bytes. The gateway (apps/home-node-lite/a2a-gateway) keeps the client's body as a string, picks the internal route from it by the shared table, and forwards the raw body and the client's Authorization header to Core, signed with its own key. Core authenticates the client, parses the signed body strictly, checks the route against it (bindSignedDispatch), and writes the JSON-RPC answer the gateway relays. The gateway answers only what needs no authority: parse errors, methods Dina does not serve, oversized bodies, its per-address limit.
  • One table for both sides. The method → route table and the list of methods served today (A2A_SERVED_METHODS: SendMessage, GetTask, ListTasks, CancelTask) moved into @dina/a2a. Core registers exactly one route per served method and no other; the gateway routes by the same table (ingressPathFor).
  • The public card is projected with invocation's own functions. a2a/inbound_card.ts classifies each listing capability with the action registry, the pinned-schema audit and hash, and §7.3's executor selection, then applies M0's projection. Signed ES256 with the D4 key at generation 0; kid is the key's RFC 7638 thumbprint; jku is the gateway's /.well-known/jwks.json, which Core builds beside the card. version is 1.0.0+ and 16 hex of the digest of everything else on the card, so any change to what it says changes it. Name and description come from the self listing when it is live and public, else the first such listing. The public origin comes from Core's own configuration (DINA_A2A_PUBLIC_URL), never from the gateway, so a compromised gateway cannot get Dina's signature on a card that sends clients elsewhere.
  • The effect boundary is the claim, on every path. admitInboundClaim runs in the claim route, the plugin claim guard and the in-process runner: the claimant must be the pinned runner, the authority the call was accepted under must still hold, and an effectful child's permit is consumed by compare-and-swap, which marks the effect started. A refused claim ends the operation with its reason, then fails the child; the claimant gets nothing. A lease that lapses after the permit was consumed ends outcome_unknown, never a second run.
  • A pinned child is its runner's alone. The SQL claim leaves out a child pinned to another device, so other runners neither take it nor stall behind it. Every executor verb on it (heartbeat, progress, complete, fail) needs the pinned runner's DID and the claim token; a device or agent reads it only as its pinned runner, Brain reads no inbound execution child at all, and the owner and admin read it as any task (C6-7). A report under a claim token a lease already moved past is refused.
  • The listing validator's rules hold at call time. A capability the catalog never allows in public (isPublicExposureAllowed) is refused on a public listing (not_public_exposable), as the card leaves it out. The review rules (a write-class action; a subject-scoped read where strangers can reach it) are now one predicate in @dina/protocol (reviewRulesFor) that the validator and Core's ingress both read, so a row the validator never saw cannot lower them.
  • Every read that hands out a result checks again (design §7.3): the client still active, its grant (if any) live, the listing still live on the services surface. Otherwise the caller sees a neutral FAILED and the result stays the owner's.
  • Core writes the owner's card words once. An inbound review card carries display (title and detail) and post_hash. The params appear as JSON text with every invisible, bidi and control character spelled out as \uXXXX, so the owner reads exactly what the runner will get and the text passes the phone mirror's checks. The server console and the phone show those words as they are; a phone decision binds to post_hash. A card too long for the phone stays on the console.
  • Runner bindings have owner routes: GET/POST /v1/owner/a2a/runners and POST /v1/owner/a2a/runners/:lane/unbind.
  • Limits per client, not per gateway. The gateway: 120 calls per minute per client address. Core, per client: 60 new calls, 600 replays and 600 reads or cancels per minute. Every client's call reaches Core under the gateway's one DID from one address, so Core exempts the gateway's routes from its per-address limiter and the gateway's DID from its per-DID bucket (an infinite named ceiling), as design §4.1 says: a shared bucket would let a few busy clients throttle all the rest.
  • Server wiring. DINA_A2A_PUBLIC_URL and DINA_A2A_GATEWAY_DID go together or not at all; config refuses an origin with a path, credentials or plain http off loopback. Boot registers the gateway DID as caller type gateway and installs the card key from the master seed. The Lane 1 runner's tick also runs Lane 2's sweep (approved review cards with no execution, ended children with no settle).
  • Inbound operations purge 30 days after they end, with their children, permits, workflow tasks and idempotency receipts (a receipt would otherwise answer a replay with a task GetTask cannot find).

Design decisions — M2 preconditions (plan §3.18)

  • Brain serves signed callers only. Every Brain request but /healthz and /readyz carries Dina's canonical signature, checked by the same function Core uses (checkRequestSignature, now shared: Core's middleware calls it too). Brain accepts two signers: Core, under its service key (m/9999'/3'/0', which Core already derived and now uses), and the owner's paired devices. Brain learns both from Core (GET /v1/brain/callers, Brain only) over its own signed link: in the background once its copy is 15 seconds old, and when an unknown DID signs (at most once in five seconds); after a failed ask the next waits 1 s, doubling to 15 s. A copy 30 seconds old is never used, even when Core is silent, and open event streams end when their caller leaves the set, so a revoked owner device stops within 30 seconds, streams included (and everyone does while Core is silent). A signer Brain does not know is refused before its signature or nonce is looked at, so strangers cannot fill the replay cache; an unknown route answers 401 too.
  • Core signs all five of its Brain calls (the ask bridge, service search, the Tier 1 runner, the A2A result notice, the service result) through one signed fetch (brain_link.ts). The facades keep a separate option for it, so Brain's signature never goes to AppView.
  • The web app signs with the owner device. brainFetch signs each call over the URL as the browser serialises it; PeerLens reads (Brain's AppView proxy) use the same signed fetch. The event streams moved from EventSource (which cannot send headers) to a signed fetch reader that behaves as EventSource does for Brain's streams, with one departure: a refusal is retried (the wait doubles to a minute) and retried at once when this browser connects as the owner, because a 401 here is usually brief. The page's runtime config moved to its own module so the Brain client can use the owner signer without an import cycle. Brain's CORS admits the four signature headers.
  • Who an ask is for comes from the verified caller. Core's forwarded ask keeps the requester Core authenticated; an owner device's ask is the owner's own, whatever its body says; approve and deny are owner-device acts (Core never sends them).
  • DINA_BRAIN_CALLER_AUTH=off exists for development (the /dev page cannot sign, so it is served only then); config refuses it with release endpoints.
  • Isolation for the gateway is a compose profile (a2a): its own container, user (UID 10003), read-only root and key volume, on a network that only Core shares. The gateway cannot reach Brain or the vault volume. A native install that runs the gateway as Core's user does not meet the precondition; the gateway's README says not to open its port there.

Design decisions — M3 (delivery, streams, push, the extended card)

  • One recorder for every change a client can see. recordInboundChange (a2a/delivery.ts) runs inside the transaction that changed a task: a commit, a new child, a claim, a requeue, a settle. It compares what GetTask would now show (projectInboundTask, split out of inbound.ts into inbound_view.ts so the recorder and the ingress read one projection) with the state the task's last event reported. A difference stamps the status time and writes the events: an artifactUpdate for a result, then a statusUpdate, each once per target (the task's streams and each webhook config). The same change seen twice writes nothing, so the repair sweep may call it too. The stamps that M2 scattered (claim, new child, requeue) now come from this one place.
  • A requeue reaches A2A through a workflow hook, not SQL. M2's workflow repository updated a2a_tasks directly on a requeue. The repository now has one requeue-observer slot (observeRequeues), told inside the move; A2A's hooks supply the observer (onTaskRequeued, an optional third member of WorkflowHooks), and a workflow service installs it when given one. One slot, not a list: the server swaps its early service for the full plane over one repository, and the observer must move with it rather than pile up.
  • A task's creation is no event. Its creator already holds that view (the SendMessage answer, or a stream's opening Task), so the commit that creates a task notes where it starts (noteInboundCreated). A task with no note (one open across the v57 upgrade) has its next change recorded: an extra event is harmless, a lost one is not.
  • Streams open from Core's answer and a cursor. SendStreamingMessage and SubscribeToTask answer the Task a stream opens with, plus x-dina-a2a-event-seq: the last event that Task already reflects (read after the view settles the task, so nothing is sent twice and nothing is missed). The gateway never relays the header. Both doors share SendMessage's idempotency key: a call retried through the other door is the same call.
  • The gateway fans out; Core keeps the truth. The gateway's hub (stream_hub.ts) sends each stream the events after its cursor, each once, in order, and ends it with the task. It keeps each task's recent events for the moment between Core's answer and the stream's registration. Only an event recorded after a streaming call reached Core can fall in that gap, so it keeps events only while such a call is on its way, for at most 30 seconds and 8 MB. Its delivery loop (delivery_pump.ts) claims every due stream event, and no more webhook events than it has free POST slots (webhook_limit on the claim), so a claimed webhook POST starts at once and ends well inside its 30-second lease.
  • Order per target, one webhook event at a time, clients in turn. Stream rows and webhook rows are found by separate queries, so neither backlog can crowd the other out of a claim. A stream row waits while an earlier one of its task is claimed under a live lease; for webhooks only each target's head row counts, so a webhook sees its task's events in order, and heads are taken in turn across clients (each client's oldest, then each one's next), so one client's backlog cannot hold every POST slot.
  • Webhooks use the outbound policy Lane 1 uses. The host transport moved from core-server to @dina/net-node (createA2AHostTransport), and the gateway POSTs through it: resolve once, refuse any blocked answer, pin the vetted address, TLS to the original name, no redirects. A new response: 'status' mode reads only the status and never the body (§6.6: webhook answers are discarded). A config's URL is checked when set with Core's URL rule; the address is checked at each POST.
  • The client's address behind a proxy. DINA_A2A_GATEWAY_TRUST_PROXY is a count of proxies (normally 1, the TLS terminator), never "trust all": with Fastify's true, the leftmost X-Forwarded-For entry, which the client writes, became its address, and the stream and call limits keyed on it. A value that is not a whole number is refused at boot.
  • Webhook outcomes. 2xx is delivered; 408, 429, 5xx and a failure to reach the host are retried after 5 s, 30 s, 2 min, 10 min and 30 min; the sixth failure is final. Any other answer, and a destination the policy refuses, is final at once. Core decides the timing; the gateway only reports.
  • Revalidation: only final losses gate a result. Settle, every read that would hand out a result, and every claim run one egress check (§7.3): the client active, its grant (if the call used one) live, and the listing the call was made to still there. Every loss it can find is final: a revoked client, a revoked or expired grant, a deleted listing, including one made again under its rkey (the call pins the listing's created_at, which an edit keeps and a re-creation changes; a call accepted before the pin compares the listing's creation with its own). The first path that finds a loss ends a completed result for good, kept for the owner, as the neutral end settle would have given (outcome_unknown for an effectful call, else failed), and records it; the next claim suppresses the task's waiting events and names it in closed, so the gateway ends its streams with nothing more sent. No loss is ever undone, so nothing a client is shown later flips back: a result once withdrawn stays withdrawn (a final loss after the result was shown does turn COMPLETED into FAILED on the next read, as §7.3's revalidation at reads asks, grant expiry included). A deleted config's waiting events are suppressed in the same step as the delete, and a row whose config is gone is suppressed at claim.
  • Push configs. At most four per task, with server ids. The token and the credentials must be safe header values (visible ASCII), the scheme an HTTP auth token; a non-empty tenant is refused. Get and List hand the client its own config back as set. Delete is idempotent. Create spends the new-call budget; the reads, the read budget. An invalid inline config refuses the whole SendMessage before anything is stored.
  • The extended card. One projection with an audience: the public skills in the client's scope, and the skills its live grants open on unlisted or known_only listings, each grant re-checked when the card is built. A grant on a public listing adds nothing, as at invocation, where the public rules and the scope decide. Examples on the extended card carry the full envelope (grant_id, schema_hash), and a test sends each one and sees it accepted. The card is signed like the public card. A node with only known_only listings names a grantee's card for a listing the grant opens.
  • Every method is served. With streaming routed, the dispatch table has no empty entry left, so its null case, A2A_SERVED_METHODS and the unsupported_operation branches in the library, Core's binding and the gateway were dead code, and are gone. The card's flags are all true.

Design decisions — M4 step 1 (DID credentials, design §5.1)

  • The owner names the DID; the challenge is the authority. The owner asks Core for a challenge for one client and one DID (POST /v1/owner/a2a/clients/:id/did-challenge, body {did}): random, single use, 15 minutes, and a new one replaces an unused one. A client made with an expected DID gets challenges for that DID only. The answer carries what the client needs: the challenge, the DID, the node DID, the client id and the public binding path. The holder of the DID's key signs didBindingSigningInput (a domain, the node DID, the client id, the DID and the challenge, one per line, so the signature fits no other node, client, DID or challenge) and POSTs {did, challenge, signature} to the gateway's /a2a/v1/did-binding, with no other credential. Since the challenge names the DID, only that key's holder can complete it: a thief with the bearer and the owner's message binds nothing, and a client whose key was removed (below) can be bound again.
  • One commit. Core resolves the DID's keys, checks the signature, then inside one transaction re-checks everything that could have moved while it resolved (the challenge still live and unused, the client still active, no other active client on the DID), spends the challenge, swaps the client's credential to the DID and the key that signed (the bearer is gone), and appends the change to the credential history. The principal is unchanged, so grants and tasks carry over. Of two completions of one challenge, one binds.
  • Which keys count. Ed25519 only (Dina's request signature is Ed25519), of type Multikey or Ed25519VerificationKey2020. A document with an authentication member: the methods it names, by reference or embedded. A document without one: its verification methods. Every did:plc document is of the second kind (PLC carries no relationships; a Dina node's key is #dina_signing, beside a secp256k1 #atproto key, which cannot sign a Dina request). A did:key carries its key; any other method is resolved by the host (design §4.1: Core opens no outbound connection). core-server installs D2D's PLC resolver, so did:plc binds and did:web does not yet. The card's requestSigning states the rule.
  • The key bound is the key checked, and the host re-checks it. Each request is verified against the key that signed the binding: no network on the request path. Every 10 minutes the A2A runner looks bound DIDs other than did:key up again, off the tick, one pass at a time. The lookup (DIDResolver.lookup, new beside D2D's resolve) takes no cache and runs none of D2D's messaging checks, and answers one of four things: a document, deactivated (PLC's tombstone, HTTP 410), not_found (404), unavailable (anything else). A client whose key has left its document (every key removed included), or whose DID is deactivated, stops authenticating at once (its DID binding ends in the history; the owner sees credential: did_key_removed) until the owner binds it again. A 404 for a DID that bound earlier is the directory's fault, since a PLC DID can only end in a tombstone, and like an outage it leaves the client alone; at binding, anything but a document refuses. The update is guarded on the key it read, so a binding that lands during the lookup keeps its new key.
  • Per-request signing. A bound client signs its own request to the gateway with Dina's canonical string (method, external path, query, time, nonce, the raw body's hash) in X-DID, X-Timestamp, X-Nonce, X-Signature. The gateway passes the four values through untouched; Core checks them with the same function its own signed routes use (checkRequestSignature), against the bound key, then binds the operation to the signed body as it does for every call. A bearer and a signature together are refused.
  • Replays: on disk, per DID, kept as long as the signature lives. Spent nonces go into a2a_request_nonces (DID, nonce, expiry), kept until the signature could no longer pass the ±5-minute check: its own time plus 5 minutes, or now plus 5 minutes for a request dated in the past. On disk, a replay fails after a restart too; kept by its own date, a nonce outlives a signer whose clock runs ahead. A nonce must be 16–128 characters of [A-Za-z0-9_-]. A row follows only a proven signature, and the gateway's per-address limit bounds how fast they come; the runner purges expired rows.
  • The card says how. The Dina extension gains requestSigning (headers, canonical string, signature form, which keys count, the binding path), as design §7.6 asks of the extension.
  • A bound client has no bearer to rotate (409 did_bound). A revoked client's DID may be bound to a new client.

Design decisions — M4 step 2 (inbound multi-turn, design §7.7)

  • Asking. The runner holding a round's claim posts POST /v1/workflow/tasks/:id/input-required {claim_id, prompt, input_schema} (paired runners only; the pinned-runner and claim-token guard of every executor verb), or, in process, its capability returns CapabilityInputRequired. In one commit Core parks the child (running → awaiting through a new store transition, parkForInput: lease cleared, deadline 24 h), voids the round's permit if still minted, stores the question on the operation (input_required_json) and records the change. Refused with a reason (400, 403 or 409): a malformed question, another runner, a stale claim token, a settled call, a plugin runner, an effect already started, or the round cap.
  • The question's shape. A prompt (plain text, up to 2,000 characters, no control characters but tab and newline) and a JSON Schema of type: "object", held to the rule a call's params schema meets (no keyword Core's validator would skip), up to 16 KB, stored canonical.
  • What the caller sees. TASK_STATE_INPUT_REQUIRED, with status.message from the agent: the prompt as a text part, then the schema as a data part typed application/schema+json, message id {task}-input-{round}. The view key includes that id, so a second question is its own event even if the stream missed the states between. A continued round reads WORKING, never SUBMITTED again.
  • Answering. SendMessage (or the streaming form) naming the task. In order: the principal owns it (else TaskNotFound, nothing revealed); the receipt on the new message id (a replay returns the task, whatever it is doing; the same id with other bytes is message_id_reused); the task is asking (else -32004 task_not_awaiting_input); the context matches; exactly one part, a data part holding an object, valid against the stored schema; the webhook cap if one is set inline; the principal's new-call budget. Then one commit: the round moves on by compare-and-set, the next round's child is minted with every answer so far, the waiting child is cancelled, the receipt and any webhook are stored, and the change is recorded. A second answer finds the task no longer asking.
  • The next round's payload. service_query_execution gains an optional continuation: {turns: [{prompt, input_schema, input}]}, every question and answer so far, oldest first; the params stay as the call sent them. One codec in @dina/protocol, as for every field of that payload.
  • Permits per round. An effectful round's permit binds to what that round runs: the first round to the snapshot's post-hash; a continued round to the hash of (post-hash, every turn), so a payload changed after minting fails the claim (permit_mismatch). Under review, a later round's permit names the call's original approval: the owner approved the call, and the answers are the caller's own input to it, held to the runner's schema. Minting refuses (rolls back) while any earlier round's permit is live; by construction it never is.
  • The effect boundary, by executor. An external runner crosses it at claim (design §7.3), so an effectful call's runner cannot ask. The in-process runner keeps the boundary at claim for every capability except those its host names in effectAuthorizingCapabilities: capabilities whose own code calls turn.authorizeEffect() right before every effect. For those, the runner calls it once more before a result goes out; a round whose permit is already consumed is then authorized again without a second judgement, since its effect began (cold audit C4-4). The promise is the capability's, so the declaration is per capability, never per runner. Until then the round is pre-effect: it may ask, and a lost lease requeues it (the lease sweep already reads "permit consumed" to choose between requeue and outcome_unknown). A refusal at the boundary ends the call with its reason and nothing acts.
  • Ends. An unanswered question fails its child at the deadline (the expiry sweep); settling reads input_not_received. The caller may cancel while asked (pre-effect). A round past its boundary that tries to ask fails, and the call ends outcome_unknown.
  • Caps. Eight rounds a call (the first and seven answers); 24 hours a question.
  • A question is egress. Like a result, it reaches the caller only while the call's authority holds (§7.3). The view shows it only then; a call that lost its authority while asking is ended (failed, authority_revoked, its waiting round retired) by the first read, claim or sweep that finds it, since no answer could let it run.
  • Which rounds may ask. Core marks a round's payload may_ask when its claim crosses no effect boundary (a non-effectful class). The Python agent offers the ask tool only then, and its ask tool answers a refusal with "finish the task now", so an agent never stops on a refused ask and leaves the lease to lapse.
  • Streams end at the question. A stream (SendStreamingMessage, SubscribeToTask) now ends at an interrupted state (INPUT_REQUIRED, AUTH_REQUIRED) as well as a terminal one, and a stream that opens on a task already asking sends it and ends. The reference SDK (a2a-sdk 1.2.1, EventConsumer.consume_all) ends its streams at INPUT_REQUIRED; the client's answer, streamed, opens the next one. M3 had pinned "terminal only"; nothing reached INPUT_REQUIRED before step 2.
  • The Python runner. dina-agent learns the claim token (next bullet), a dina_task_input_required MCP tool, an ask hint in the prompt of a call from an A2A client, and the answers so far in a continued run's prompt, marked as data from the requester, not instructions.
  • Fixed on the way: the Python runner never sent a claim token. Since M2, Core requires claim_id on every report on an A2A call's child; the agent's client, daemon and MCP task tools sent none, so a real paired runner could claim a Lane 2 call and never report on it. The daemon now takes the token from the claim and sends it on every report; the MCP task tools take it as an argument and the prompt carries it. Also: the client's task read returned Core's {task} envelope, so the daemon's "already reported?" check never saw a status; it now reads the task.

Design decisions — M4 step 3 (the REST binding, A2A v1.0 §11)

  • Built, though the design says "on demand". §12 M4 lists "REST binding on demand"; the plan lists it under M4 "as designed, with REST on v1.0 paths". Built now, so a client that speaks only HTTP+JSON can call Dina too. The card lists it second, after JSON-RPC, in its preference order.
  • Where it lives. Under /a2a/rest on the gateway, at the v1.0 paths with no /v1 prefix, as the reference SDK serves them: POST /message:send, POST /message:stream, GET /tasks, GET /tasks/{id}, POST /tasks/{id}:cancel, GET|POST /tasks/{id}:subscribe (the proto says GET, the prose POST; the SDK serves both), POST|GET /tasks/{id}/pushNotificationConfigs, GET|DELETE /tasks/{id}/pushNotificationConfigs/{configId}, GET /extendedAgentCard.
  • One table, one set of operations, two ways in. @dina/a2a rest_binding.ts matches a method and path to its operation, reads its params from the path, the query and the body, and names the Core route it goes to (the same route a JSON-RPC call reaches). Core binds the REST request it was handed (method, path, query, raw body) to the route the gateway called (bindRestDispatch, beside bindSignedDispatch): the same operation, the same ids. Every operation then runs as it does for JSON-RPC; the answer, built in JSON-RPC form, is rendered for REST in one place (renderRestAnswer): a result is the bare body, typed application/a2a+json; an error is A2A's HTTP status and google.rpc.Status, its details led by A2A's own ErrorInfo (a2a-protocol.org, as the SDK sends it) and keeping Dina's reason after it. Internally a REST call carries a fixed id (REST_REQUEST_ID), which the rendering drops.
  • Strict where the binding leaves room. A query may carry only the operation's own parameters (camelCase, typed: ints, booleans) and A2A-Version, each once; a body is parsed strictly and refused where the operation takes none; an id in a body must be the path's. The SDK ignores unknown query keys; Dina refuses them, as it refuses an unbound query on JSON-RPC, since a DID signature covers the query and nothing signed should go unread.
  • One receipt book. A message sent by REST and the same message by JSON-RPC (the same messageId and params) are one call; the second is a replay.
  • Streams. :stream and :subscribe answer as Server-Sent Events whose data: is the bare StreamResponse, with no JSON-RPC envelope; the rest (the hub, slots, ending at a terminal or interrupted state) is shared with JSON-RPC.
  • The gateway's own answers to a REST client (no route: 404; a wrong method: 405 with Allow; its edge limit: 429; Core out of reach: 503) are google.rpc.Status too.
  • DID clients sign REST requests as they sign JSON-RPC ones: the method, the path, the query, the body's hash.

Design decisions — M5 steps 1–2 (publishing the card to the directory, design §8.2)

  • The publication row. One row (a2a_card_publication, v59), made by code with a fresh random publisher instance (a v4 UUID). An archive carries no A2A table, so a node restored from one has no row: it starts switched off and inactive under a new instance, and writes nothing until the owner activates it. That is the design's "boot-inactive after restore", with nothing to reset.
  • The projection revision, by trigger. Every write that can change the public card bumps card_projection_revision in its own transaction, through SQLite triggers: any listing insert, revision change or delete (runner-binding changes already bump the revision of every listing naming the lane), and any plugin-install change. A trigger covers every writer, present and future, where a call in each writer would miss the next one. The owner's switch bumps it in code. Before the row exists the triggers change nothing.
  • Every step guarded. Core keeps the state and the rules; the publisher drives the steps. An attempt is claimed against the projection revision, the epoch, the instance and the fencing generation; its completion lands only if that attempt still stands. Activation, deactivation and stand-down each move the fencing generation, so an attempt begun before one of them never lands after it.
  • The publisher (core-server/src/appview/a2a_card_publisher.ts, a trusted host process beside the profile publisher, on the same PDS session):
    • Activation: read the fence through the pinned read sequence (head, fence, head again); absent means epoch 0; this node's or another's gives its epoch; one that does not verify refuses, unless the owner asks to re-fence. The new epoch is one above the greatest seen; the fence is written with swapCommit and swapRecord, then the activation is recorded. If another fence lands during the ceremony, the owner gets lost_race; an unrelated write only restarts the read sequence.
    • Each step: the predicate decides; the card is built and hashed; the card is published on a new projection with a new hash, a due refresh, or a missing or failed publication; a projection that leaves the card unchanged records the new revision and writes nothing (a byte-identical put would be no commit). Every write is fence-checked through the read sequence and bound to the head with swapCommit, after the PDS session's DID is checked against the node's.
    • Recovery by evidence: a lost swap or a lost answer reads the record back; only a byte match with the record attempted (the attempted-record digest) counts as published. A lost swap retries after 5 s; other failures after 5 s, 30 s, 2 min, 10 min, then every 30 min.
    • The 14-day refresh bumps only the envelope's freshness epoch: the card bytes stay, the record is a new commit.
    • Key rotation (§8.2 trigger c): the row records the dina_signing key that signed the fence (fence_key_id) and the key and epoch under which the published envelope was signed (published_key_id, published_publisher_epoch). When the current key differs, the next step re-signs the fence (keeping epoch and instance) and, if a card is published, republishes the envelope at once, with the same freshness epoch. A re-activation's new epoch republishes the envelope the same way. A new card key changes the card's bytes, so its hash, so it republishes too.
    • No reads when nothing changed: because the row says what was signed under what, a step with nothing to do touches the repository not at all (it used to read the head and the fence every 30 seconds).
    • The card key in the DID document: AppView verifies a card's JWS against #a2a_card in the publisher's DID document, so no card is published until the document names the P-256 key. ensureA2ACardKey (beside applyDinaPlcUpdate in @dina/home-node) reads the PLC audit log's last operation and, when the key is missing or old, posts a chained update that sets only a2a_card, signed by the rotation key. The publisher asks once per process; a failure waits the retry delay before the next PLC call.
    • Stand-down: a foreign fence (a greater epoch, or the same epoch under another instance) stops the node with an owner notice (another_server_publishing); so does a missing fence while active (fence_missing: the fence is never deleted). Only the owner's activation brings it back, claiming a greater epoch.
    • Deactivation is two-phase: the state's one authority is the fence-bound delete of the card; then the node is inactive. A restart in between resumes it.
  • The durable unpublish intent is evidence. The design's "durable unpublish intent" is built as card_maybe_present: whether the repository may hold a card this node answers for. A publish claim sets it before the write goes out (the write may land though its answer never arrives), and so does every activation (a handoff leaves the previous holder's card under the new fence). Only evidence clears it: a delete that landed, or a read under this node's fence that found no card. While the predicate is false and it is set, the publisher deletes; while it is clear, the node reads nothing.
  • Claims are tied to the state. Core accepts a publish claim only from an active, switched-on node that is neither stood down nor deactivating, and an unpublish only from an active node that is not stood down (deactivating keeps that one authority). The publisher's own order no longer stands alone between a deactivating node and a publish.
  • The owner's switch drops an earlier backoff. Turning the listing on or off is a fresh instruction, so a failure's retry delay no longer holds it back.
  • Multikey in @dina/a2a. The package decodes and encodes the two Multikey forms a node's DID document uses for A2A (Ed25519 z6Mk…, P-256 zDn…) with its own base58btc, since it takes no runtime dependency.
  • The card's bytes. The gateway now serves the card's canonical JSON (RFC 8785), the bytes its signature covers and the bytes the record's card string holds, so the directory copy and the live card can be compared byte for byte. Its P-256 signature is deterministic (RFC 6979), so the bytes change only when the card does.
  • The PDS client gains getLatestCommit and a swapCommit precondition on put and delete.
  • Owner routes: POST /v1/owner/a2a/directory-listing {enabled}, GET /v1/owner/a2a/publisher, POST /v1/owner/a2a/publisher/activate {refence?}, POST /v1/owner/a2a/publisher/deactivate; the last two need the host's publisher (503 without one).

Design decisions — M5 step 3 (the AppView directory, design §8.3)

  • Recording before acknowledging. Every com.dinakernel.a2a.card event goes to a Postgres spool (a2a_event_spool) before the consumer counts it done; the insert retries until it lands, and meanwhile the event stays in flight and holds the shared cursor. The bounded queue takes a card event even when full (it still pauses the socket), so none reaches the capped file spool or the dead-letter path. Recording ignores every flag.
  • One pipeline for live and drained events. A processor in the ingester drains the spool: only the earliest pending event of each repository is eligible (by revision, then arrival), under a 60-second lease, with retries at 5 s, 30 s, 2 min, 10 min, then 30 min. "Live" is a short drain, so equal-revision conflicts behave the same in both arrival orders, live or spooled.
  • Phases. a2a_directory_enabled (off by default) gates processing and serving. Turned on, the directory records the spool's highest row as its watermark and drains (draining); it opens (ready) once nothing at or below the watermark is pending, so a live event arriving meanwhile never holds it shut. Off, or a flag that cannot be read (also recorded as reconciliation_required), closes it at once.
  • Decisions are pure (shared/a2a/directory-decide.ts): older revision, stale; equal with the same operation and event hash, a replay; equal with anything else, a conflict (unavailable, both events as evidence); newer delete, a tombstone row kept so nothing older brings the card back; newer valid, the card; newer invalid, withheld with evidence. Every write is conditioned on the revision read under the row lock. The event hash is sha256 over the operation, the CID and the record (RFC 8785 when the record has a canonical form).
  • The card check (shared/a2a/card-verify.ts): rkey self, exact record members, 128 KB, the card string its own RFC 8785 form, no U+0000, a v1.0 card shape, an ES256 signature that verifies against #a2a_card in the DID document, the Dina extension naming the repository DID, the convenience fields equal to the card's JSON-RPC interface and skills, every skill a known capability allowed in public, and the envelope verified against #dina_signing and bound to this record and these bytes. A DID the PLC directory does not know is an invalid record; a PLC directory that does not answer is no verdict (the event waits).
  • Keys. An identity event marks a card holder for another check; an hourly sweep marks any card unchecked for a day (the fallback for a missed event). A card that no longer verifies is withheld until its publisher republishes. A card an identity event marked is withheld until a check against the new document lands a verdict, since the key that verified it may be gone; a PLC directory that does not answer keeps it withheld, and the check is tried again every five minutes (cold audit C4-7). The daily check withholds nothing: a card it waits on stays served.
  • Gaps. At boot, and before every reconnect, the gap generation moves when events may have been lost: no cursor over a directory holding anything (a card or a spool row), or a resume point older than Jetstream's retention (A2A_JETSTREAM_RETENTION_HOURS, default 24) less a 10-minute margin for the two clocks. The resume point is the later of the cursor and the last time the consumer was proven live: on the 30-second timer the socket is pinged, and a live note (at the pong's time) needs the last ping answered, nothing queued, in flight or failed, and the replay over (the last message near its own time, or a minute of silence with pings answered). A socket that answers nothing for 90 seconds is terminated and reconnected, except while the queue holds it paused (backpressure): a held socket can answer nothing, so the tick then does nothing, and the stall clock restarts once it is released. So a quiet stream moves no cursor yet loses nothing, while a socket that died silently, or is still catching up, earns no note. If the check fails, ingestion does not resume. The consumer keeps one queue for its life and re-points it at each new socket, so events still waiting from an earlier socket keep holding the cursor; a socket re-pointed while the queue is full is held when it opens (ws.pause() does nothing while it connects, so it is never marked paused before then). Each card event is stamped with the generation the consumer held when it came off the socket (carried through the queue), so an event that waited while a gap was declared applies but never proves; an event with no stamp (from the file spool) never proves.
  • Serving. Both methods need ready (otherwise 503 DirectoryUnavailable) and every gate. searchAgents: a skill (an exact id, a capability through the registry's aliases) and text decide the candidates; order is (fresh before stale, trust, text rank, DID), with a cursor carrying the ranking version. getCard returns the card string exactly as published; a missing card is 404 NotFound. The dispatcher gains XrpcError so a handler can send a status it means; any other throw stays a 500 with no reason. Staleness counts from indexed_at by AppView's clock, inclusive at 30 days; indexed_at is when AppView received the event that gave the card, not when it got to it (C6-9).
  • Trust per card is resolve's, through one shared module (db/queries/subject-trust.ts, which resolve now uses too): the DID's subject scores, profile and active flags, and a moderator's tombstone (always avoid); nothing relative to a viewer. COALESCE(overall_trust_score, 0) orders. A test pins that the directory's band equals resolve's for a flagged and for a tombstoned DID.
  • Identity changes during a check. The processor keeps the DIDs it is checking; an identity event for one of them makes the check run again against the new document before anything lands, a first create included.
  • Account status is kept per DID the directory knows (a card or a spool row) in a2a_account_status, latest by Jetstream time; an account event for a DID whose card event is being recorded waits for that record. A card is withheld while the account's latest status, taken after the card's commit, is inactive: a status taken while the directory was off holds when the card is processed, and a reactivation lost in a gap is answered by the next commit (a repository that commits is active). Account events are never dropped from the queue, and a per-DID advisory lock serializes an account event with a card write for the same DID, so each sees the other's commit.
  • The moderator's gate is its own table (a2a_card_takedowns), written only by dina-admin peerlens-moderation a2a-card takedown|restore, with audit verbs takedown_a2a_card and restore_a2a_card. It can precede any card, an owner's republish never lifts it, and lifting it never brings back a card the owner deleted.
  • Payloads are JSON text, not jsonb. jsonb refuses \u0000; since a card event is never dropped, a payload the spool could not store would stall the consumer for everyone. Cards holding U+0000 are refused at the check for the same reason.
  • Housekeeping. Processed spool rows are pruned after 30 days (a replay of one is still judged by the card's revision). Rate-limit tiers: searchAgents 60 a minute, getCard 120.
  • Lexicons for the two records (card, fence) ship in packages/a2a/lexicons/; a test ties them to the constants (keys literal:self, the members, the 128 KB cap) and checks every type against Lexicon's closed list. The two queries return trust scores as JSON numbers, which Lexicon cannot express (it has no float), so they are documented in the design rather than published as lexicons, like AppView's other methods.
  • One statement per answer. Both methods read the open phase and the gap generation in the same statement as the cards, so one answer never mixes two states.
  • Evidence stays. Conflict and newer-invalid evidence name every spool row they rest on; pruning spares those rows while the card stays unavailable.

Design decisions — M5 step 4 (the Brain tool search_a2a_agents, design §8.4)

  • Candidates, never grants. The tool returns each candidate's DID, name, skills, trust score and band, staleness, and the card_url the owner would register (the endpoint's origin plus /.well-known/agent-card.json). Nothing in it is an agent_id, so nothing the model holds can reach delegate_to_a2a_agent; using one means the owner registers it in the console, where §6.1 fetches the live card and asks which skills to allow.
  • Brain refilters on its own registry, as search_provider_services does: never this node's own card; never a card holding a skill the bundled registry does not know or allow in public (AppView should have refused it, and a stale or hostile one might not); never one that does not offer what was asked (the exact id, or any skill of the capability or its alias). It then orders as the contract says, fresh before stale and then trust, whatever order arrived. A skill Dina does not know is never sent to the directory.
  • Where it is offered. Only where Lane 1 runs (the server host), since registering a candidate is Lane 1's; the phone's client need not implement the directory call. Not tied to a conversation's owner turn: it reads public data and proposes nothing.
  • The AppView client gains searchA2AAgents, which parses each result into a clean copy or drops it. An outside agent's words get the rule Core gives the same words: the name passes a2aDisplayText (invisible characters out, whitespace collapsed, 120 code points), and a name of nothing visible drops the result. The endpoint must pass checkOutboundUrl, the rule Core's registration applies (HTTPS, no credentials, no literal IP, no fragment, 2,048 characters); otherwise the owner could never register the candidate. Each skill id is at most 256 characters, the card validator's bound. indexedAt must be an ISO 8601 timestamp with a zone, since Date.parse alone takes "1" and "October 1, 2026". The rest: a DID, trust in 0..1, a known band, a 64-hex card hash.
  • Outage or fault. A closed directory (503) or an unreachable one (no status) tells the model plainly. A 400 or a 500 is a fault and surfaces as a tool failure, never as "unavailable". The tool holds the directory's own limits (A2A_DIRECTORY_QUERY_MAX_LENGTH 200, MAX_ID_LENGTH 256, A2A_DIRECTORY_PAGE_MAX 50, shared with AppView through @dina/a2a), so an over-long query gets a note saying what to change and never reaches AppView.
  • The node's own DID comes from Core. The tool asks Core (a2aSelfDid, GET /v1/a2a/self, Brain only) for the DID this node's card is published under, the DID the directory names. The owner's DID is another identity on a server node (brain-server defaults it to a placeholder), so filtering by it let the node's own card through. A node with no DID yet has published no card, so there is nothing to leave out.
  • Brain now depends on @dina/a2a (the skill-name grammar, the well-known path, the display and URL rules, the directory limits), which Core already bundles on the phone. a2aDisplayText and checkOutboundUrl moved from Core into @dina/a2a, so Core and Brain apply one copy of each.

Design decisions — fixes from the test-plan run (areas A–F)

  • A card is always bounded, and one listing never breaks it. The example sampler is a total function: it never throws on any JSON. It gives no example past a 64-character string, a 16-item array, a depth of 16 (Core refuses listing schemas deeper than 8), or 256 JSON values once written out (otherwise 8 nested arrays of 16 would be 16⁸ values). It also gives none for a malformed bound (a negative or fractional minLength; 'x'.repeat(-1) would throw). A const or enum member is used only when it is of the schema's type. Core then runs each example through the validator invocation uses (CardProjectionInput.acceptsExample), so an example is never a call Core would refuse (an enum member breaking maxLength, say). The skill stays; only its example goes.
  • No try/catch around the sampler. The finding asked for one. Once the sampler is total it could never fire on real input, so it was left out, and the tests prove each bound instead. Review round 2 (W1) found the claim false as first built: the value count spread a whole const array into push(), and 200,000 items overflowed the stack. It now counts one value at a time, and stops as soon as a container alone passes the budget. Tests cover a 200,000-item const array, a 200,000-key const object, and an enum member of that size.
  • One skill's share of a card is bounded (A2A_LIMITS.maxSkillShareBytes, 16 KB). W1 showed that a sampler that never throws is not enough. The skill's contract rides the card, so one listing with a 400 KB schema still pushed the whole card past 128 KB, and the whole card was refused. The bound measures what the skill puts on a card: its skills[] entry (name, description, tags, example) and its contract in the extension, canonical, in the largest form any card gives it (granted, full envelope, with the longest grant id a call may carry). A skill past it is left off with skill_too_large, and the rest of the card stands. A skill that cannot be canonicalized (nesting past 32, a lone surrogate) does not fit either.
  • The card and the call share the bound. Core's invocation asks the same function (skillShareFits) of the same capability, built by the same Core function (projectionCapability). It does so after normalization, so the earlier refusals keep their reasons. A skill no card shows cannot be called. The reason is declared once (INBOUND_CARD_FAILURES), and the outcome map rejects it.
  • Examples are short. An example repeats what the schema already says (a long const comes back whole). It is optional, so one over 2 KB (SAMPLE_MAX_EXAMPLE_BYTES) is left off and the skill stays. Review round 3 (W2) caught the first bound for leaving the example out: five skills inside it could fill a card.
  • The card's own name and description are bounded as a remote's words are (a2aDisplayText: 120 code points for the name, 1,000 for the description, invisible characters out, whitespace collapsed). They come from one listing, and the listing validator bounds neither field. Without this, a 140 KB description refused the whole card (review round 4, W3). A name of nothing visible gives the card "A Dina node". Bounding at the card keeps the change inside A2A; tightening the listing validator would also change D2D and the owner's other screens.
  • A suspended client's events wait (gap workflow, D-F1). A DID client whose key the re-check found gone from its document cannot authenticate until the owner binds it again (notes, M4 step 1). Its open streams and webhooks used to keep receiving results. Now a delivery claim that meets such a task closes its streams and holds its waiting events: they leave the due set, in order, for SUSPENDED_HOLD_MS (60 s) at a time. The hold is not the final loss in inboundEgressLoss, since it can end: binding again releases what waited, in order, and revoking makes it the loss, so the events are suppressed. A task that waits sends nothing; the owner has the client page to see why. Rejected: suppressing at once, which would throw away results the client gets back the moment it is bound again.
  • Dot-segment task ids are refused before any forward (gap workflow, D-F2). A task id of . or .. turned the gateway's forward into another Core path once its HTTP client folded the segment. Escaping does not help: WHATWG URL folds %2e as well. No task has such an id, so ingressPathFor refuses it (id_unroutable, which the gateway answers as TaskNotFound, -32001), and the REST matcher treats it as no route (404). The REST Allow list is now derived from the matcher itself, so a path whose id no route accepts is a 404, never a 405.
  • Dina calling Dina: the envelope's skill (gap workflow, B-X1). Lane 1's PII scrub read eta_query@bus as a UPI address and sent [UPI_1], so Dina could not call another Dina's skill by the id its card gives it. An unlisted skill, callable only as capability@rkey, could not be called at all. The data part's own top-level skill, when it equals the bound skill id, is now left as the card writes it. It is the remote's word and holds nothing of the owner's. Everything else is scrubbed as before, the same id deeper in the data included. The review also found a second point. For a remote whose pinned card declares Dina's extension, the envelope's skill is what the remote will run, so it must be the bound skill exactly (envelope_skill_not_bound). Otherwise a message could reach a skill the owner never allowed. A remote that does not speak Dina reads data as free-form, and nothing is checked there.
  • PeerLens evidence in the owner's review (gap workflow, B-X6; design §6.1, §8.4). The review showed no PeerLens evidence, and Brain's tool told the model it did. Now the trusted host reads it (installA2ADirectoryEvidence over AppViewClient.getA2ACard); it is never relayed by Brain. A Dina agent's live card names its node's DID, and the directory holds a card for that DID that AppView verified against the DID's own keys. That evidence is the agent's only when the directory's card names the same endpoint as the live card. An agent naming a DID it does not hold gets "not this agent's evidence", never the DID's trust. The owner route GET /v1/owner/a2a/remote-agents/:id/evidence answers listed, other_endpoint, not_listed, not_dina or unavailable. The console shows one line under the signature. Nothing is stored, and evidence changes no status or binding. Rejected: having Brain pass the candidate's numbers into registration, since Brain is an untrusted tenant. Rejected: storing evidence at registration, since it goes stale and the owner looks later.
  • Brain moves no inbound child (gap workflow, C-F1, high). An in-process (dina.local) child has no pinned runner, so the pinned-runner guard let Brain complete one with a result of its choosing. Core's own runner claims and reports those children; it asks Brain only for the answer. So Brain is now refused (403) on every executor verb (complete, fail, heartbeat, progress, input-required) for any inbound child, pinned or not.
  • Brain never reads an outside client's words on a review card (C-F4). The workflow read routes redact an a2a_inbound_review payload for Brain, as they already did for a price card. Params and display (which quotes them) are dropped and the payload is marked redacted: 'owner_only'. What Dina wrote stays: the skill, the owner's name for the client, the listing. The owner's surfaces read it whole.
  • What a credential set up ends with it (C-F3, revised by the dual review's CX-2 in rounds 1 and 2; design §10, "stolen bearer: rotation"). Rotating a bearer left a thief's webhook receiving results, and any stream the thief had open. Now, whenever a client's credential ends (bearer rotation, a DID bind that replaces it, a DID suspension, revocation), the push configs on its tasks are deleted, and the client's credential generation rises (a2a_clients.credential_gen, migration v60). The gateway holds the streams and Core cannot list them, so the generation travels with them:
    • Core answers each stream's opening Task with the generation the call was authenticated under and an opaque key for its client (a digest of the principal: A2A_CREDENTIAL_GEN_HEADER, A2A_STREAM_CLIENT_HEADER, neither relayed).
    • Every claimed stream event carries the client's current generation, and a stream older than that ends instead of getting it.
    • For A2A_STREAM_FENCE_HOLD_MS (5 minutes) after a credential ends, every delivery claim carries the client's fence (a2a_clients.streams_fence_until; {client, before_gen}). The gateway replaces its fences with each claim's, ends the client's older streams on every task at once, and refuses an older stream that registers later, before it is sent anything, buffered events included.
    • The gateway checks a streaming answer's client and generation against the fences before it writes a byte of it (round 3). A fenced client gets the 401 Core gives (A2A_BEARER_CHALLENGE), with nothing of the task: not the opening frame, not a finished task's result, not a question. A Task answer from Core that does not say whose credential it was answered under is not relayed (503).
    A stream the client opened under its new credential is at the new generation, so it stays. This also changes the hold above: a suspended DID's webhook ends at suspension, and only the stream's events wait for the rebind.
  • The fence is per client and repeated while it holds (CX-2, round 2). Round 1 fenced tasks, once. A stream whose opening answer was still on its way registered after the fence and replayed the gateway's buffer, and a task whose events had all reached the buffer was never fenced at all. A fence on the client covers every task, including ones Core has no row waiting for. Because it is generation-bounded, repeating it is harmless: a stream the client opened under its new credential is not behind it. So Core sends it in every claim for five minutes, longer than any streaming call takes to reach the gateway, and a claim answer lost on its way loses nothing. Rejected: acknowledged closes (a third report in the delivery contract, and a repeated close ended the new stream too); a per-task fence kept by the gateway (it never learns about tasks with nothing waiting). DeliveryItem is a union, so a stream item always has its generation and a webhook item always has its webhook.
  • A SendMessage waits for its task (CX-3, rounds 1 and 2; A2A returnImmediately, false by default: "the operation MUST wait until the task reaches a terminal ... or interrupted ... state"). The route serves awaitSendMessage. The call is committed as before. Then the wait holds no transaction and ends at COMPLETED, FAILED, CANCELED, REJECTED, INPUT_REQUIRED or AUTH_REQUIRED (the set a stream ends at). It reads the task each time recordInboundChange, the one writer of a task's events, signals a change (InboundChangeSignal, one per store), and every second whatever is signalled. The answer is the view GetTask would give at that moment, its settle and egress checks included. returnImmediately: true answers once the task is made, as before; a value that is not a boolean is refused (return_immediately_malformed). A stream never waits. Both bindings reach it, and so does a continuation and a replay of the same message.
  • Two things end the wait early, and neither touches the task.
    • The bound passes with the task unfinished (round 2). An unfinished task is not an answer A2A allows here, so the call fails with internalError, reason wait_deadline_exceeded, and the task's id in ErrorInfo.metadata (over REST, 500 INTERNAL). The client reads the rest by GetTask, a stream or its webhook, or sends the same message again (a receipt replay) and waits again. Rejected: answering 200 with the unfinished task, which round 1 did; the reviewer showed it hands blocking clients unfinished work as the final answer.
    • The credential the call was authenticated with ends (CX-7, round 2). The call keeps the generation it was admitted under, and a wake that finds another answers 401: a stolen bearer's waiting call does not outlive its rotation. The task goes on, and the client reads it under its new credential.
  • A result Dina cannot use after an effect began ends "unknown", both ways (cold audit CO-1 and CK-1; A2A-I8). Inbound: a result that breaks its schema, cannot be read, or is pinned to a schema Core cannot enforce ends the call FAILED when nothing could have happened, and OUTCOME_UNKNOWN once the effect began (a booking made, its answer malformed). Outbound: a remote that reported its task done, whose answer Dina refuses (a url part, too large, a schema mismatch, an unreadable pinned schema), ends a read or quote FAILED and any other class, or one whose snapshot cannot be read, OUTCOME_UNKNOWN, its dispatch child too. Brain tells the owner the agent reported it done and it may have been carried out, so check before asking again. Both now follow the rule the send-error branch and the plugin completion path already kept.
  • A bearer that runs out is a credential that ended (cold audit CK-2; §5.1, §10). It was refused at its next request, but what it set up went on: its webhooks posted, its streams received, and a call waiting under it got the answer. endExpiredBearers ends it as a rotation does (webhooks deleted, generation raised, the client fenced), once: the active bearer binding row is marked (revoked_at), so a later look finds nothing to do, and the auth reason stays expired. Every delivery claim runs it before handing anything out, and a waiting SendMessage runs it for its client at each wake, so the wait ends 401.
  • Both schemas of a pair are audited, and the params that run satisfy theirs (cold audit CK-3, CK-4; §7.2 step 9, §7.3). Admission refused a params schema with a keyword Core's validator skips, but not a result schema; the validator then skipped, say, not at settlement and released what it forbade. Now a pair with such a keyword in either schema is schema_unenforceable: the skill is left off the card (the projection's field is now schemasEnforceable) and a call is refused; a call pinned to one anyway never releases its result. And params are checked again after undeclared members are dropped: a required member the schema never declares was dropped after the check passed, so the executor got a payload its own schema refuses; that call is now refused as params_invalid.
  • The Tier 1 adapter takes Core's signed Brain fetch, with no unsigned default (cold audit CO-2). Its header said the call was unsigned, and it fell back to the bare global fetch, which Brain refuses. Boot always passed the signed one; the option is now required and the header says what happens.
  • ListTasks reconciles before it counts, orders and pages (round 5, CX-9; A2A §3.1.4). Building a task's view can settle a round that ended, or end a result whose authority lapsed (a listing gone, a grant expired), and either moves the task's status time to now. ListTasks built views after ordering, so a list could come back out of order, and a task moved past the cursor could be lost between pages. It now brings the principal's tasks to the state their views would give first (open tasks settled or ended; completed ones checked once per distinct authority they were accepted under, through one grouped query on the snapshot, A2AStore.completedInboundAuthorities), then counts, orders and pages, and builds every view, all as of one reading of the clock (round 6): a grant that expires a millisecond into the request is the next list's to see, so no view finds more to change than the reconcile did. Rejected: re-running the query until no row changed (a task changed on a later page still slipped past the cursor); a check per completed task (a client's old results would make every list slower).
  • statusTimestampAfter is inclusive (round 5, CX-10): "greater than or equal to this value" (a2a.proto v1.0.1). It was exclusive, so a client polling from the last time it saw missed tasks changed at that same time.
  • A Dina envelope's skill is checked as it goes out (second cold audit, CK-5). The bound-skill check read the raw data, but cleaning removes invisible characters from keys too, so Brain could send sk​ill naming another skill: not skill when checked, skill once cleaned, and the remote would run a skill the owner never bound. The raw check stays (the value must be the bound id exactly), and the cleaned envelope is checked again before anything is stored: a key that becomes skill only by cleaning is refused, whatever it names, since only a member written skill is the envelope's own.
  • Every round of an inbound call names its listing (CX-1, high). The execution child carried no service_uri, and both Tier 1 runners (the server's adapter and Brain's runtime) take the default listing (self) when none is named, as a D2D query that names none means. So a call accepted for listing night could run with self's instruction and vault pin. Every non-plugin child now carries at://<node DID>/com.dinakernel.service.profile/<rkey>, on its first round, after review and on every continuation; with no node DID no round runs (no_executor). Both runners now fail a run that names a listing they cannot read, instead of falling back. (A plugin child already carried its rkey.)
  • The card publisher runs whenever the node has a PDS (CX-4; design §8.2: "predicate-false always drives an unpublish", gateway disable among the cases). It was started only with a card configuration, so a node restarted with its gateway removed never took down the card it had published. It now starts whenever there is a PDS and an A2A store. With nothing published, a step reads Core's row and stops. It becomes the owner's port (activate, deactivate) only while a gateway is configured, so those ceremonies still answer 503 without one. The card goes, the fence stays, and the publication stays active: a gateway configured again puts the card back.
  • The gateway closes with streams open (C-F2). The server waits for every open connection before its onClose hooks run, and a stream never goes idle, so close() hung. The pump stops and the streams end in a preClose hook.
  • No row id in the ListTasks cursor (C-F5). The cursor is base64url(JSON [status_updated_at, external_id]), the order follows it, and an old time:row cursor is refused. A node-wide row counter had told a client how much else the node does.
  • receiptId on task results (C-F6; design §7.6). A settled task's Dina extension metadata carries receiptId: the sha256 of the client's own canonical params, which the client can compute. It shows Dina took exactly that request, and is never a row id. Refusals carry it too; it depends only on the request, so refusals still look alike apart from it.
  • A tenant is refused alike on every method (C-F7; plan D5). Dina serves no tenants. Push configs refused a named tenant while every other method ignored it, so now the shared admission step refuses a non-empty params.tenant (tenant_unsupported). An empty tenant is no tenant.
  • An answer is a read (test fix-up, D-F105). An answer to a call whose grant was revoked, or whose listing was deleted, was told WORKING, and a new round was minted; only the next claim ended the call. The answer now runs endLostEgress, the check every read runs. It does so before the budget is charged, and again inside its own commit, so a revocation in between is caught too. The call ends at once, and the caller gets -32004 task_not_awaiting_input. An ended call also drops its stored question.
  • Throttling answers 429 (test fix-up, C). Core's signed router answered a DID past its per-DID bucket with 401, so Brain, a runner or a misconfigured gateway could not tell "slow down" from "bad key". It now answers 429 with retry-after: 60, as the owner-device path already did.
  • Close takes the DID lookup down with the rest of Lane 2 (installA2ADidResolver(null); getA2ADidResolver beside the other installs' getters).
  • The two-node harness is type-checked on its own. It runs Core and the gateway in one process, so it imports both apps. Adding the gateway as a dev dependency would have broken the core image's npm ci, and the packaging test caught that. Instead core-server's tsconfig.json excludes that one file, and tsconfig.cross-app.json (root: both apps) checks it as part of core-server's typecheck.
  • What the bound promises. Seven skills, each at the largest share that fits, always build a signed card under 128 KB, in any form, beside a name and description at their caps; a test builds them with every listing's text far past its cap. Because the share is measured in its largest form, a public card often holds an eighth. Enough skills at the bound fill the card, and then card_too_large is the right answer, since the owner has listed more than one card can carry. 16 KB is several times any schema in the catalog.
  • One card cap everywhere (A2A_LIMITS.maxCardBytes, 128 KB of canonical bytes). buildInboundCard refuses a larger card with card_too_large. The publisher treats one as not publishable: none goes out, and one already there is taken down. AppView's A2A_CARD_MAX_BYTES is the same constant.
  • A skill id longer than a card allows (capability@rkey over 256) is left off with skill_id_too_long; the rest of the card stands. The card lexicon's skills items allow 256, as the card validator does.
  • Cancel after the effect started ends an inbound call outcome_unknown (canceled_after_effect), never TASK_STATE_CANCELED. Brain may not cancel an inbound child at all (403); the owner and the gateway's CancelTask may.
  • A grant on a public listing adds nothing. The listing decides the access mode, as for a named rkey: public rules and the client's scope apply whether the call names the rkey or carries a grant.
  • Stated rules, one copy each: REST query names are looked up as own members only (constructor, __proto__ are not parameters). The unreachable default in queryValue was removed, so the own-key check is the only guard and a test proves it. One A2A-Version grammar (A2A_VERSION_GRAMMAR) serves the gateway and Core's ingress. An id-less object is a notification only when it is a valid Request; otherwise it gets -32600 with id null (JSON-RPC 2.0 §5).
  • DID challenges are stored as their sha256, like a bearer token; the clear value never touches disk.
  • The host transport never throws. The pinned lookup answers on the next tick, as a real lookup does; answered at once, an unroutable IPv6 connect failed before the request had its error listener, and the process died. If https.request refuses its options (a header value with CR/LF, which a remote token endpoint controls) the call settles as a failure with nothing sent. That path was in the first fix but never ran: its finish read the deadline timer before the const was declared, and the ReferenceError rejected the promise. The test that exposed this is now in the suite. The extra socket error listener was dead (the http client attaches its own before 'socket' fires) and is gone.
  • A stand-down is guarded on the fencing generation, so a step that read the row before the owner's activation cannot undo it.
  • Conflict evidence stands. A recheck of a withheld card adds its verdict to the conflict's evidence (revalidation: {reason}) and takes it off when the card verifies again. It never replaces the conflict, so the spool rows the conflict cites stay spared. A card with no conflict that verifies again keeps no stale verdict. Every further event at a revision already in conflict joins the evidence, up to 16 (A2A_CONFLICT_EVIDENCE_MAX). Past that the card is withheld either way, and a broken or hostile stream cannot grow the evidence or the spared rows without limit. The finding's verifier judged the third-event case no breach of a stated rule (design §8.3 speaks of "both events"); it was fixed anyway, since keeping every event costs a bounded list.

Design decisions — the sixth cold audit (2026-10-04)

A fresh Claude cold audit of bd3da7809fcb0a71, five slices, each finding put to a skeptic. 13 findings stood (C6-1..13); a fourteenth came up while fixing them. Each fix has a test, and each was broken on purpose to show a test fails.

  • An inbound call's result is never posted in the owner's chat (found fixing C6-7). An inbound execution child is a delegation task, and Brain's event consumer turns a delegation task's ending into a chat message, so every outside call that ran (auto or reviewed, pinned or in-process) put its result in the owner's chat, and handed Brain the result. That breaks Silence First (Law 1, A2A-I7). Core migration v62 adds two triggers: the events of an inbound execution child are kept for the audit stream but never queued for Brain's delivery feed, whoever writes them; the upgrade clears any already queued. Fixed in the database, not by hiding the events at read time, which would leave them undelivered at the head of the queue. Lane 1 dispatch children and approval cards keep their events.
  • Brain reads no inbound execution child (C6-7). The single read and /running refuse it, and Brain's task list leaves it out (the list was a second way to the same payloads). Brain lists approval tasks only, and answers an in-process round through Core's own runner, so nothing of Brain's needs these reads. The owner and admin still read them.
  • A slow guard scan holds back no other result (C6-5). The worker bounds each model call by the time its claim has left, less 5 s to post the verdict, and skips a second attempt it cannot finish; a scan that runs out posts nothing. Core hands out every job not yet tried before any whose claim lapsed. The lease is 3 minutes, room for two model calls at the router's default 60 s. A result the model cannot judge in time stays held, fail-closed, and the owner gets the held notice.
  • A held task's lapsed claims are held with it (C6-6). When a client cannot authenticate for now, its task's events wait; a claim a gateway took and never answered is now given back and held with them, so it leaves the due set. Before, it stayed due and every claim read it again: a crashed gateway's full batch could stop stream delivery for every client.
  • Error answers with a null id (C6-1). JSON-RPC 2.0 §5 has a server that could not read the id answer a parse error or an invalid request with id null. Those two, and only those, are read as errors (refused unread, so remote_rejected); any other answer with a null id is still malformed.
  • The card's id rule holds at the call (C6-2). A skill whose capability@rkey is longer than a card allows was off the card yet callable by bare name or reference. One predicate, skillIdFits, now decides both, as skillShareFits already did; the call is refused skill_id_too_long.
  • Every default-ignorable code point is invisible (C6-3). The shared set adds the Khmer inherent vowels, U+FFF0–FFF8 and all of U+E0000–E0FFF; a test checks it covers \p{Default_Ignorable_Code_Point} as well as Cf.
  • One frame for Dina's card (C6-4). dinaCardFrame in @dina/a2a holds both interfaces, the bearer scheme and its description, the scope-less requirement and the flags; Core's card and the SDK vector's fixture both use it, so a change to what Core passes fails the vector check. The JSON-RPC path moved to @dina/a2a beside the REST path; Core re-exports it.
  • A card's freshness is its receipt time (C6-9). The spool stamps received_at on AppView's clock; a card's indexed_at is that time, so a card drained after the directory was off for a month, or reinstated after weeks withheld, is served as stale.
  • A failed publish never delays an unpublish (C6-10). The wait after a failed attempt now holds back only the operation that failed (migration v63, retry_operation), and the step judges what the card should be before it looks at any wait. Design §8.2: predicate-false always drives an unpublish.
  • Tests that could not fail (C6-11, C6-12, C6-13). A credential's end (rotation, expiry, revocation) is now tested against a second client with a webhook and streams of its own; Brain's event feed after an approval is tested for the card's words; the foreign-key delivery ack is sent while the claim is live, and the claim's holder is checked through the route.

Design decisions — the third cold audit (2026-10-04)

A fresh Claude cold audit in five slices (the @dina/a2a package, Lane 1, Lane 2 and the gateway, Lane 3 and the directory, and the tests themselves), each finding put to a skeptic. 19 findings; 16 stood, 3 were refuted. Every fix below has a test, and each was broken on purpose to show a test fails.

  • A card is signed in two forms (C3-1). The reference SDK (a2a-sdk 1.2.1) signs and verifies a form of the card that §8.4.1 does not describe. It reads the card into its proto (members the proto does not know are dropped), prints it back, and then removes every empty string, list and object at any depth, REQUIRED fields included. Every bearer card carries a scope-less requirement ({"bearer": {}}), which that form drops, so the SDK's verifier refused every card Dina served, and Dina read a genuine SDK-signed card as invalid. Now cardSdkSigningPayload computes the SDK's form. Dina verifies a signature over either form, and signs its own card over each form that differs (two signatures, one key). The verifier gets every form's signing input in one call (JwsVerifyFn.signingInputs), so each signature still writes one note for the owner's review card. Vectors the SDK itself made (card_forms.py) hold the payloads byte for byte, and a live test runs the SDK's own signer and verifier both ways.
  • A request signature names its audience (C3-2). A DID-bound client now signs dina-a2a-request:v1, the DID of the node it addresses, and then the six request lines. One DID may be a client of many nodes, every gateway serves the same paths, and each node keeps its own spent nonces. Without the audience line, whoever saw a request (the node it was sent to, a gateway, a TLS terminator) could replay it to another node inside the time window. Core checks the text under its own DID, and a node with no DID yet checks none. The card states the new text; design §5.1 and §10 are updated.
  • One ambiguity rule for the card and invocation (C3-3). A capability one listing configures under two names (itself and an alias) is ambiguous whatever else is true of either entry: the card leaves the skill off (ambiguous_skill) and invocation refuses every call to it, by any name (skill_ambiguous). Both call ambiguousCanonicals. The old card rule counted only entries that were otherwise projectable, so the card could show an id that resolved to the other entry.
  • One cancel per operation, answered truthfully (C3-5). The runner treats only the errors that say a cancel cannot happen as final (task not cancelable, task not found, operation unsupported, method not found). Any other error is asked again on the next poll, as a transport failure is. Once the remote has refused, the owner's next cancel answers 409 cancel_refused, and the operation view and the console show the cancel's state. Re-arming a refused request was rejected: design §6.4 keeps one request per operation.
  • The poll ends a fixed time after the send (C3-6). Migration v61 adds a2a_tasks.sent_at, written with the transmitting phase before the send, and backfills running operations from their status time (when they became running). A resume after a restart or a lost lease polls until sent_at plus the deadline, never a fresh 30 minutes.
  • A credential is created from the schemes Dina offers (C3-7). Creation and binding both read cardSchemeChoices (16 schemes, 32 scopes each), so no secret is stored that could never be bound.
  • A refused plugin child fails under its claim (C3-8). A plugin lane fails a task only under its claim token. Core's refusal now carries the claim it refused, so the child ends failed; before, it stayed running under the plugin's lease, came back to the queue, and wrote a late report each round.
  • The rate-limit exemption is the gateway's, by DID (C3-9). Core's per-address budget skips a gateway route only for a call that names the gateway's DID. A call that names it without the gateway's key costs one signature check and is refused there. Separately, a DID no caller holds no longer spends a per-DID bucket (it is refused at authorization whatever it asks), so a flood of self-made did:keys grows nothing.
  • A tombstoned DID has no trust in the directory (C3-11). resolve gives a DID a moderator tombstoned no trust, and the directory now orders, pages and reports it at 0. One query finds every served DID whose subject merge chain touches a tombstoned subject (a superset), and resolve's own loadSubjectTrustFacts decides each one, so the merge-chain rules stay in one place.
  • The console has a directory panel (C3-12). Plan §3.8 asks for console panels and design §8.2 for an owner-visible notice. The panel shows the listing switch, the publisher's state, and the stand-down notice in words. It starts and stops publishing. It offers to replace the fence only after activation found one it cannot verify.
  • The publisher reads the node's own repository (C3-13). Every read names the node's DID. Before, reads went to whatever account the PDS session held, and a missing or foreign fence there could stand the node down. The wire fake now honors the repository a read names, which is why the old test passed.
  • Tests that could not fail (C3-14..16). The gateway pump's fences, the action classes quote, booking and agentic, and a new key under the same kid each gained a test that fails when its rule breaks.

Deviations

  • A waiting SendMessage gives up after 10 s (dual review CX-3). A2A says a call that did not ask to return at once MUST wait until its task ends or is interrupted, with no bound. A call may run for ten minutes, and a reviewed one waits a day for the owner; no hop between the client and Core holds a request that long (the gateway's forward, the TLS terminator in front of it). Past A2A_SEND_WAIT_MS (10 s) the call fails with wait_deadline_exceeded, naming the task; it never answers with the unfinished task as if it were final. The client reads the rest by GetTask, a stream or its webhook, or sends the same message again and waits again. Most Tier 1 answers land inside the bound. The gateway gives that one forward Core's wait plus 5 s, whatever its timeout for other calls.
  • M2, no status filter on ListTasks. A completed call reads FAILED once the authority behind its result lapses, so no stored column answers a status filter exactly, and an inexact one would page wrongly. The filter is refused as invalid params; contextId, statusTimestampAfter and includeArtifacts are honoured.
  • M2, no A2A SDK handler. Plan §4.3 mounts the JS SDK's DefaultRequestHandler in the gateway. It would be a second interpreter of each request with its own task model, in front of Core's receipts, refusals and route binding. Core already parses, binds and answers; the gateway forwards bytes. The SDK is also not a dependency of the repo.
  • M2, the gateway's key is its own random seed, not m/9999'/3'/3' from the master seed. Deriving it would put the owner's seed in the installer step that provisions the gateway; Brain's lite key is a random file for the same reason. Core learns only its did:key. Index 3 stays reserved and unused.
  • M2, a rogue claimant is not told 403 at claim. The design says a paired agent naming another's lane gets 403. A bound lane still carries D2D work any paired runner may take, so a lane-wide 403 would break D2D on every bound lane. The A2A children are invisible to other claimants instead; every verb and read on one answers them 403.
  • M2, the card key is published through jku, not yet in the DID document (design §7.1). Publishing a verification method is a PLC update; Lane 3 (M5) needs it and does it. Until then Dina's own Lane 1 verifier (which requires jku) and any client can check the card.
  • M2, no official TCK run. The A2A TCK is a separate Python project fetched from the network. M2's stand-ins: the gateway e2e over real HTTP into Core's router with signature checks, every card validated against the v1.0 shape, and every task answer built by the shared view code. Run the TCK before a public port opens (open question).
  • Ingress move, kept as it was: a task create that fails on the auto path is logged and the requester hears nothing. Brain's handler threw that error to the dispatcher; Core's never throws. The requester's view is the same either way, and answering service_unavailable would change the wire (open question).
  • Ingress move, behaviour fixed: the phone's plugin plane answered plugin_lane_unavailable to every inbound query, because the runtime read the workflow global before the phone set it; it now hands off. The registry looked names up with in, so a capability named toString or constructor "resolved" to a function and the params fallback threw; it now reads its own keys only.
  • Ingress move, behaviour changed on review (security): an approved card whose listing is gone or paused answers unavailable, one whose published schema changed answers schema_version_mismatch, and one whose params fail the live schema answers the validation error; each closes the card. Brain's handler ran the card's own lane, tool and params, so a card Brain created through the route, then approved, could put any work on any lane, reserved ones included. A schema with no canonical JSON form is now refused at save (schema_not_canonical), and the server publisher records one as a failed publication rather than throwing, which had taken core-server down at every boot.
  • Ingress move, A2A not yet folded in: plan §3.5 says A2A must not get a second copy of these rules. M0's a2a/normalize.ts keeps its own: the hash is optional, params use the strict plugin validator, and a schema that validator cannot enforce is refused. M2 makes it call the shared rules where they agree and keeps those three differences on purpose.
  • Design §8.2 says the directory envelope signs over "the project's canonical JSON". The code uses RFC 8785, which is that form for every field the envelope carries.
  • Migration v53 adds columns the design's §9 does not list: a2a_remote_agents.name, signature_detail, updated_at; a2a_skill_bindings.updated_at; a2a_tasks.consent_json (the exact consent payload, re-hashed at dispatch) and reply_to (the conversation a result returns to); a2a_permits.void_reason; a2a_guard_jobs.held_notice_at. It adds foreign keys from credentials and bindings to their agent, makes a2a_guard_jobs.operation_ref unique (one guard job per operation, which the single-delivery rule needs), and indexes operations by state. All A2A timestamps are milliseconds. M1a also adds a2a_remote_agents.endpoint_tenant.
  • Resume at acknowledged. Design §6.4 says a lost lease at transmitting or later ends outcome_unknown. The code does that at transmitting, but at acknowledged (the remote returned a task id) the next claim resumes polling: GetTask is a read and re-executes nothing, so giving up would throw away an outcome Dina can still learn (A2A-I8 forbids re-execution, not reading).
  • The guard claim is POST /v1/a2a/guard/next: it changes state. The design first said GET; §4.3 now says POST too, so this is no longer a departure.
  • Proposals are not session-bound yet. Design §6.2 step 0 asks for a "validated live owner session". Core has no owner-turn record until M1b brings the release context and turn-start digests; M1a has the rate bounds only. M1b binds a proposal to the owner turn Core recorded.
  • No a2a-tck client checks. Plan §4.2 lists them for M1a, but the kit tests A2A servers only (its system under test is a server). Client conformance is covered by the run against the a2a-sdk reference agent; the kit belongs to M2, when Dina serves A2A. The plan is corrected.
  • The owner's words were kept as text for a while, against design §4.2 (a) and §6.2 step 2, which say digests: a quote could then be part of a message, which a digest cannot prove. Once a proof had to cover a whole message, that reason was gone, so Core now keeps only a digest of each message (migration v55 rebuilds the table, dropping any words an earlier draft stored). The design is followed again.
  • Brain records the owner's words. On the server the owner's chat reaches Brain unauthenticated, so Core cannot witness it today. Recording in deterministic code at the chat entry stops a prompt-injected model from passing text off as the owner's; it does not stop compromised Brain code. Owner-signed chat, after M2's precondition that Brain's loopback routes authenticate, would let Core witness the words itself.
  • The consent payload adds provenance to A2A-I10's field list: the owner approves the sources as shown, so the hash must cover them.
  • No standing sharing grants yet. Design §6.2 step 4 allows a standing grant as the egress authority; it matters only for an auto-approved lane (§13 Q6), which is not built. Every Lane 1 send carries the owner's approval as its one-time authorization, so a2a_sharing_grants is not created.
  • "Rehydration" is a legend, not a rewrite. Design §6.5 says scrubbed spans are rehydrated on owner surfaces. Writing originals into the remote's text would let the remote choose where the owner's details land (a link back to itself) after the guard had judged the placeholder version, so the owner sees what each placeholder stands for beside the answer instead.
  • The legacy fallback paths (reason(), runReasoningAgent) log no releases: they run only with no agentic handler installed, and offer no A2A tool.
  • The owner's cancel of a pending card runs inside the A2A transaction. Withdrawing the card fans out to every composed decision handler inside that transaction. Moving it after the commit would let a crash leave an approvable card behind an operation already cancelled; the handlers are idempotent and swallow their own errors, so atomicity wins.
  • M3: a paused listing stops new work and releases work already done. §7.3 names "listing not withdrawn" among the egress checks. Dina reads "withdrawn" as deleted (or replaced by a new listing under the same name). A pause, a draft or a move off the services surface refuses new calls at admission and new runs at claim (any edit after a call was accepted already refuses its run, through the pinned revision; the authority check also names a listing that is not live), but a result already produced is still released. M2 treated a pause like a revocation on reads; round 1 made it a hold that could be lifted; rounds 2 and 3 found that every lifted hold opened a gap between what a client had been shown and what was recorded. To cut a client off, the owner revokes it or its grant.
  • M3: the claim door is a POST. The design names GET /v1/a2a/ingress/events; a claim changes state (it leases rows), so it is POST /v1/a2a/ingress/events/claim, beside /ack.
  • M3: two bookkeeping columns the design's schema lacks. a2a_tasks.event_seq and event_state (the count of events and the state the last one reported), and a2a_push_outbox.seq. The design's source_event_id needs a stable per-task counter, and the gateway needs the sequence number to send each stream an event once.
  • M3: a refusal on a streaming call is one SSE event. The JSON-RPC binding does not say how an error before a stream is sent. Core's JSON-RPC error goes out as the stream's one data: event and the stream ends (reference clients read a stream's events as JSON-RPC responses and expect text/event-stream). HTTP refusals (401, 429, 413) stay plain HTTP.
  • M3: the token header. A2A v1.0 defines a config's token but not how it is sent. Dina sends it as X-A2A-Notification-Token, as A2A's reference SDKs do, beside Authorization: {scheme} {credentials}.
  • M3: a client that can reach no skill gets ExtendedAgentCardNotConfiguredError (reason no_skills_for_client): a card must list a skill, and Dina has none to show that client.
  • M4: the owner names the DID when issuing the challenge. The design's challenge is owner-started and single use but does not say whose DID it is for. Naming it makes the challenge enough on its own: only that DID's key completes it, so the binding needs no other credential, a stolen bearer cannot bind the thief's DID, and a client whose key was removed can be bound again.
  • M4: Core keeps spent nonces of DID-signed requests on disk. §5.1 asks for a per-DID replay cache. Core's other signed routes keep nonces in memory for a fixed time; A2A's are kept in identity.sqlite until the signature expires, so a replay fails after a restart and for a signer whose clock runs ahead.
  • M4: the binding's public door is /a2a/v1/did-binding, plain JSON. The design names only Core's route. A2A v1.0 has no method for it, so it is a Dina extension endpoint beside the JSON-RPC one, not a JSON-RPC method.
  • M4 step 2: an in-process round may defer its effect boundary. §7.3 puts the in-process boundary "immediately before the capability runs". §7.7 and §12 M4 want "a provably pre_effect in-process execution" that may ask, and "an effectful pre-effect interruption" under review. Dina keeps §7.3's rule as the default and adds an opt-in deferred boundary for capabilities that authorize each effect themselves; the runner still authorizes before any result goes out.
  • M4 step 2: one question at a time, eight rounds. The design names neither a deadline nor a cap; Dina sets 24 hours a question and eight rounds a call, so a runner cannot hold a call open forever or grow its payload without end.
  • M4 step 3: REST refuses unknown query parameters. The reference SDK ignores them. Dina refuses them, as it does an unbound query on JSON-RPC: a signed query is bound in full.
  • M5: plugin installs move the projection revision too. The design lists listing config, runner bindings, the owner's switch and the signing key. A plugin install's state also decides whether its capability reaches the card, so its changes count.
  • M5: another fence landing during activation is the owner's to resolve. The activation answers lost_race rather than claiming a still greater epoch on its own; an unrelated write only restarts the read sequence.
  • M5: a missing fence while active stands the node down. The design covers a foreign fence; a fence that vanished (it is never deleted) means the repository is not what this node left, so it stops too.
  • M5: a node learns of another server's fence when it next writes. §8.2 ties stand-down to "a writer observing a fence". The first build also read the head and the fence every 30 seconds while published, which told the owner sooner; it is gone, since every write is fenced anyway and the reads cost the PDS 8,640 calls a day per idle node. The old server's view says "published" until its next write (a card change, a switch, the 14-day refresh), then "another server is publishing".
  • M5: trigger (c)'s "any DID-document change". Read as a change of either key the directory checks: dina_signing (fence, envelope) or the card key (the card's JWS). A new handle or service endpoint changes neither the card nor what AppView verifies, so it republishes nothing.
  • M5: the card's JWS header keeps its jku and thumbprint kid. They serve A2A clients that fetch the gateway's key set. AppView ignores both and checks each ES256 signature against #a2a_card in the DID document, as §8.3 asks; a signature that verifies there proves the key.
  • M5: did:web publishers are refused. §8.3 says AppView's outbound connections follow §6.6 (resolve, refuse private addresses, pin the socket). The only such fetcher is @dina/net-node's, which brings @dina/core with it; copying it into AppView would make a second copy of security code (the Dockerfile's own history warns against that). AppView resolves did:plc through the PLC directory it is configured with (HTTPS; plain HTTP only outside production), and a did:web card is refused, fail-closed. Every Dina node is a did:plc.
  • M5: commit.rev is not added to the trust handlers. §8.3 names it a required change to the handler signature. The directory takes the revision straight from the commit into its spool; no trust handler orders by it, so threading it through all of them would be unused plumbing.
  • M5: a fourth gate, the account. An account event that says the account is inactive (deactivated, deleted, taken down by its host) withholds its card; active again, it serves. §8.3 lists three gates; a card whose repository its host no longer serves is not one to hand out, and a deleted account emits no delete for its card. The status is stored apart and judged by time against the card's commit (see decisions).

Tradeoffs

  • M2: the gateway caches the card for 30 seconds. A stale card can list a skill whose binding just went; invocation re-checks everything, so the cost is one refusal, never a wrong run. Core is spared a signature per public card fetch.
  • M2: the gateway answers protocol errors before any authentication. They say nothing about Dina's state, and Core never sees a body it could not route. Core still re-parses everything it receives.
  • M2: invisible children over a lane-wide 403 (see deviations): D2D on bound lanes keeps working; the price is that a misconfigured second runner learns of the binding only from the owner, not from a refusal.
  • Extend Core's validator, not write an A2A one. Plugins and A2A share one audited trust-boundary validator, and the profile audit makes its ignore-unknown default safe for A2A.
  • A time-based held notice, not a "no model" report from Brain. Core sees only that nothing has checked a result; adding a Brain-to-Core status channel to name the cause would add a route and a state for wording.
  • Unsigned cards register. The card is never authority (A2A-I1); the signature state and its meaning are shown to the owner, who decides.
  • Keep Brain's schema-hash copy for now (M0). Resolved by the ingress move: Brain's copy and core-server's AppView copy are gone, and Core's recipe is the only one that computes or checks a published schema_hash. The canonical-JSON code left in protocol (signing) and commerce (digests) does other jobs.
  • Ingress move: parity by unchanged assertions and a differential run, not by keeping Brain's handler behind a switch. Brain's 73 handler cases moved to Core with every assertion line as it was; only the stub changed, to a real workflow service whose create and cancel inputs are recorded as Brain's stub recorded them. Before Brain's handler was deleted, 50,000 generated cases ran through both, comparing every create, cancel, reply, notice, submitter call, log line and throw: all identical, apart from the one recorded difference (a failed create thrown versus logged). A switch would have kept two copies on the live path.
  • M3: events are stored whole. Each outbox row holds the event as sent, result included, once per target (at most five copies: the streams and four webhooks). Building events at claim time from the task would store less, but a row would then say what the task says at claim, not what changed. Rows go with the task after 30 days.
  • M3: a revoked client's stream ends without a final event. The design suppresses pending events on revocation. A client whose grant lapsed could be sent the neutral FAILED GetTask now shows; Dina sends nothing and ends the stream, and GetTask tells the rest. A stream whose task records no new event before its authority goes stays open, idle, until its 30-minute lifetime.
  • M3: the gateway buffers recent events rather than reading by cursor. Core could serve a stream's events by cursor on demand, but that is a second read path beside claim and ack. The hub's 30-second buffer covers the only gap (Core's answer to the stream's registration, milliseconds).
  • Card signatures: two forms, not one (C3-1). Signing only the SDK's form would match the reference SDK and fail every verifier that follows §8.4.1, Dina's own among them. Signing only §8.4.1's fails the SDK. Two signatures cost about 300 bytes on a card that holds up to 128 KB. Accepting the SDK's form when verifying covers less of a remote card (none of its empty values or unknown members), but the pin hashes the §8.4.1 content, so any change there still re-gates the owner's review.
  • Directory trust for a tombstoned DID: a two-step read (C3-11). Writing resolve's merge-chain rules again in SQL (deterministic ids, dangling pointers, cycles, the depth cap) would make a second copy that could drift. A column kept by the moderation tool would go stale between runs. The superset query plus resolve's own check costs one indexed pass over the served cards and a read per candidate, and tombstones are rare.
  • M3: a lost record is repaired, not prevented. The requeue observer's throw is isolated, so a bug there cannot block a requeue. The sweep records any change it finds unrecorded; a stream may then see two changes as one.

Open questions

  • D1–D7 (above).
  • Is 10 s the right wait for a SendMessage that did not ask to return at once (CX-3)? Longer serves slow runners in one call, but holds a request open at every hop for that long. And is internalError with wait_deadline_exceeded (500 over REST) the right shape when it runs out?   • Should a value the owner said AND a vault item holds keep its original? M1b keeps none when two sources cover it.

  • People-graph names, relationship hints ("my oncologist") and contact roles reach the model unlogged. They have no persona tier to taint by. Treat the people graph as a private read, or record which persona each surface came from?

  • M3: webhook hosts. Any public HTTPS host passes. A client could point webhooks at a third party's public URL, and Dina would POST its task's events there (at most four configs per task, each event's body only). Should an owner be able to allow-list webhook hosts per client?

Tradeoffs

  • Refuse at the entry point vs fall through. A request naming an owner device whose check fails is refused there (401/403), not passed on, so a bad owner signature never reaches a route; any other device falls through before a nonce is spent.
  • Presence per principal vs node-wide. Node-wide was simpler and matched the old stamp, but let a script ride a browser's proof. Per principal costs one field on the request; staff presence was already keyed per device.
  • Revoked browser: probe vs forget on any refusal. Forgetting on the first 401/403 would drop the key for a clock skew or a path off the owner surface. One status probe confirms first; timestamp, nonce and throttle refusals never trigger it.
  • Cross-tab state: fresh read vs broadcast only. A broadcast alone misses a tab that was asleep; reading the stored device on each use cannot be stale. The channel only redraws screens, and opens only while one listens.
  • Busy through the retry: run settles late vs a running flag. A flag needed every screen changed; settling run after the retry fixed all eight screens at once.
  • Multi-choice on the web: confirms in turn vs a prompt or an in-page picker. window.prompt means typing; a picker per screen is more code. Sequential confirms serve the two-option cases; true pickers stay on the list.
  • Ask when the browser is not connected: fall through vs fail closed. Failing closed blocked every Ask on such a browser; the connected-host binding is a convenience, not a policy, so only that one refusal falls through.
  • Rate limit: exempt app files vs raise the default. Raising it weakens every caller; the app's files are public and carry no authority, so they alone skip the per-IP bucket.

Group Coordination IN PROGRESS

Implementing docs/GROUP_COORDINATION_ARCHITECTURE.md: a group plan is a STAR of 1:1 availability_coordination spokes folded on the organizer's node. Phases: P0 the fold (pure) ✅ · P1 spokes ✅ · P2 disclosures ✅ · P3 surfaces ✅ · P4 the hand-off ✅ · the six-lens review round ✅ · the live two-node run over the cloud relay with a real model ✅ (2026-09-16).

Design decisions

  • Acceptance is echoing a candidate. Slots compare by a canonical key of start (trim, collapse, case-fold); a slot the organizer never proposed is a counter whatever the guest called it, and a counter reply accepts nothing even where it echoes one. The organizer controls the vocabulary, so the fold never decides whether two wordings are one day.
  • A required guest is accounted for by an answer OR the closed window — the plan moves to folded only then, so the organizer is never handed a decision over a guest who may still reply. A needs_more_info reply is an answer that accepts nothing and is never listed as having emptied the fold.
  • At least one guest must be required (§17.2 resolved) — an all-optional plan would converge on whatever nobody objected to. The fold over zero answered required guests agrees on nothing, never on everything.
  • Rounds are fan-outs — propose, confirm and widen each count; three is the ceiling and openRound refuses the fourth before anything is on the wire.
  • Bounds refuse by who authored the text. The organizer's own candidates over 80 characters are refused (malformed_slot) — a date cut in the middle is a different date; a guest's inbound disclosure text is clipped to one 120-character line instead, because a peer's long note must not cost the organizer that peer's availability.
  • The aggregate is strict, the ingress is lenient — recordReply refuses a malformed disclosure; the route (P1) normalises each inbound disclosure, drops the malformed ones with an audit count, and records the rest. Same split as every validator/ingress pair in Core.
  • Disclosures dedupe across rounds by kind and text — "gluten-free" at propose and again at confirm is one requirement, not two portions.
  • The plan row is the record — one JSON column plus state, in the identity store (migration v45, appended), rehydrated strictly with the bounds re-checked so a hand-edited row cannot carry a ninth guest.
  • The window is the plan's (P1) — windowSeconds per plan (≤ the wire TTL), roundOpenedAt per round; every spoke's task expires with it, and a negative outcome is learned only at the close, so neither the outcome nor its timing says refused, offline, ungranted or silent.
  • Two-stage spoke — a guest with a stored offer is queried at once; one without gets the 1:1 preflight (service.grant_request) and is queried when the offer lands (event-triggered; the read path is the fallback). The query replaces the preflight in the plan's memory: one spoke, not two.
  • The fold is on read, no sweeper — reading a plan consults its spoke tasks, records replies that landed inside the window (task.updated_at ≤ closesAt, so a store that kept a late reply changes nothing), closes the window for the rest with one clock reading, refolds. A per-plan promise lock serialises read, choose, widen and the offer listener.
  • A new round supersedes the last — still-live spoke tasks are cancelled on this node, and each spoke carries a dedupe scope (planId:round, an additive option on submitServiceQuery) so two plans asking one guest one question never share a task or a reply.
  • Layer 1 refuses the whole plan before anything is sent — a guest who is not a contact or is blocked refuses by name; it is the organizer's own record, so naming it costs no guest anything. Bounds likewise.
  • Nothing on the wire names the plan — random query and request ids; params are the organizer's intent and candidates; the confirm round says Confirming <slot>: <intent> because a guest's node reads the intent, not the plan.
  • Owner-only three ways — /v1/coordination in the authz matrix, in the server binder's owner-surface list, and makeOwnerGuard in every handler; the same boundary as /v1/run and /v1/commerce.
  • The disclosure gate is Core egress, on the way out (P2) — a responseEgressGate hook on the workflow service sees every completed provider answer on both bridge lanes; for this capability it drops what the contact's tier does not admit (per-category policy first, else the contact's own tier; summary/full admit, none/locked refuse), drops any about but household, and holds a reply carrying a health kind for the owner's yes. Nothing a model wrote reaches the wire ungated.
  • The hold is an ordinary approval task — disclosure_review, lapsing a margin before the requester's window (one sweep cadence plus the relay hop), carrying the task id and the lines asked about; the inbox lists it, and an approvalDecisionHandler hook on the workflow service (fired where the decision lands, whichever route, command or sweep delivered it) releases the right one through the same durable bridge a completion uses. A no still answers the availability, and so does silence (web round): the owner's auto policy already committed the availability, only the fact waited on them. With no room to ask, the reply leaves at once without the fact.
  • One schema, two copies, one test — disclosures is additive on the Brain validator and the protocol catalog; a registry test pins the two byte-identical, and about's enum has one member.
  • Two doors for Brain, every decision the owner's (P3) — POST /v1/coordination/plans and GET /v1/coordination/plans/:id admit brain and the phone's unstamped in-process transport, exact and method-bound in the authz matrix and re-checked in the handler, on the same terms as the plugin tool-invoke route; choose, widen, drop, stop and delete stay owner-only behind makeOwnerGuard and ride an owner-marked client Brain never holds.
  • One tool touches N contacts — coordinate_group is terminal, opens one plan per request, and resolves guests as the owner named them against the contact directory (exact display name or alias first, then a contained name; two matches are a question back, none is a refusal by name). Core fans out; the model never sees a per-guest dispatch.
  • The plan card is a view — the group_plan lifecycle message carries the plan id and intent only; the card reads the fold through the owner client, refreshes every four seconds while the plan is open, and sends each decision back through the same client. It shows a household as answered, waiting or "couldn't reach", never why.
  • A provisional fold is not a decision (review round) — a fold that closed on a required household nobody could reach is folded with fold.state: waiting; choose refuses it (required_unanswered), and the card shows "works so far" with §13's three moves: go ahead without them, ask again, stop. §4's fold is "the slots every REQUIRED guest accepted".
  • A settled plan is not a dead end — widen and abandon are allowed from settled (§13: a family changes its mind → the card reopens the fold; the organizer cancels), within the same round ceiling.
  • The review card is a decision, not a payload — it carries the execution task id, the response's identity and the lines the owner is asked about; the release rebuilds the bytes from the task's OWN stored result and gates them again, and refuses a card whose identity names another requester. The workflow create route refuses the type outright, and Brain may not approve or cancel one.
  • Every door a provider answer leaves by is gated — the delegation and plugin bridge lanes, the reasoning lane's staged commit, and the owner's manual /v1/service/respond (which answers held and stores the answer for the card to release).
  • The organizer's own tier applies on receipt (§13's last row) — the same resolver the guest's gate reads (per-category policy, else the contact's tier) decides what the organizer holds; a refused disclosure is dropped and counted, the slots stay.
  • A spoke has no Talk card — spokes carry origin_channel: group_plan:<id> (local only) and the chat deliverer posts nothing for it, so a per-spoke outcome never renders at its own time with its own reason; the plan card is the surface.
  • The fan-out resumes on read and never throws a plan half-sent — a spoke fault is audited; a guest the fan-out never reached is queried on the next read inside the window and closes like any silence after it. Deleting a plan scrubs every spoke's stored reply (a new scrubResult repository verb), since the disclosure text lives there too.
  • A withheld disclosure takes the model's prose with it (live run) — when the gate removes any disclosure the model attached (tier, shape, or the owner's no), the reply leaves as availability only: no message, no slot note. The organizer applies the same rule on receipt. Free text cannot be gated line by line; a no to any part of what the model added is a no to all of it.
  • Brain has a third door: plan handles (live run) — GET /v1/coordination/handles lists recent plans as id, intent, state, chosen and nothing about who is in them, so a later turn with no memory of the turn that opened a plan can find the one the owner means. group_plan_handoff takes an optional id: one plan, or the one that is bookable, is picked; several are handed back to choose from.
  • Requirements carry the needs (live run) — {kind, count, needs}, the needs being the disclosure lines deduplicated and sorted so their order says nothing about who asked. §10's "one gluten-free portion" needs the need; rule 7's "no disclosure text" is read as no household, no name, no attribution — the catalog instruction now tells the guest's model to write the need itself as the text.
  • A scoped dedupe is terminal-inclusive (review round, confirmed by two refuters) — under a planId:round scope a hit in any state means "already asked this round", so a crash between the send and the plan write re-links to the task on the wire, even one the guest already answered, and never asks twice. The 1:1 path keeps its active-only dedupe.
  • The hand-off is a tool that returns two things (P4) — group_plan_handoff gives the model the chosen slot and the de-identified requirements and nothing else; guests, replies and disclosures never pass through it, and a test pins that its output carries no DID, no name and no line a guest wrote. From there it is the existing search_provider_services → query_service lane, unchanged.
  • The sweeper expires through the service (web round) — WorkflowService.expireTasks runs the repository's sweep and tells the decision handler lapsed for each approval still pending; TaskExpirySweeper takes a TaskExpirer and every host hands it the service, pinned structurally at the plane and the lite server and behaviourally on the phone. The hooks read the service's own clock.
  • The deadline is arrival plus TTL — not the task's expires_at, which a manual claim extends by a lease the requester never granted; the same authority /v1/service/respond already uses.
  • The schema says what a disclosure is (web round) — disclosures and its text carry a field description in both copies ("a need the household has… omit when there is none; never state that a need is absent"), because a listing's own instruction replaces the catalog's default and the model then saw only the bare shape. The result schema hash moves with it (pre-release; a re-save republishes).
  • The owner console can settle a card (web round) — the lite server's owner surface admits /v1/workflow/tasks/:id/approve and /cancel and nothing else on the workflow tree; an owner-marked caller is re-validated against the capability in the handler (makeOwnerGuard), fail closed when none is configured. Without it a server node's owner had no door to a card Core refuses Brain.
  • The web page decides through Brain, and says so — a disclosure_review card on the web shows the lines that would leave and where to decide, no buttons (OWNER_DECIDES_ON_THIS_SURFACE from the inbox resolver's two peers); every other kind keeps its buttons and a refused decision reads Core's own reason on the card, since RN-Web's Alert is a no-op.
  • Null island is no location (vendor round) — a model that has no place to name fills lat: 0, lng: 0, radius_km: 0; the AppView refused the radius and the retry searched 50 km around a point in the Gulf of Guinea, so a named bakery was "not found". viewerLocationFromArgs drops (0, 0), a lone coordinate and a non-positive radius before the call, in both discovery tools; the descriptions say "omit otherwise" as an aid, the code is the rule.
  • A list answer is the answer — the generic result card kept scalar fields only, so an availability reply whose WHEN lived in slots read "Status Ok · Date". Arrays of small objects now render as rows (lead field, note beneath, six shown then "and N more") under a section; arrays of scalars one row each.

Deviations

  • §13 "organizer cancels → a cancelled notice to answered guests" is not sent in P1. Nothing on a guest's node handles it yet (the reminder removal is P3's), and a notice must not count against the round ceiling. Abandon cancels the live spokes locally. Owed with the surfaces.
  • §7's window (a date window) is not a plan field — the plan's window is the reply window; the date window lives in the intent, which is the only place a guest's node reads it from.
  • No "unreachable" fold state — after the window closes, fold.state: waiting with missingRequired means required replies never came; plan.state: folded is what says the round is over. Two facts, two fields.
  • makeOptional is allowed while a round is open and at confirm — P0 allowed it only when folded; §13 says the plan "proceeds on the organizer's say with that family marked optional", which is a decision taken while waiting.
  • The tier the doc names has no production writer. §6 reads getSharingTier(contactDID, 'health'); that per-category store is only ever filled by tests today, and the contact directory holds one tier per contact. The gate reads the per-category policy when one exists and the contact's own tier otherwise, so the doc's rule holds the day a per-category setting ships and the contact tier answers until then.
  • The review card is in the inbox, not yet the Talk thread — §6 places it "in their Talk thread with Mike"; P2 lists it in Activity with a plain approve/deny, and the thread placement rides with P3's surfaces.
  • Transport and note leave unreviewed under the general tier, as §6 says; a model-authored name in such a line is bounded and one-lined but not scrubbed. The vendor-bound derivation never carries text, so the exposure is to the organizer alone.
  • The plan card reads Core; nothing patches it — §9 describes spoke rows patched in place by the event consumer; the card polls the folded plan instead, because the fold is Core's and a card that re-derived it from N spoke events would be a second fold. The guest rows still carry their spoke task ids for a surface that wants both.
  • The intent seam is the tool's description, not a regex — "plan X with A, B and C" reaches coordinate_group through the model's tool choice, the same way every other intent reaches its tool; no per-scenario rule was added to a prompt.
  • Household names on the card come from the platform contact source (in process on the phone, Core through Brain on the web) — read once per card; a failed read leaves a shortened DID. ISO slots read as a day, date and wall time as written; free text stays as written.
  • A plan Core persisted but never carded (the card post failed after the tool succeeded) has no phone surface beyond the owner list route; an "open plans" screen is owed with the surfaces work.
  • The live bed picked OpenAI, not OpenRouter — the node bed's provider order prefers an OpenAI key when one is in the environment; the product decision for real-model harnesses is OpenRouter. The run's findings do not depend on the model.
  • The health gate keys off the model's kind — a diet fact the model labels note leaves under the general tier without review. The kind is the schema's own category claim; a mislabelled fact is a model fault the review of health kinds cannot catch by construction. Recorded as an open question rather than papered over with text heuristics.
  • Talk on the web is parked work, not this feature's — the 1:1 screen sends from the browser-local node, the People "YOU" card shows that node's stale identity, and the guide's plain "Tell Sancho…" has no chat-box route; recorded in the test plan's §12, left to the web plan's Phase 9.

Tradeoffs

  • SpokeReply restates the 1:1 result schema in Core — Core cannot import Brain's AvailabilityCoordinationResultSchema, so the wire shape appears twice; the repository's rehydrator is the guard that keeps them in step.
  • One sanitiser — a third copy of the control/bidi/whitespace stripper was about to land; extracted util/one_line.ts and pointed the context templates at it too.
  • The confirm intent is one line of English composed in Core — a guest's node cannot yet tell a confirm from a proposal by the candidate count alone; the P3 tool can pass the organizer's own wording instead.
  • origin_channel is the guest DID — a reply routes like a Talk-thread query with that guest; P3 decides whether the plan card, the thread, or both render it.
  • A failed send names its task — submitServiceQuery's 502 body gained task_id (additive), so a caller that keeps its own record can point at the task instead of guessing its id.
  • Two generic hooks rather than a coordination import in the workflow layer — responseEgressGate and approvalDecisionHandler are injected like the commerce transformer and the plugin completion handler, composed by one factory (coordinationWorkflowHooks) at all three hosts so neither host wires the gate and forgets the release.
  • The approve leaves the card queued, a state nothing claims; the handler walks it to running and completes it, so the inbox reads "approved, sent" rather than a card stuck in a queue.
  • Two more verbs on CoreClient (openGroupPlan, getGroupPlan) meant every hand-built fake in five test files and the phone's lazy client grew two stubs; the mock in the test harness carries canned answers like every other verb.
  • GroupPlanLifecycle.status is stamped once ("open" at posting) and never patched; the card reads the live state, so the field is the row contract's requirement, not a source of truth.

Open questions

  • Should a plan expose emptiedBy to the organizer by name in the card, or only "no Saturday works for everyone"? Naming is honest and the doc says it; it is also a social fact about a friend.
  • The wire TTL (300 s) bounds the reply window. A review-gated health disclosure needs a human tap inside it; the lapse now answers availability-only a margin before the window, so a slow owner costs the fact, not the guest. Whether to raise the ceiling for this capability is still open.
  • A yes that lands after the window is dropped with the round. Should the card offer "ask them again" as a widen with the same candidates, or is a text to the family the right tool?
  • Should every kind be review-gated rather than only health, given a model can mislabel a diet fact as a note? The cost is a tap per reply; the gain is that no household fact leaves without a yes.
  • Should a health disclosure require the contact's full tier rather than the default summary? Today a new contact's default tier admits it and the review card is the only stop; full would make two explicit decisions stand between a health fact and the wire.
