Change Passphrase (uncommitted)

Settings → Security → Change passphrase (2026-06-17). The capability existed only as dead code (useSecurity.doChangePassphrase + the changePassphrase crypto primitive) but was never wired to a screen and never persisted. Built the durable path + UI. mobile: new service 10 tests, new screen 5 tests, legacy useSecurity suite still green (39 total); tsc clean.

Decisions / invariants
  • A passphrase only wraps the master seed (Argon2id KEK → AES-256-GCM). Changing it is a re-wrap of the SAME seed, so every persona DEK (HKDF-derived from the seed) is untouched and all vault data keeps decrypting — no content re-encryption, no migration. The 24-word recovery phrase (which encodes the seed, not the passphrase) is unchanged.
  • Durable order (the bug the legacy hook had): load wrapped seed → re-wrap (wrong current passphrase fails the GCM tag here, writes NOTHING) → saveWrappedSeed (the unlock source of truth) → then refresh the auto-unlock cache. Seed-first so the new passphrase is live even if the cache write fails.
  • "Unlock automatically" users get saveAutoPassphrase(new) so silent boot keeps working; manual-mode users get nothing cached. The cache refresh is best-effort (try/caught): a failure can't report the change as failed — worst case the gate falls back to a one-time manual prompt and re-caches.
  • Generic wrong-passphrase surface ("That current passphrase is incorrect.") — no oracle about which step failed, matching the recovery-phrase + unlock gates.
Implementation
  • New durable service apps/mobile/src/services/change_passphrase.ts (changeVaultPassphrase) over the real wrapped_seed_store + startup_preferences — NOT the in-memory useSecurity hook (which is left in place for its tests + reused pure helpers validatePassphrase/getPassphraseStrength, now annotated as legacy).
  • New screen apps/mobile/app/change-passphrase.tsx (current/new/confirm via PassphraseField + strength meter + success state) registered as a drill-down route in _layout.tsx; row added to Settings → SECURITY under "View recovery phrase".
  • Client-side guards (empty current, new≠confirm) short-circuit before the service; the service re-validates + rejects no-op (new == current) before any keychain touch.
Not yet usable in the running web build
  • The Home-Node-Lite web app serves a pre-built bundle (apps/home-node-lite/web/dist, last exported 2026-06-15) — the new row won't appear there until cd apps/mobile && npm run web:export rebuilds it. Instant on the iOS dev-client sim via Metro hot reload.

Explicit Composer Modes (uncommitted)

Spec: docs/COMPOSER_MODES_DESIGN.md — explicit composer chips Ask · Remember · Task · Services · Reviews · Talk (2026-06-16). Brain + mobile shipped, deep-reviewed, a 6-agent adversarial workflow, then an external (Codex) review round (P1–P3) all fixed. Verified live on iOS (iPhone 17 Pro) + Android (Pixel 10). Brain reasoning+composition+ask+chat 829 pass / 15 skipped; mobile composer_modes 14 + hooks 17; tsc + eslint clean.

Decisions / invariants
  • Services forces ['provider_services'], Reviews forces ['peerlens'] — ENFORCED, not advisory: system-prompt lane block + tool-policy allowlist (ToolRegistry.subset) + post-loop result-validation gate. Ask stays classifier-smart.
  • A mode picks the EXTERNAL lane but never disables personal-context enrichment (vault/people tools stay in every lane — §6.6).
  • No prefix leak (§7.1): the user bubble stores CLEAN content + metadata.mode; the slash prefix never reaches stored content. Mobile chip + render logic extracted to a pure, tested src/components/composer_modes.ts.
  • Talk is a contact-picker NAVIGATION (/people?pick=talk), not a text mode (§7.7) — reachable from the chip strip AND (after the Codex round) the mode-switch popover.
  • Single source of truth: reasoning/forced_lane.ts (prompt block + tool allowlist + result gate) shared by BOTH ask paths so they cannot drift; ask_handler.ts re-exports the moved symbols.
External review (Codex) — P1–P3 fixed

Fixed by threading forcedSources through the whole chain + persisting it on the in-memory AskRecord so it survives an approval-resume (applied in both resumer branches). NEW production-bridge test drives the REAL bridge end-to-end (the test that would have caught this — prior tests used a stub handler).
  • P2a: isPeerlensBacked now requires REAL evidence (search results non-empty OR attestationSummary.total > 0), not a present key. P2b/P2c (outage vs absence): the gate distinguishes an OUTAGE (network unreachable → "couldn't reach the review/services network") from ABSENCE (reached, nothing → no-result); search_peerlens sets a failed flag on an AppView throw.
  • P2d: Talk re-entry used a mount-once ref that never reset → replaced with useFocusEffect (every Talk entry re-forces Contacts; a manual tab switch isn't yanked). P2e: Talk row added to the mode-switch popover (reachable once a mode is active). P3: a bare /services//reviews no longer persists an empty user bubble.
Deviations (honest)

  • The chip strip is a small RN ScrollView that Maestro's swipe can't drive (only OS-level idb/adb can; Talk is clipped past the strip's right edge at rest) → hybrid runner maestro/run_composer_modes.sh (Maestro asserts chips + Task-gating; idb/adb scrolls + taps Talk; Maestro asserts the picker hint).
