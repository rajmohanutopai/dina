Dina Plugin Architecture — Implementation Notes

Running notes for the active goal: implement docs/PLUGIN_ARCHITECTURE.md. Captures design decisions, deviations, tradeoffs, and open questions as the build proceeds. (Supersedes the prior E2E-testing notes that lived in this file — those are in git history.)

Scope read of the spec

The spec is phased P0–P3 (§20). This build implements P0 — the substrate + runner mode end-to-end first: it is the phase the spec itself marks as the trust foundation ("prove the box"), and every later phase layers on its primitives. Interpreted mode + sessions (P1), distribution (P2), and ingest/notify/hosted (P3) are explicitly OUT of this pass except where a P0 artifact must carry their shape from day one (the spec pins lexicons, digests, and the workflow state machine as freeze-with-P0 items, so those are built to the full spec now even though their consumers arrive later).

PLG-1 — protocol plugin layer DONE

packages/protocol/src/plugins/{types,normalize,validate,digests,release_rkey,verifier}.ts · __tests__/plugins.test.ts (52) + __tests__/plugin_vectors.test.ts · conformance/vectors/plugin_digests.json + plugin_release_rkey.json (frozen, wired into the conformance CLI)

Design decisions (spec was ambiguous)

  • Hashing is caller-injected (Sha256Fn), following the package’s existing verify_record.ts convention: protocol owns the SHAPE of the digest flow, runtimes own the crypto. Keeps the zero-runtime-deps gate (dep_hygiene.test.ts) intact.
  • Manifest-level consent fields fold into every capability’s scope hash. §8.1 lists config_schema, execution mode, and runtime identity as consent-relevant but they are manifest-level; I fold them into each per-capability digest so a config_schema or issuer change re-consents the whole install — which is the spec’s stated intent (“a new field asking the owner for more input is consent-relevant”; “a new issuer is a new party”).
  • installScopeHash = SHA-256 over the sorted (capability_id, scope_hash) pairs — one comparison answers “did anything change” while grants still key on the per-capability hash.
  • behavior_hash covers initial/states/terminal too, not only the spec’s “transitions, turn rules, timeouts” headline list — all of it is machine wiring (“everything machine-behavioral that consent excludes”), and leaving states out would let a rewire hide behind a rename of an unreferenced state.
  • Set-normalization extends to required_features and advisory affected_cids beyond §8.1’s six named fields — same set semantics, same reorder-must-not-move-hashes argument.
  • Caps the spec left unnumbered (spec: “capped + sanitized”): MAX_CAPABILITIES=32, MAX_INTENT_PHRASES=8, MAX_PHRASE_LENGTH=80, MAX_CONTEXT_ITEMS=25, MAX_NETWORK_DOMAINS=16, display 64 / description 400 chars; verify_budget ceiling 8 (spec §21 open decision 4’s proposal). All in one frozen PLUGIN_CAPS table.
  • Ops-library names frozen as commit, verifyCommit, sharedRng, compare, tally, counter, timeoutAssert, verifyFact (§10.2 named them descriptively; the identifiers are now the contract).
  • CID parsing is deliberately narrow: CIDv1 + multibase b + dag-cbor + sha2-256 only, single-byte varints (which that shape guarantees). Anything else → null, closed-default. ATProto records are exactly this shape; wider parsing only widens the forgery surface.
  • Trust anchors (§12) are a typed union on the verifier contract — repo_proof | org_key | local_publisher_key | debug_unsigned — so “private ≠ unsigned” is a type, not a comment.

Deviations (intentional departures)

  • $ref is banned entirely, not just “recursive $ref” (§5 rule 4). Plugin schemas are small by design; $ref indirection buys nothing but a recursion vector, and a flat ban means there is no cycle detector to get wrong. Documented in hasRecursiveRef.
  • The validator REQUIRES pre-normalized input (not_normalized rejection) instead of normalizing internally. Rationale: §8.1 says the normalized form is the STORED form; a validator that silently normalizes would let a caller store the un-normalized original and hash a different representation than runs. Failing loud makes “hash form == runtime form” structural.

Tradeoffs (alternatives considered)

  • Anti-Her ban check = exact category match + substring match on the capability id. The substring side can false-positive (a legit id containing “romantic”); chose conservative — a rejected honest manifest can rename, a slipped hostile one cannot be un-consented.
  • Secret-field detection (§5 rule 6) = structural (format: password, writeOnly) + name-pattern heuristic. A hostile manifest can mislabel; the spec’s own second layer (paste-pattern warnings on the consent form) covers that, so the validator stays a floor, not a promise.
  • Manifest byte cap uses caller-supplied rawByteLength (the honest fetched-bytes number) with a JSON.stringify UTF-8 fallback — good enough to stop schema bombs when a caller forgets, correct when they don’t.
  • Vectors registered in the existing conformance machinery (index.json + suite.ts verifiers + CLI counts) rather than a parallel plugin-only harness — the no-orphans gate and exit-code contract now cover them for free. Cost: two frozen-count test bumps (10→12), which those tests self-document as the procedure.

Open questions

  • Interpreted + query capabilities (Tier-1-style, no session): the validator currently ties ops_used/verify_budget validation to interaction: session. If P1 wants interpreted query capabilities, that block needs widening. Spec §5 shows the field comment “interpreted + session only” so I matched it — confirm.
  • Unnumbered caps: MAX_CAPABILITIES=32 / phrase 8×80 / context-items 25 / domains 16 — numbers are mine; the spec pins only the §5 rule 4 table. Tunable, existence non-negotiable.
  • icon blob is typed unknown and not validated protocol-side (AppView’s ingest owns blob validation). Confirm that split.

PLG-2 — workflow hardening DONE

packages/core/src/workflow/{domain,repository,plugin_envelope}.ts · storage/schemas.ts migration v17 · __tests__/workflow/plugin_hardening.test.ts (34, dual-store) + domain.test.ts updates

Design decisions

  • Claim tokens are universal; strictness is caller-opt-in. EVERY claim now mints a claim_id and advances attempt (columns, migration v17), but the CAS guard on heartbeat/progress/complete/fail fires only when the caller PRESENTS a token. Legacy dina-agent daemons predate tokens and keep the state+ownership guard; the plugin route layer (PLG-6) REQUIRES the token. This avoids breaking every deployed agent while making the strict path structural for plugins.
  • The envelope pins its own classification inputs. action_class + effects_idempotency ride in the payload (like schema_snapshot), so the lease sweeper and cancel path classify without a registry lookup — the task is its own frozen authority.
  • One shared classifyLeaseLoss decision table drives both stores, so SQLite and in-memory cannot diverge on the §9.1/§9.5 semantics. The whole test matrix runs against BOTH engines (the outbox_repository dual-store pattern) for the same reason.
  • Backoff rides next_run_at. The claim SQL gains (next_run_at IS NULL OR next_run_at = 0 OR next_run_at <= now) — semantically "don’t run before its scheduled time", which gives exponential retry backoff for free. Behavior change worth knowing: queued delegations now RESPECT next_run_at (nothing set it on delegations before; full suite green).
  • late_report events are needs_delivery=false. Evidence surfaces through the decision/Activity log, never the result pipeline — the §14 "never applied, never hidden" split expressed as a delivery flag.
  • Migration v17 rebuilds the idempotency partial index to exclude outcome_unknown: a §9.5 reconciliation re-dispatch (same idempotency_key, new task) must not collide with the parked row. All 7 inline terminal-state SQL lists collapsed into ONE TERMINAL_STATES_SQL constant.

Deviations

  • Retry backoff is per-sweep, not per-verb: the spec’s "exponential backoff" is implemented at requeue time (next_run_at = now + base·2^(attempt-1)). Constants in PLUGIN_RETRY (3 / 24h / 30s base) — §21 open decision 11 says they need empirical tuning.
  • expireTasks became per-row (was one blanket UPDATE): §9.5 requires deadline expiry MID-RUN on a declared-effectful plugin task to park as outcome_unknown while everything else keeps failed(‘expired’). Queued plugin tasks that expire stay plain failed — never executed, no mystery.

Open questions

  • Honest completion retry: a runner re-posting its OWN completion after a network blip currently gets CAS-miss + a late_report evidence row (the task is already terminal). The route layer (PLG-6/8) should answer idempotently (200 with the stored result) by checking task state on a 0 return — flagging so it lands there.
  • Reconciliation UI actions (§9.5: confirmed-happened / confirmed-didn’t / unresolved) are decision-log writes — they land with PLG-4’s plugin_decisions table.

Iteration record

What changed: outcome_unknown state + transitions (running-only entry, terminal); migration v17 (claim_id / attempt / first_claimed_at + index rebuild); claim mints tokens; CAS-guarded verbs with late_report evidence; markOutcomeUnknown; lease-loss classifier (legacy requeue / bounded idempotent retry with backoff / effectful→outcome_unknown / read→failed); cancel + TTL-expiry mid-run special cases; plugin_envelope module (parse + classify + retry budget).

What the tests showed: new dual-store suite 34/34; whole core package green — 263 suites / 4837 tests — so the state-machine extension broke none of the existing service, sweeper, bridge, or route flows. Two domain-test pins updated (state list + running transitions), which the tests themselves document as the procedure for a deliberate state-machine change.

Deep review findings (fixed): (1) my first domain edit created a DUPLICATE running: key in the transitions object (last-wins would have nuked the real list) — caught on self-review before tests, rewritten as an edit to the original entry; (2) cancel special-case had a TOCTOU hole: if the task left running between the read and the outcome_unknown CAS, the owner’s cancel was silently DROPPED — now falls through to the generic cancel, correct in every interleaving, both stores.

PLG-3 — plugin identity + authz DONE

devices/registry.ts · routes/pair.ts · auth/{caller_type,middleware,authz}.ts · __tests__/auth/plugin_caller.test.ts (pinning + matrix sweep) · full core suite green (263 suites)

Design decisions

  • Suffix-aware authz rules. The §9.0 verbs live at /v1/workflow/tasks/:id/<verb>; pure prefix matching cannot carve them from the wider sub-tree, so rules gained optional suffix — listed BEFORE the generic sub-tree rule (first-match-wins). The plugin surface is exactly claim + 4 verbs + healthz; create/list/get/approve/cancel/running fall through to the generic rule, which excludes plugin.
  • Method-aware rules (deep-review find, fixed before landing): without a method gate, GET /v1/workflow/tasks/complete — the get-single-task route with a task id literally named "complete" — matched the suffix rule and leaked read access. The verbs are POST-only; the rule now says so.
  • Explicit role→callerType mapping. role='plugin' resolves to callerType 'plugin' in resolveCallerType; the spec-mandated pinning test asserts it NEVER resolves to 'device' (privilege escalation by default-case). Both unions — resolution (caller_type.ts) and authorization (authz.ts) — changed together, plus the middleware’s mapToAuthzRole bridge between them.
  • getAuthorizationMatrix keys became composite (prefix*suffix [METHOD]) so the diagnostic view stays lossless — five rules share the tasks prefix and last-write-wins was silently collapsing them.

Open questions

  • /v1/workflow/tasks/:id/running is the Python daemon’s post-claim echo; §9.0 says "nothing else", so plugin is DENIED there and the TS plugin SDK will not use it. If a port needs it, that is a spec §9.0 row, not a quiet matrix edit.

PLG-4 — dynamic registry DONE

migration v18 · src/plugins/{registry,grants,decisions,index}.ts · wired into core-server + mobile storage init · __tests__/plugins/registry.test.ts (18, real SQLite engine)

Design decisions

  • install_id (`pli_<hex>`) is the anchor; identity is indexed, NOT unique — two installs of one (publisherDid, plugin_id) verified by test. Version state (current_cid) swaps in place via applyUpdate; grants/config/vault stay anchored (§6: "structurally cannot orphan").
  • Grant consumption is per LOGICAL EXECUTION. plugin_grant_uses PK (grant_id, execution_id): the atomic check-and-consume inserts inside the same transaction as the constraint check, and re-authorizing the SAME execution_id (idempotent lease recovery) returns allowed without a second consume. releaseUse frees provably-never-executed reservations.
  • Creation-time guards: unconstrained standing for booking/write/agentic throws (§8 — the card never offers it, and the store won’t accept it either); malformed constraints or above-ceiling counts throw — a grant that cannot be enforced must not exist.
  • Fail-closed on stored constraints the node can’t parse (restored archive from a newer node): denial reason constraints_unparseable, verified by injecting a version-99 object.
  • Missing dispatch metadata fails toward denial: a resources-constrained grant with no resource tag on the dispatch denies (resource_not_allowed); a value-capped grant with no declared value denies (value_exceeds_cap). Absence of evidence is not a wildcard.
  • plugin_capability_stats table carries first-N counters for PLG-5’s gatekeeper.

Deviations

  • Constraint vocabulary v1 = {max_count, resources, max_value}. The spec also names a "time window" — expressed here as expires_at on the grant row (grant_type window), not a constraint key: one expiry mechanism instead of two competing ones.
  • Explicit cascade instead of FK cascade (deep-review find): NodeSQLiteAdapter does not enable PRAGMA foreign_keys, so the schema’s ON DELETE CASCADE never fires — remove()/sweep delete grants + uses + stats transactionally. Decision-log rows survive uninstall: records of the past, not authority (§14).
  • SQL CHECK gotcha fixed pre-landing: x IN (NULL, ...) is a NO-OP check (NULL member ⇒ NULL result ⇒ CHECK passes for any value) — rewritten as IS NULL OR IN (...).

Iteration record

What changed: migration v18 (4 tables), 3 repositories + singleton accessors, core barrels, storage-init wiring in core-server + mobile (incl. teardown resets).

What the tests showed: 18/18 on the real better-sqlite3-multiple-ciphers engine; workspace composite typecheck green (both apps compile with the new wiring); full core suite green after PLG-3.

PLG-5 · PLG-6 · PLG-7 · PLG-8 — gatekeeper, claim guard, install, tool lane DONE

gatekeeper/intent.ts (evaluatePluginIntent) · plugins/{claim_guard,install_service,dispatch,schema_validate}.ts · routes/workflow.ts (plugin claim branch + claim tokens) · workflow/service.ts (claimId plumbing) · repository.ts (exact-match plugin lanes) · __tests__/gatekeeper/plugin_intent.test.ts (24), __tests__/plugins/{claim_guard,install_service,dispatch}.test.ts (14+14+21). Full core suite 263 suites green.

Design decisions

  • evaluatePluginIntent returns a mode (silent/card/blocked) on top of the risk level, and the doc-comment states loudly that silent is NECESSARY not SUFFICIENT — dispatch.ts is where "only if params clear egress" (§11.5) actually gates. BRAIN_DENIED is checked on the capability id’s terminal segment AND the action_class, before any floor math.
  • Exact-match plugin lanes in BOTH stores. The claim SQL’s back-compat "named filter also takes untagged tasks" clause was exactly the §9.1 hazard (a plugin claiming generic agent work); plugin lanes now join dina.local as exact-only, and a generic agent (empty filter) additionally excludes any plugin:% lane. Both the SQL and in-memory paths, verified by the dual-store nature of the claim-guard test driving real routes.
  • The claim guard drains stale-authority rows (bounded to 8/claim) rather than returning the first dead row: checks 5/6 TERMINALIZE via the claim’s own claim_id CAS (atomic — no other claimer can race), so a valid task queued behind a stale one is still reachable and the claim loop never spins on a dead oldest row.
  • Verifier is an injected seam (setRepoProofVerifier) matching the @dina/protocol RepoProofVerifier contract; install FAILS CLOSED when none is wired (no TOFU, §5 rule 5). The pure halves — rkey==f(cid) and manifest validation — run regardless.
  • Compatibility gate is real (§14): NODE_SUPPORTED_FEATURES = P0’s {kind.tool, config, idempotent_retry}; derived (∪ declared) ⊄ supported → needs_newer_dina. An interpreted (session + op.*) or notify/provider manifest is correctly REFUSED on this P0 node — the test asserts interpreted-mode install returns needs_newer_dina, which is exactly right: interpreted is P1.
  • Minimal pinned-schema validator (schema_validate.ts): the manifest validator already bans $ref + caps depth, so results validate against a bounded, non-recursive subset (type/properties/required/items/ enum/bounds/additionalProperties). Unknown type keyword FAILS CLOSED — a result we cannot check is a result we reject. No ajv: a small auditable surface at the trust boundary beats full coverage.
  • params-are-egress (§11.5): regulated PII (card/SSN/bank/Aadhaar/PAN/IFSC/UPI) OR an out-of-scope category makes the invocation card, whatever the floor; the owner sees the SCRUBBED text (never the raw PAN). An unclassified param category is treated as out-of-scope — fail toward the card.

Deviations / boundaries

  • Scope of PLG-8 is the Core-enforced invariants: dispatch decision, envelope assembly, params-egress, pinned-schema result validation. The brain-side context PROJECTION (Dina-owned templates, §11.3) and the mobile InlinePluginApprovalCard UI are larger P1/P2 surfaces deliberately left for their phases — Core owns every security invariant here; the SDK/UI make honest behavior easy.
  • claim tokens are REQUIRED for plugin callers, optional for legacy agents: the route’s extractClaimId 400s a plugin without a claim_id but lets agents omit it (they predate tokens). The old private failTask helper was inlined into the fail route so the claim_id threads through.

Open questions

  • Honest completion retry (carried from PLG-2): a plugin re-posting its own completion after a network blip gets a 409 + late_report. The route could answer idempotently (200 + stored result) on a CAS miss where the task is already completed by the SAME execution — a small refinement for the SDK’s retry loop, flagged not built.
  • data_scope categories on the claim guard: check 3 uses the capability-hash map as the consent record (presence = consented). The finer per-category egress intersection (§11.2 inner gate) lives in dispatch.ts’s consentedCategories input; wiring the two into one enforcement call is a P1 integration task once the brain-side projection exists.

What happened

The audit workflow spawned 9 dimension reviewers, each cross-checking the implementation against the spec, with every finding routed to an adversarial verifier. The account hit its session token limit mid-run — 17 of 18 agents errored with "session limit resets 2:50pm", so the workflow’s confirmed: [] is an ABORTED result, NOT a clean pass. Only the D7-install reviewer completed. Its findings survived in the failed verify-agents’ labels (which encode the file:line claims), and one D6-egress verifier had written a repro test file before dying. I verified each claim against the code myself (I had the context the killed verifiers couldn’t reach) and fixed the real ones.

Real bugs the (partial) audit found — all FIXED

  • [install] Blind cast crash vector. proof.record as PluginManifest fed a verifier’s unknown record straight into normalizePluginManifest, which throws on .capabilities.map for a non-object — a CRASH, not fail-closed. Added an isManifestShaped guard → validation_failed.
  • [install] Unsigned soft-path. beginInstall refused debug_unsigned in production but the publicly-exported beginInstallVerified did NOT — a caller could route an unsigned manifest around the §20 refusal. Added an explicit allowUnsigned flag (debug builds only; never derived from request data).
  • [install] Anchor-kind mislabeling. beginInstall ran the repo-proof verifier for ALL anchor kinds, so an org_key/local_publisher_key anchor got repo-proof-verified and then stored claiming a different authority. P0 supports only repo_proof; the others now fail closed until each gets its own verifier.
  • [install] Activation TOCTOU. confirmConsent activated without checking pendingExpiresAt — between sweeper ticks an EXPIRED pending could resurrect abandoned consent. Now refused.
  • [egress/schema] additionalProperties:false bypass via prototype names. The schema validator used the in operator, which walks the prototype chain, so a result {"status":"watching","toString":"http://evil"} (or constructor/valueOf/ __proto__) slipped past the pin — JSON.parse produces own-enumerable keys for exactly those names. Switched every membership test to hasOwnProperty. This is the sharpest catch: a plugin could smuggle arbitrary extra fields (tracking pixels, exfil URLs) past a consented result schema.
  • [egress] Empty-category silent run. assessParamsEgress cleared egress when the classifier returned an EMPTY category list, even for non-empty sensitive params (“stuff about my depression”) — contradicting its own “unclassified → out-of-scope” doc. Now non-empty-text + empty-categories fails toward the card (genuinely empty params still clear).

Not-a-bug / moot-for-P0 (assessed + skipped): multi-install not consulting listByIdentity (by design); interpreted query-cap feature derivation (interpreted is refused by the P0 compatibility gate anyway); manifest byte-cap using the JSON.stringify fallback rather than fetched bytes (the fallback is correct; threading raw bytes needs a protocol-shape change, noted for later).

PLG-9 (cont.) — lean re-audit of the security-critical dimensions DONE

4-agent review-only Workflow (claim-CAS, claim-guard, gatekeeper, grants) — completed cleanly this time (4/4, 0 errors, 310k tokens) — findings self-verified against the code and fixed

What the lean audit found — all VERIFIED and FIXED

  • [CRITICAL — claim-guard] Plugin-lane hijack by a generic agent. A caller with callerType='agent' that named plugin:<install_id> in runner_filter skipped the plugin branch (which only fires for callerType='plugin'); the claim route rejected only dina.local, not plugin:*, so it fell through to the generic claim path where an exact-match plugin filter let the AGENT claim the plugin-lane task — reading the pinned envelope (params + scrubbed context) and forging a completion with NONE of the six checks, no result-schema validation, and no claim token. Fixed: the claim route now 403s any plugin-lane runner_filter from a non-plugin caller — plugin lanes are reachable ONLY through the plugin branch that forces the lane from the install.
  • [HIGH — grants] Unbounded HIGH grant via non-standing type. The "no unconstrained standing for booking/write/agentic" guard keyed strictly on grantType==='standing', so a 'window' grant with no expiry (or a 'once' grant with nothing enforcing once-ness) authorized a HIGH capability unbounded forever. Fixed: a HIGH grant must be bounded some way (once / expiry / meaningful constraint); a 'window' grant must carry an expiry; and 'once' is now enforced as an implicit max_count=1 at consume (same execution re-auth still free).
  • [MEDIUM — gatekeeper] maxRisk non-monotone on garbage declared risk. An out-of-enum declaredRisk made maxRisk return the garbage string (n >= undefined is always false), LOWERING a HIGH floor to an invalid level that could run silent. Fixed: maxRisk ranks unknowns as BLOCKED, and the call site coerces an unrecognized declared risk to BLOCKED — a hint we can't understand fails toward blocked, never toward silent.
  • [MEDIUM — grants] max_value had no ceiling. A "constrained" grant could carry max_value: 1e18 — theater. Added MAX_VALUE_CEILING (1e12; the unit is plugin-defined so it only rejects the absurd).
