Design decisions and spec interpretations

  • Separate package (§6 topology): commerce protocol versions independently of the core wire protocol; same conventions (nullable-error validators, injected Sha256Fn, frozen vectors, dep-hygiene gate — src/ imports relative paths only). canonicalJson is a deliberate copy of @dina/protocol's JCS subset; frozen vectors on both sides turn copy drift into a test failure.
  • §9.1 "exact under the declared unit conversion" read as: the CONVERSION must be exact (kg/g, l/ml, same-code); the quantity/priceBasis ratio may be fractional — the integer-quotient reading would falsify the spec's own "per-unit pricing always does" clause. Case↔each is refused, never guessed.
  • Choices the spec left open (flagged below for confirmation): unit vocabulary v1 = each/case/pallet/g/kg/ml/l, custom unit codes rejected; bounds = 15-digit minor units / 12-digit quantity integers; currency validated as shape only (no ISO table pin); termsDigest input = charges + estimates + paymentTerms + validUntil; reasonCode = open bounded snake_case vocabulary; timestamps = canonical ISO UTC (Z, fraction absent or 3 digits); totals reject an intermediate-negative running sum.
  • Deviation from house export policy: operational commerce tables (heads, counters, order refs, watermarks) ARE exported — §16.2 requires it; restoring receipts without them would reset counters or fork heads. The stale-backup residual is fenced by the commerce epoch, not by exclusion.
  • Partial quotes are legal (a quote need not answer every request line, §19); all-or-none binds ORDERS to quotes. Genesis status state is DERIVED from the recorded acknowledgement — callers cannot claim a different resolving event.
  • host_operations enters the scope hash only when non-empty, so every pre-commerce manifest and frozen digest vector keeps its hash while widening still forces re-consent (absent == empty == no brokered authority).

Owner decisions (both previously blocking, now settled)

  1. Post-restore quote capacity (X-10). §16.2 says admission against a restore-voided quote returns quote_superseded with “a freshly signed head at the new epoch”, and separately that “capacity is never resurrected from a backup”. It never says what capacity that fresh head carries — and that is a money question. Decision: Core never synthesizes a replacement. It holds no commercial authority (Kernel-not-Platform), and it cannot know how much of the original allowance was really consumed: the backup’s use counter is precisely the number a stale restore makes untrustworthy. A supplier-side seam owns the re-offer. With no seam wired, admission refuses with quote_voided and no digest — naming the voided head would have the buyer re-approve forever against something that can never go live again. This is a deliberate, recorded deviation from the spec’s literal wording: the spec asks Core to do something Core is not permitted to do.
  2. Scope of this pass. The two reviewers read §24 oppositely — a genuine specification ambiguity, not reviewer error. Decision: the broad reading. This pass owes the extension-operation broker, the provider installer journey, the update-rebind coordinator and validated archive restore, alongside the Phase 0 spine and the §23 Core work. Both reviewers now share this as a frozen rubric, which removed the four-item disagreement in round 3.

Owner decisions, 2026-08-07 (binding)

  1. Wire version. 1.x is explicitly unfrozen until the §24 Phase 0 exit criterion is met; it then freezes at 1.0. The HeldEvidence change was incompatible, but nothing is deployed and no external peer exists, so burning a major on pre-release churn buys nothing — and further Phase 0 changes are expected (units, catalog records, missing vectors). Consequence: no conformance claim may be made, and no third party may target the wire, until that note is lifted. This must be stated in packages/protocol/docs/conformance.md, not only here.
  2. Quotes do not reserve stock (spec §27 Q6, now closed). max_uses caps how many orders a quote family admits; real inventory stays supplier/ERP authority. Core cannot honour or verify a stock reservation, and modelling one would put a commercial commitment inside the kernel. This confirms the built semantics — recorded so a later reader does not mistake capacity for inventory.
  3. Unit vocabulary v1 is a closed list; custom units are rejected (spec §27 Q4, now closed). Widening after the freeze is additive and safe; a permissive v1 cannot be narrowed without breaking peers. Supplier-declared units with conversion evidence were rejected because two implementations can disagree on a conversion, which breaks the byte-identical arithmetic §9.1 depends on.
  4. Archive carries operational tables as EVIDENCE; restore never adopts their counters. §16.2 requires quote/status heads and use counters in the archive, while the house posture treats them as live authority — a genuine contradiction. Resolution: export them so an archive is a complete record, and make the restore ceremony always void capacity and re-fence chains rather than trusting restored counters. Consequence: the WS-4.2 preflight no longer has to establish that counters are trustworthy — only that the archive is intact and authentic. Capacity and chain state are re-derived every time. This is both smaller and safer than the spec-faithful reading, and it removes the "validated counters" failure mode entirely.

Architecture decision — why a refactor, not more patches

Four review rounds kept finding second-order breaks: a correct, tested fix in one place broke a rule enforced in another. Twice the damage came from my own remediation — the §11.2 ownership gate silently disabled §16.2 disaster recovery, and persisting valid_until supplied the last ingredient for reviving an expired pre-backup quote family. That is not bad luck four times; it is a structural signal.

The smells, measured:

ruleplaces enforcing itowner
“capacity is never resurrected from a backup”4+none
“does this order exist”14 call sitesnone
“wire records are snake_case”12 as castsconvention

Named: shotgun surgery (one idea, many edit sites — the cost of a change tracks how many sites you remember, and I remembered three of four); anemic domain model (rows plus discipline, so a quote family cannot refuse an illegal operation because it is not a thing); lying casts (the compiler told not to look at exactly the boundary that needed checking); and a non-exhaustive switch over parsed JSON (the type system asserting a fact about untrusted data). The tests were the only net holding these together, and seven of them turned out to hold nothing.

Recorded because I got the reasoning wrong first: I declined the deeper fix partly because it was a day’s work and would invalidate four review rounds. Neither is a reason. Reviews are cheap to re-run; wrong structure is not cheap to live with. The only legitimate constraint is avoiding rigidity.

Agreed design (refined against a Codex review of the proposal)

Plain validated data crosses boundaries. Pure domain aggregates own local state rules. Transactional application services coordinate cross-aggregate changes. Raw persistence primitives are not available to production callers.

Four corrections to my first proposal, all accepted:

  • Uniqueness across (buyer_did, purchase_order_id) and (buyer_did, idempotency_key) is a database invariant. One CommerceOrder cannot own a rule about all orders.
  • Deciding an order and settling its quote hold spans two aggregates plus receipts. It belongs to a transactional application service, not to CommerceOrder — my version would have pushed quote knowledge into the order.
  • Typed results, not throws, for business outcomes. Expired, consumed, superseded and illegal-transition are normal results that travel to the buyer as wire reason_codes. Corruption and impossible state (a failed settlement inside a committed decision; a head row whose receipt is missing) throw and roll back. Conflating the two is arguably what produced the ignored settleUse boolean.
  • Hiding the repositories is the whole point. QuoteFamily.advance() is worthless while casAdvanceHead() stays callable — the next call site simply bypasses it. Success is measured by a grep returning empty, not by a passing test.

One discipline added on top: application services coordinate and persist, and must not re-derive aggregate rules. A service that re-checks epoch or capacity “to be safe” has scattered the rule again and become a god-object with extra steps.

Wire types stay plain serialisable data with validators — they are hashed byte-exactly, frozen in conformance vectors, and must be reproducible by a Go/Rust/Swift port. Turning them into classes would fight both. No unit-of-work ceremony over the existing synchronous DatabaseAdapter and explicit TxRunner: that is rigidity, not correctness.

ARCH-0a — QuoteFamily aggregate, quote ledger hidden (done)

packages/core/src/commerce/quote_family.ts. The supplier-side quote family is now an object that refuses illegal operations, and CommerceQuoteLedgerRepository is no longer reachable from any production caller. Three engines took the store instead: admission, epoch, lifecycle.

Decisions worth knowing:

  • Refusals are values; corruption throws. Expired, consumed, superseded, voided, stale-epoch and duplicate are ordinary outcomes that become wire reason_codes, so they are returned. A settlement CAS that cannot fail failing, or a head row that will not read back after being written, throws — those mean the ledger and the order references disagree, and committing half a decision is worse than aborting.
  • The aggregate does not re-check the protocol verifier. Revision numbering, audience, request binding, in-chain epoch regression and immutable max_uses belong to verifyQuoteRevisionExtends. My first version re-implemented two of them locally — the same scattering, one layer down — and answered with a vaguer message than the real one. It now calls the verifier and carries its sentence through in a detail field. Only one rule is the aggregate's alone: epoch monotonicity, which compares the head to Core's restore history and is invisible to a verifier that only sees two revisions.
  • detail is operator text, never wire text. The buyer-facing reason_code is derived from the refusal name alone, through a total Record<QuoteRefusal, string> — so a new refusal cannot reach a counterparty unhandled. stale_epoch maps to quote_voided: to the buyer they mean the same thing, this family is gone.
  • Duplicate is decided before capacity. Capacity-first told a caller retrying its own order that the quote was consumed — by the caller's own hold.
  • hold() checks expiry itself rather than trusting that admits() ran first. An aggregate whose rules only hold when methods are called in the right order is the discipline this refactor exists to remove. It judges against the head's window, which the family keeps current; admits() judges the record the order names, which may be an honoured superseded revision with a different deadline.
  • An instance is a one-transaction snapshot of the head row. Stated in the class doc because nothing in the type system says so.

Debt this leaves, recorded rather than hidden: the restore sweep still calls voidUnexpired, which by construction cannot see an already-expired family. It is kept because the restore is an event that must leave a receipt with a real count — the fence itself is now epoch monotonicity, which needs no sweep and cannot miss a row.

Verification: nine mutations, each asserting its anchor exists before removing it — a silent no-op mutation reads as a passing suite. All nine went red. Two (stale_epoch at admission, settlement rollback) were caught only by the aggregate's own unit tests until cross-layer tests were added; both now fail in two suites. Grep confirms no production file outside the aggregate names registerHead, casAdvanceHead, holdUse, settleUse, voidUnexpired or activeUseCount. Gate: tsc clean, eslint clean, core 6,271 passing.

Two false-green tests were caught during this item. The first asserted the validity window advanced with the head without ever reading it — fixed by exposing validUntil and asserting it. The second asserted duplicate_use on a single-use quote, where capacity is exhausted by the first hold, so the refusal it named was unreachable.

WS-0.3 — StatusChain aggregate (done)

packages/core/src/commerce/status_chain.ts. Chain CREATION, ADVANCEMENT and FENCING are now three operations on one object, and CommerceStatusHeadRepository is unreachable from production. Each operation carries its own restore prerequisite: create refuses when the ORDER predates the epoch, advance refuses when the HEAD does, and fence requires a higher epoch because fencing is how a restored chain rejoins.

The rule this closes escaped three times. Missing from signStatusUpdate; then missing from signStatusUpdateInTx once added to the first; then, shared as a predicate, unable to express chain creation at all — the predicate takes a head epoch, and at genesis there is no head. That last one is worth stating plainly, because I got it wrong myself and published a table asserting genesis was safe: the state that matters after a restore is the BUYER's copy, not the local row. A restored supplier whose head row was lost signs a second sequence-0 record, the buyer holds two, and the fence cannot repair it — unavailable before a genesis, blocked afterwards by the fork check. Local absence is the restore symptom, never proof of safety.

Design decision: two bars, not one. Re-adoption first stamped the order with previousEpoch(current) to make creation refuse. A test caught that as a no-op at epoch 1, where there is no lower epoch — the sentinel only worked from epoch 2. That was a workaround wearing a rule's clothes. "Was re-adopted from a counterparty's evidence" and "belongs to an older generation" are different facts, so they are now a boolean (reconciliation_required) and an epoch (admitted_epoch) with separate refusals. The flag holds at every epoch.

Duplicate removed rather than tested. The aggregate also re-checked "a fence needs a strictly higher epoch". Mutation showed deleting it changed nothing, because setFence enforces that itself in both implementations and the interface documents it as the STORE's guard. Re-checking a rule that already has an owner is the same scattering this aggregate exists to end, pointed one layer down. Deleted, with the reasoning recorded in place so it does not come back.

Tests: 157 commerce, 6,298 core. Mutations — genesis restore gate (4 red), advance restore gate (4), transition legality (2), re-adoption bar (2), re-adoption stamp (2). All caught.

Process failure worth recording: a greedy multi-line regex intended to delete one 15-line method matched from the first /** in the file and deleted 965 lines of lifecycle_engine.ts. Restored from the commit and re-applied the migration as 15 exact-string edits, each asserting a unique match. This is the fourth loose-anchor incident in this work and the first destructive one. WS-0.2 — CommerceOrder aggregate + §12.8 atomicity (partial)

packages/core/src/commerce/commerce_order.ts. The order owns its own lifecycle (reserved → decided, pre_effect → effect_started), whether a transition is legal now, and what a replay answers.

What it deliberately does NOT own. Uniqueness across (buyer_did, purchase_order_id) and (buyer_did, idempotency_key) stays in the repository: one order cannot enforce a rule about all orders, and the unique indexes already do. Nothing about the quote lives here either — deciding an order AND settling its capacity hold spans two aggregates, so it is coordinated, not absorbed. Pushing quote knowledge into the order is how the two got tangled originally.

§12.8 race closed. Acceptance and its status genesis were two transactions. A cancellation arriving in the gap saw a decided order with no chain and answered refused_policy; the same cancellation a moment later could cancel. The reason code depended on timing rather than on the order. They now commit together: the admission engine takes an injected createAcceptedGenesisInTx, supplied by the composition root so neither engine learns the other's internals, and a genesis failure throws so the acceptance rolls back. An accepted order with no chain — the state the race exploited — is no longer reachable.

Tradeoff, stated plainly. The reviewers asked for an AdmissionService as a separate transactional coordinator. What landed is the atomicity requirement met through a narrow injected seam, with the engines still owning their transactions. The correctness defect is closed and mutation-verified; the file-level extraction is not done. Recorded as WBS 0.2b rather than described as complete.

WS-0.5 — the boundary made real (done)

packages/core/src/commerce/runtime.ts composes the commerce stores once. Production code receives QuoteFamilyStore, StatusChainStore and CommerceOrderStore; the five mutable per-repository globals are gone, and both boot paths install one runtime instead of five raw repositories.

Why this mattered more than it looked. I previously told the owner "the ledger is hidden — grep-verified". That was true of call sites and false of the boundary: the raw repositories were still exported from the package root AND installed into mutable globals, so any future caller could reach past every aggregate rule with no compiler or test failure. A grep proves a fact about today; it says nothing about the design.

The guard is now static, not behavioural. __tests__/commerce/boundary.test.ts asserts over the SOURCE: no production file outside an owner calls a raw mutator, no per-repository globals exist, no engine declares a raw repository dependency, and only the composition root constructs SQLite repositories. Behavioural tests cannot express this — they test what the code does, and the risk here is what a future caller could do. It fails on the commit that reintroduces a bypass rather than on the incident that exploits one.

It immediately found two things I had missed while believing the item was finished: the fifth global (watermarks.ts) was still there, and both engines still declared orderRefs: CommerceOrderRefRepository even though CommerceOrder existed. That is the guard doing exactly the job a grep could not.

WS-0.6 — authorization separated from existence at the ingress gate (done)

The §11.2 gate treated all three order-scoped capabilities identically: prove you own an existing order reference, or be refused. That was right for two of them and broke the third.

The defect, which was mine. order_reconcile exists to resolve outcome_unknown (§12.7/§16.2): the buyer submitted an order and never learned whether it landed. The case that matters most is the one where the supplier holds NO reference — it crashed before the durable write, or restored a backup taken before the order arrived. Requiring an existing reference made exactly that case unanswerable. My own §11.2 remediation silently disabled the disaster recovery it sat next to.

The fix is a distinction, not a bypass. Two capabilities are entitlement-by-possession (order_status, cancel_order): you may ask about an order you own, so the reference IS the proof and absence stays a denial. One is entitlement-by-evidence (order_reconcile): authorization comes from the buyer-bound payload, which must name the authenticated sender, and whether a reference exists is the handler's answer rather than the gate's business.

Why this leaks nothing. A reconcile for someone else's order is keyed on the authenticated sender and also answers never_received, so "no such order" and "not your order" stay indistinguishable — the endpoint is not an existence oracle. That is exactly why the same relaxation would be wrong for order_status, and a test now pins that contrast rather than leaving it as reasoning in a comment.

Tests: 17 ingress, 6,309 core, workspace typecheck clean. Mutations — restoring the reference requirement for reconcile (1 red), dropping the payload buyer binding (2 red), dropping the existence check for status (4 red). All three branches load-bearing.

WS-1 protocol defects — arithmetic order and calendar dates (done)

Totals were order-dependent, which breaks §9.1 interop. computeTotal rejected any INTERMEDIATE negative running value, so subtotal 100, subtract 200, add 500 was refused while the same three charges reordered summed to 400 and passed. §9.1 specifies a plain integer sum, so two conforming implementations iterating a charge set differently must agree — otherwise the byte-identical guarantee is false for any invoice where a discount precedes a surcharge, which is an ordinary shape. Non-negativity is now a property of the RESULT.

The existing test asserted the wrong behaviour and had to be replaced rather than adjusted: it explicitly pinned "order of add/subtract cannot rescue an intermediate negative". A test encoding a non-authoritative interpretation is worse than no test, because it converts a defect into a defended decision.

And then my own fix contained the same smell. I added an explicit final non-negativity check to computeTotal; a mutation showed deleting it changed nothing, because minorUnitsToString already refuses a negative bigint. Removed — re-checking a rule that has an owner is the scattering this refactor exists to end. The test now pins the OWNER's message, so a future duplicate cannot satisfy it while the real guard is deleted.

Frozen vectors, including a rejection. Three new cases: charge_order_discount_first and charge_order_surcharge_first must produce identical totals, plus final_total_negative_is_invalid. The vector runner now handles expected-rejection cases, because a permutation pair is meaningless if an implementation can also accept what this one refuses.

validateIsoUtc accepted impossible dates. Date.parse('2026-02-30T00:00:00Z') succeeds and silently means 2 March. A timestamp that means a different day than it reads is worse than one that is rejected: it is digest-covered, so two implementations disagreeing about whether to normalise produce different bytes for the same input. Now round-trips the parsed instant and refuses a mismatch — with a real leap day (2028-02-29) and a legitimate month end still accepted, so the check is not a blanket refusal.

WS-1.5 — buyer-side quote verification (done)

verifySignedQuoteForBuyer previously bound only the request DIGEST. That proves the supplier SAW the request; it proves nothing about whether the quote's lines correspond to it. A quote could reuse a genuine digest while inventing line ids, misnaming requested_product, or substituting a different exact variant where the buyer said none — and the buyer's Dina would authorise the wrong goods against a quote that verified cleanly.

Five bindings added, each mutation-verified: expiry against a canonical acceptance time; request_id agreement; every quoted line must correspond to a requested line (a quote may price a SUBSET, but may not invent); exact product identity by scheme AND value, never name similarity; and substitution authority, which defaults to none and requires substitution_evidence when granted.

Design decision: subset yes, invention no. A supplier that cannot supply every line still gives a usable answer, so a partial quote is legal. What is not legal is a line the buyer never asked for — that is the §20.4 bait-and-switch surface, and it must not rely on the owner noticing by eye.

Context now carries the retained REQUEST, not just its digest. That is a wire-adjacent API change to BuyerQuoteContext, and it is the point: a verifier that cannot see what was asked cannot check that the answer matches. It also carries at_iso, because "is this quote still live" is a question about a moment, and a verifier without a clock silently answers "always".

WS-4.2 — the restore fence had no trigger, and I had just made it reachable (part)

Say the bad part first: my own WS-2.4 change opened this. Before it, nothing installed the epoch service, so currentEpoch() threw and commerce refused everything — a restored node was safe by accident. Installing the epoch service made establish() run on every boot, and establish() ADOPTS the live epoch. A node restored from a backup would come up, adopt the unchanged epoch, and find every restored quote head matching it. The backup's use counters would be live again: capacity already spent, spendable a second time. That is the resurrection §16.2 exists to prevent, and I put the last piece in place for it two items ago.

Why nothing caught it. establishAfterRestore() — which increments the epoch, voids unexpired capacity, and writes the fence receipt — is fully implemented and well tested, and had no caller anywhere. The same shape as the engines and the ingress bridge: correct code, reachable by nobody.

Why a marker rather than a check. Nothing in restored data distinguishes it from data this node wrote itself — that is what a faithful restore MEANS, and the commerce tables are in the archive deliberately (restoring receipts without heads and counters would re-serve quotes against reset counters or re-sign forked heads). The knowledge that a restore happened exists for exactly one moment, inside the import, and has to be written down before it is lost.

Written in the import's OWN transaction. A marker written after the import committed could be lost to a crash in between, leaving resurrected counters with no fence pending — the precise state this prevents, reachable by unlucky timing. Inside the same transaction, restored capacity and the obligation to void it are one atomic fact.

Three deliberate asymmetries. The marker is set unconditionally, with no attempt to detect whether a given archive carried commerce rows: an empty commerce set costs one wasted epoch increment, a missed one lets capacity be spent twice. It is left set when the fence cannot complete, so a node that could not reach its repo retries next boot instead of quietly adopting the live epoch later. And an unreadable kv_store reads as "fence owed" — "no marker found" is the answer that resurrects capacity, and a database we cannot query is not evidence that this node is safe to trade from.

It does not travel. The marker describes THIS node's pending obligation, not the backup's content. Exported, a backup taken while a fence was owed would demand a second fence on a different node for an event that already happened here.

The owner decision says preflight must prove the archive is intact and authentic — row counts, digests, required-table coverage, cross-table invariants — and that is not implemented; restore still trusts the archive's structure. WS-3.4 — the extension-operation broker (part)

The problem §3.4 solves. A plugin runner is untrusted code out of process that must be able to ask for effects only Dina can perform — search the AppView, send a D2D message — without ever holding the authority to perform them. The answer is a four-step protocol, and this is its state machine: propose, permit, execute, verify.

Durable first, because every step boundary is a crash boundary. The proposal is recorded before anything is permitted, so a crash leaves a readable row rather than an intention that evaporated. executing is written BEFORE the effect, so a crash mid-effect is discoverable through listExecuting() instead of being retried into a double send. That is also why outcome_unknown is a first-class terminal state rather than an error: an effect that MAY have happened is a different fact from one that certainly did not, and only the first forbids a retry.

Two orderings that are load-bearing. Deny-before-validation: an operation the capability never declared is refused without consulting the registry or touching params — those params are not input this node should be parsing. And params are validated BEFORE the row exists, because a recorded proposal is something the owner may be asked to permit, and it should never be possible to be asked about params nobody checked.

Schema digests pinned at proposal time. The registry's schemas change when an adapter updates. A proposal permitted under one contract must be verified under that same contract, or an update silently reinterprets a decision the owner already made. A result that violates the pinned schema is recorded failed and the drifted payload never lands.

Refusals are recorded, cancellation is bounded. A silent drop leaves the runner retrying for ever and the owner with no record of a decision they made. A runner may withdraw before a decision but never after execution begins — an effect that may already have happened cannot be un-asked.

PART, and the honest gap is the one this work keeps finding: NOTHING CALLS IT. There is no typed host operation to execute (3.5), no owner-facing permit surface, and no sweeper wired over listExecuting(). I am recording that plainly rather than marking DONE, because "built and unreachable" has been the defect in seven of the eleven items before this one. Verification: 13 tests, 7 mutations, all caught (one of my first mutations was a no-op — an appended comment rather than a behaviour change — and was redone). WS-3.5 — typed host operations (part)

One sentence is the whole rule: the runner supplies the PARAMS, Dina supplies the AUTHORITY. That is enforced structurally rather than by checking — the context an executor receives carries the validated params and the asking install's identity, and has no field for a credential, a session, or a key. A runner cannot smuggle authority through a payload because there is nowhere to put it. Everything an executor needs in order to ACT is closed over at composition time by the boot that owns those things.

A thrown executor settles outcome_unknown, never failed. A socket can die after the bytes have left, so a throw cannot distinguish "never happened" from "happened and the wire died". Calling it failed invites a retry that sends twice. The asymmetry is deliberate and costed: a false "unknown" costs an operator a manual check, a false "failed" costs a duplicate effect. Executors that CAN characterise a failure return failed themselves and stay retryable.

"Bounded" is a security property, not a performance note. An unbounded search lets a runner page an entire index through a channel the owner approved for one lookup. The cap is applied in Core after the search returns, and the request carries no limit field at all — so there is nothing for a runner to widen.

Mutation distinguished a layered pair from dead code, again. The dispatcher's `permitted` pre-check survived deletion, because the broker's own CAS catches the same case. Defeating BOTH lets an unpermitted proposal execute (11 tests red), so they are layered rather than duplicated: the pre-check reports which state blocked it and avoids parsing params for a proposal that cannot run, the CAS makes two concurrent dispatchers resolve to one winner. Kept and documented, where the redundant buyer check in WS-4.3 was deleted — the difference is whether removing both changes behaviour.

One helper, both boots. createPluginHostRuntime builds the broker and the dispatcher already knowing each other, and both storage inits call it where they already composed the operation registry. The alternative — an option each composition root remembers to pass — is precisely how the provider-ingress bridge, the commerce engines, and the epoch service each came to exist with no caller.

Two independent reviewers: a Claude continuity subagent and Codex via the openai-codex plugin. R1 8+17, R2 5+12, R3 7+15, R4 6+15. No version has yet had both PASS.

The counts did not fall monotonically, and the reason matters: R1 reviewed the original code; R2 mostly reviewed the snake_case conversion R1 demanded (1,400 renamed sites); R3 mostly reviewed R2’s fixes and their tests; R4 reviewed the wire change and the round-3 fixes. R4 produced no reviewer disagreements — the first round with none, because the scope ruling above was given to both as a frozen rubric. Four findings were flagged independently by both. Where severities differed the higher was taken.

Test quality was the dominant recurring theme. Seven tests were caught passing for the wrong reason: a missing verifyHeldEvidence default; hand-built acknowledgements rejected before the branch under test; a guarded if that asserted nothing; receipts.put ignoring conflicts so in-place corruption silently no-oped; admission returning reserved with no acknowledgement; an assertion comparing a value to itself; and an unwrapped evidence fixture. Traps worth remembering

  • tsc --noEmit does not typecheck __tests__ in either package. A broken test signature shows up as a silently smaller suite total, never as a red. Watch totals, not failures.
  • Object spreads are never excess-property checked, whatever the target annotation. Only satisfies catches a misspelt wire key inside a conditional spread. Annotating the const achieves nothing — I tried it and the misspelling still compiled.
  • Raw NUL bytes in three source files made grep/rg treat them as binary and skip them silently. Replaced with escapes. Any audit that relies on grep was blind to those files.
  • Edit scripts must anchor on strings that occur once, asserted before mutating. A loose pattern matched the wrong if (head.voided) branch — there are two — and deleted a method.
