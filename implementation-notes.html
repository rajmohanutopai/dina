Service Capability Catalog — Implementation Notes

Spec: docs/SERVICE_CAPABILITY_CATALOG_DESIGN.md (2304 lines — a design + handoff that explicitly asks Claude to validate before implementing (§43, §10) and to ship a curated set, not all 80+ capabilities). This file tracks the validation, the phased plan, and per-iteration progress.

Validation (the spec's §43 primary ask)

Validated

Core architecture is sound — AppView-served curated catalog + @dina/protocol types + mobile cache + bundled fallback. One source of truth across mobile / Brain / AppView; new official capabilities ship without an app release; deprecation/promotion is central. The load-bearing invariant (§43) — official-curated capabilities + namespaced-custom + unknown-flat-rejected, and every listing carries capability + concrete category + explicit discoverability — is correct and enforceable. This is what I'll enforce end-to-end.

Validated — curate, don't dump

The exact 80-capability list is NOT the architecture (spec §43). V1 ships a representative ~13-capability set that exercises every dimension — action_class read/quote/booking, privacy_class public→sensitive, default_discoverability public/unlisted/known_only, and cross-category capabilities. The remaining catalog can be appended later with no app release (the whole point of an AppView-served catalog).

Overlap decisions (spec asked Claude to decide)
  • order_status / package_tracking / delivery_eta — kept separate: merchant order state, carrier package state, and active-delivery ETA are different provider contracts/result schemas (spec §1120 concurs).
  • Food: use generic order_status/delivery_eta + category_id=food rather than minting food_* duplicates, until result semantics genuinely differ. Deferred food_*.
  • appointment_status / appointment_availability / appointment_book — kept as shared cross-category capabilities; the concrete category travels on the provider listing (the spec's core cross-cutting model, §9.1).
  • Over-generic status_query / availability_query (§34) — rejected for V1: they make cards + routing vague (spec §1824). Use specific capabilities.

Design decisions

Decision

Catalog is a NEW protocol module that supersets the existing resolver registry; a consistency test prevents divergence (the §79 "explicit drift test"). Today capability-registry.ts is the sync resolver (classify / canonicalize), byte-duplicated protocol ↔ appview with a drift gate (AppView is a separate build that can't import @dina/protocol at runtime). Rather than rewrite that drift-gated, ingest/search- critical file in one shot, V1 adds capability-catalog.ts as the richer source of truth and a test asserting the catalog is a superset of the registry (every registry canonical appears with identical aliases). Migrating the resolver to be a projection of the catalog (and duplicating the catalog into AppView with its own drift gate) is Phase 3/4 work, scoped so the high-risk ingest path changes deliberately.

Deviation

V1 CapabilityDefinition trims the spec's full field set + makes params_schema/ result_schema optional. The spec's type (§5) is the eventual shape; V1 carries the fields that drive product behavior now (id, aliases, category_ids, default_category_id, display_name, short_description, lifecycle, action_class, privacy_class, default_discoverability, approval_policy_hint, introduced_in) and embeds default schemas only for the 3 launch-backed capabilities (where real demo schemas exist). Catalog entries are a discovery menu; the authoritative schema/hash lives on each provider listing (spec §5.1). Marking catalog schemas optional avoids inventing 10 speculative schemas now (spec §43: the list/schemas aren't the architecture).

Tradeoff

Catalog generated_at / catalog_hash are injected, not computed in protocol. @dina/protocol is zero-runtime-deps (no crypto, and clock calls hurt determinism/testability). So buildCapabilityCatalog({generatedAt, hash}) does deterministic assembly and the caller (AppView, which has crypto) injects the timestamp + hash over the protocol-provided canonical serialization — the same pattern as buildCanonicalPayload. CATALOG_VERSION is a hand-bumped date constant.

Open questions

Open question

Expanding the recognized canonical vocabulary. Making canonicalization (Core D2D ingress / AppView ingest) recognize all ~13 catalog capabilities widens what's admitted as "official" beyond today's 3. That's intended by the catalog model, but it means a provider publishing e.g. deploy_status is now an official (not custom) capability. Confirm that's desired before Phase 3 wires the resolver to the catalog. (V1 Phase 1 does NOT change the resolver — it only adds the catalog + a superset test — so nothing is admitted differently yet.)

Open question

discoverability migration. Phase 2 adds discoverability: public|unlisted|known_only to listings with back-compat isDiscoverable:true→public, false→known_only (spec §460). Confirm no currently-public listing should silently become known_only. (Today only the demo rigs publish; low risk.)

Phased plan

  1. Phase 1 (this iteration) — protocol catalog foundation. Catalog types + curated data + integrity/ consistency validators + tests. Pure-additive to @dina/protocol; nothing else changes → green.
  2. Phase 2 — provider-listing contract. Add discoverability + per-listing category_id + capability_kind + optional policy hints to the listing types + validators (official→allowed category; custom→namespaced+category; discoverability required; back-compat).
  3. Phase 3 — AppView. Catalog endpoint GET /xrpc/com.dinakernel.catalog.capabilities; catalog-in- AppView (drift-gated like the registry); search honours discoverability (public-only) + category filter.
  4. Phase 4 — Core/provider. Accept only catalog IDs or valid namespaced custom; persist + publish discoverability + category; resolver derives from catalog.
  5. Phase 5 — Mobile. Fetch/cache catalog; category→capability picker; "Who can find this service?" discoverability; developer mode + schema fields + validation; diagnostics.
  6. Phase 6 — Brain/router. capability+category routing; known-binding-first; never invent flat names.

Catalog seeding — single source, re-runnable script (user requirement)

Decision (per user)

The catalog must upload from ONE common place, via a re-runnable script, idempotently across environments. Confirmed design: the catalog DATA lives only in @dina/protocol (the common source — Phase 1). AppView has NO @dina/protocol dependency (verified — that's why the resolver registry is byte-duplicated), so AppView's runtime can't import it. Resolution — a snapshot table + bridge script:

  1. AppView stores the catalog as an opaque snapshot row: {catalog_version, catalog_hash, generated_at, payload JSONB} (Drizzle table + migration). AppView serves it verbatim at GET /xrpc/com.dinakernel.catalog.capabilities — it never needs protocol types at runtime (serves JSONB).
  2. A workspace-level seed script (scripts/seed_catalog.ts, run via tsx) is the ONLY place that imports @dina/protocol: it calls buildCapabilityCatalog + serializeCatalogForHash, hashes with Node crypto, and UPSERTS the snapshot into AppView's Postgres (DB URL from env → works on dev/test/prod). Idempotent: same content → same hash → no-op (or version-bump only on change). Re-runnable any number of times.
This cleanly respects the import boundary (runtime = DB-only; the script is the single protocol→AppView bridge) and satisfies "common place + script + environments + provide properly." This is Phase 3.

Completion status (the §43 invariant, end-to-end)

Core invariant — DONE end-to-end

The load-bearing §43 invariant is now implemented across the whole path: protocol catalog source (curated, integrity-gated) → AppView seeding (single-source re-runnable script, greenfield) + serve endpoint → mobile bundled+live fetch (fail-soft) → Category → Capability picker (no typing ids) → fail-closed publish carrying per-capability category + explicit discoverability, with the anti-spoof kind DERIVED not trusted. A provider can't pollute the official namespace with flat names; custom stays namespaced + categorised; every listing carries capability + category + discoverability.

The 3-way "who can find this?" discoverability selector is now DONE (Iter 8) — unlisted is reachable; the §5.3 "discoverability ≠ authorization" disclaimer ships. Additive follow-ons remain (don't change the invariant): Core D2D-ingress vocabulary enforcement (deferred — the category-required validator can't retrofit category-less configs without making fixtures catalog-clean first); Brain router capability+category routing; mobile dev-mode diagnostics; docs.

Iter 11 — wire discoverability + category through the network layer (Codex #2/#3/#5/#6/#7/#8)

Context: an external (Codex) review found that Iters 7–9 wired the tri-state discoverability + per-capability category into the UI + local config + mobile validation, but NOT into the PUBLISH/AppView layer — so `unlisted` meant "don't publish at all", `known_only` overpromised a pairing path, and `category` was dropped at the wire. My green tests didn't catch it (nothing asserted those fields reached AppView). Verified every claim in code before acting. Chosen model (Codex's "correct option" + Dina's privacy ethos): public = publish + searchable; unlisted = publish (AppView excludes from search via the `isDiscoverable=false` gate, but the PDS record exists → resolvable by URI/link/QR/D2D); known_only = NOT published (local/pairing-bound).
