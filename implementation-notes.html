Design decisions (where the spec or plan left room)

  • @dina/ucp depends on @dina/a2a. Both are pure leaf packages. UCP needs RFC 8785 canonical JSON, base64/base64url, UTF-8 helpers and the Ed25519 envelope pattern, which @dina/a2a already has and tests. Copying them would leave two codecs to keep in step; the hygiene test allows exactly @dina/a2a and checks it stays dependency-free.
  • RFC 8941 byte sequences accept missing padding (RFC 8941 §4.2.7 SHOULD) by padding before @dina/a2a's strict decode; any other malformed base64 is refused.
  • Signature verification order per candidate: shape and tag, alg, coverage, digest, key, thumbprint, signature; the failure reported is the one that got furthest. Coverage and the digest come before the key lookup, so a forged message never triggers a profile refresh.
  • Tags. Untagged signatures are UCP's default. A web-bot-auth one (the dual-audience shape) is verified the same way, plus keyid must equal the key's RFC 7638 thumbprint (overview :2424-2429), and its "signature-agent";key="<label>" component is a Dictionary member selected per RFC 9421 §2.1.2. Any other tag is skipped (tag_unsupported), per the identity-resolution algorithm (overview :2370-2390). An alg, if sent, must be ecdsa-p256-sha256 (RFC 9421 §3.2 step 6.5). Dina itself signs only the default shape and refuses to sign with a Signature-Agent header.
  • Totals check uses the spec's own formula (checkout/index.md:1330-1334): every non-total entry, unknown types included, sums to total; sub-lines sum to their parent. A mismatch is reported and the answer shown as the merchant gave it, never repaired. Line-item, option and adjustment totals are plain entry lists (parseTotalEntries) with no one-subtotal-one-total rule, as their schemas say.
  • Units: a UCP quantity converts to Dina's Quantity only exactly: one of the five Rec 20 matches and no more fraction digits than Dina's unit holds (kg and l: 3; each, g and ml: 0). Otherwise the unit stays opaque and is shown by its display_text. Requests always carry quantity_unit as {unit, scale, display_text}, each included: an omitted unit asserts nothing and the merchant reads the count in its own basis (checkout/index.md:90-104), so sending the approved unit lets the merchant refuse a basis that changed. increment is the merchant's policy, outside the unit's identity, and is not echoed. (An earlier version left each out; the U0 review showed that misreads the spec.)
  • Readers type only what Dina acts on. Full validation against the merchant's negotiated schemas is Core's job (§3.6 step 4a, U1). The hand-written readers are the second line: a resource with a malformed acted-on field is refused (Dina hands off rather than guess), except a catalogue answer, where one unreadable product is dropped and counted. An unknown checkout status is kept as {unknown} and never treated as terminal. Links, continue_url, permalinks and tracking URLs are kept only when https without userinfo.
  • The shipping address is written bare. The spec reads a request destination id as a reference to an address the merchant already holds (fulfillment.md:270-289), so Dina sends postal fields only, then resends them under the id the merchant assigned. It selects a shipping destination only when the merchant's copy has exactly the approved postal fields, no more and no fewer; a merchant that rewrites the address, or lists a saved one (even one that adds a field), does not match, and Dina hands off rather than select an address the owner did not approve.
  • An approved address goes out on every update. Updates are full replacements (checkout/index.md:1078-1083), so an update without it would erase it at the merchant. The builder resends it on the merchant's shipping method, or in the create's own shape (a shipping method with no id) before the merchant lists one; the dispatch check refuses any update that drops it. With an approved address, choosing pickup needs a new card. Every method that writes destinations names its type (dependentRequired in fulfillment_method.json).
  • Only pickup chooses a merchant location. Plan §3.7 allows filling in "a pickup location id from the merchant's own destinations": a non-shipping selection is admitted only on a pickup method and only for a business_location. A custom method type is refused and goes to hand-off.
  • The checkout intent hash is SHA-256 over RFC 8785 JSON with v: 1, quantities as decimal strings, capabilities as a sorted map, lines in the approved order, and units as identity (unit, scale). An intent with two lines for one variant is refused: the merchant's line ids could not be matched back to items.
  • Update bodies are built from the intent (buildUpdateCheckoutBody), so an update is a full replacement of everything approved plus the merchant's ids; the dispatch check (checkUpdateFitsIntent) still runs on every body. Merchant line ids are matched by item id.
  • The kept order record never drops an id: events are a union by id (only each event's type is kept for good; tracking numbers and descriptions live in the open-order snapshot, dropped at close), adjustments keep their first type, their latest status, and whether a completed or a failed status was ever seen. A first failed interrupts in either delivery order; a dispute or cancellation interrupts when first seen and when first settled; a re-typed adjustment is judged by its first type. Each adjustment interrupts at most once per answer.
  • Merchant-chosen strings never index a plain object. The order record's maps are null-prototype objects read through an own-property check, so an id named __proto__ or toString is an ordinary key; the Rec 20 and total-type tables are Maps.
  • Merchant JSON inside MCP answers (the content[0].text fallback and SSE events) is parsed with @dina/a2a's strict I-JSON parser, as Core parses every body: no duplicate members, no __proto__, numbers in range.
  • An error answer's continue_url is kept only when https without userinfo, like every other URL Dina may offer.
  • Lists that are not lists (applied, options, destinations, groups) are malformed, never read as empty; only absent means none.
  • Context carries address_country, address_region, postal_code and language only, whatever the owner allows within those (§3.16). currency, though in the context schema, is not sent.
  • Search pages ask for 20 products per merchant, the guard's per-answer cap (§3.11).
  • REST sends Accept: application/json beside the required headers. MCP offers protocol versions 2025-11-25, 2025-06-18 and 2025-03-26, and reads JSON or SSE answers.
  • Spec fixtures are harvested by packages/ucp/scripts/harvest_spec_examples.mjs: it reads indented fences inside mkdocs tabs too, renders the {{ ucp_version }} macro from mkdocs.yml as the site build does, strips HTTP heads, unwraps MCP answers, records each block's <!-- ucp:example … --> marker, and the tests use the marker (not the shape) to skip profile fragments (extract=$.ucp.*) and illustrations. 117 examples at v2026-08-25. The fixture is generated, so it is in .prettierignore like the other generated fixtures.
  • Publication is off until the owner turns it on. The owner settings that switch UCP on are U1.5; until then a deployment opts in (DINA_UCP_ENABLED=true on a server, EXPO_PUBLIC_DINA_UCP_ENABLED=1 in a phone build). Both read the profile host's name from configuration (DINA_UCP_PROFILE_HOST, EXPO_PUBLIC_DINA_UCP_PROFILE_HOST; default ucp.dinakernel.com), and the envelope's host member names it, so a test host's upload can never be replayed at production.
  • Epochs. A fresh installation holds epoch 0, meaning "never claimed". Its first publish reads the label's state: an unbound label is claimed at epoch 1; a label another installation serves (a restore on a new phone, say) makes this one stand down and say so, and only the owner's "use this device" (activate) claims the next epoch, after which the old installation is refused and stands down too. Two devices never fight over one profile. The owner's "Turn UCP off" and "My key may be compromised" also claim the next epoch when another installation holds it: the owner acted on this device, and the profile must stop whichever device last published it.
  • Owner controls are kept until the host confirms them. "Turn UCP off" and "My key may be compromised" are stored as a pending control (status stopping) and retried with the upload backoff, so the owner never reads "off" while the host still serves the profile. A pending retirement is never downgraded to a pause. A sealed phone keeps the control pending until the next unlock.
  • The host's HTTP status comes first. 200 is applied or replayed; 409 is a refusal of the change, with the state; 400 and 401 refuse what this node sent and are not retried as they are; 429, 503, other statuses and no answer are temporary (unreachable, retried). A host that cannot resolve the DID document now answers 503 with no refusal body.
  • The publisher's schedule: at boot, then daily; a failure retries after 1 minute, doubling to 1 hour; an hourly check that the host serves exactly the bytes Core built (else stale, and a fresh upload), which keeps checking after a failed check. Every owner action moves a fence: a job that began under an older fence stops before it sends, and a result that arrives after the fence moved is not saved, so a late refusal cannot stand down a device the owner just activated. A kick during a run runs again when it ends. A run takes the identity once and sends nothing after the vault is sealed.
  • The publisher's stored record (KV ucp/publisher) is Core's own and is checked field by field when read (readPublisherState); anything unreadable starts again as a fresh installation, which stands down rather than fight if the label is already served. Archives leave it out (export/archive.ts), as they leave out the commerce restore fence: it names this installation, and a device restored from an archive is a new one.
  • Every node lists the drop-box webhook (https://<label>.<host>/webhooks/orders) until U3 builds signed webhooks for servers with a public domain. The host answers it 200 with {"ucp":{"version":…}}, reads nothing, keeps nothing, and allows 60 deliveries a minute per label (S9). It counts bound labels only (an unbound label is a 404), so posting to random labels cannot reset a real label's count.
  • The host's HTTP contract lives in @dina/ucp (createUcpHost, pure: storage, log, DID keys, SHA-256 and Ed25519 are passed in), so AppView serves the same code Core's publisher tests run against. AppView runs it as a route in appview-web (§3.5), selected by host name before any AppView route, so nothing else AppView serves is reachable under the host's names. Uploads are checked against the publisher's DID document as resolved now (the A2A directory's PLC resolver and its dina_signing reader, both reused), then applied by applyPublication inside one Postgres transaction per label under an advisory lock, so even two first claims run one after the other. At most four host transactions run at once (a short queue, then 503), so a slow bucket cannot take every connection of the pool AppView shares. An upload's document must list exactly the keys its envelope registers, so a retired key cannot ride along unregistered.
  • Publishers are did:plc nodes. The envelope's DID pattern admits did:web, as Dina's other signed contracts do, but the host resolves keys only through the PLC directory (the A2A directory's resolver), so a did:web publisher is refused (401). Every node that publishes has a did:plc: the phone always, a server once it has its PDS identity (boot starts the publisher only then).
  • The off-host log is one write-once object per applied change in an S3-compatible bucket (aws4fetch signs; If-None-Match: *), named so a label's records sort by revision and then by write order (the clock in µs, made strictly increasing). The change is appended inside the transaction, before the row is written; a failed append fails the change and nothing is written, and a write that fails after its append makes the label catch up again before its next use. A refusal or a replay is never logged. Catch-up reads the bucket outside any transaction and refuses a history that is not one: another DID, a missing revision, an epoch or generation going back (the label then serves nothing, 503). Reads from the bucket are capped as they stream.
  • No access log, by construction. Caddy writes access logs only for sites with a log directive, and the host's block has none. Caddy's error log would still carry the label host and the merchant's address when the proxy fails, so the block answers errors itself (handle_errors), which Caddy logs only at debug level; both checked with Caddy 2.11.7 and a dead upstream. The application writes no line per request; it counts ucp_host_requests_total by route and status, and an error line carries the error's class and the route only (tested), since a database error's message can contain the label.
  • The interpreting validator (commerce/ucp/schema_validator.ts, @cfworker/json-schema 4.1.1, draft 2020-12). A set is built from documents keyed by the URL each was fetched from: the document's $id becomes that URL, so every relative $ref resolves where the document came from (§3.6 step 4a); a nested $id is refused; every $ref must land on a document in the set; a JSON-pointer fragment is percent-decoded (RFC 6901 §6), which the library does not do itself. A merchant-hosted schema loses pattern and patternProperties (and the property rules beside them): a merchant's regular expression never runs on the phone's one JavaScript thread, and without it the schema only accepts more. Errors keep the keyword and locations, never the value. On Hermes it needs a WHATWG URL: React Native's own joins a relative reference onto the whole base path and cannot set a hash; Expo 57 installs a WHATWG one at start-up, and the device self-test proves the cases. The build walks every object the validator might read (only const, enum, default and examples are skipped), refuses id as well as nested $id, refuses recursive and dynamic references, checks that every reference's target node exists, and refuses a set whose evaluation could expand past 200,000 nodes (nested references that double at every level). Sets that check merchant answers drop uniqueItems, which the validator checks by comparing every pair of items in an array the merchant sizes.
  • Request and answer forms of a schema (@dina/ucp schemaVariant): a schema's required is the response requirement; ucp_request (one value, or one per create/update/complete) overrides it for requests and ucp_response for answers, as the spec's own docs build reads them. omit becomes the false schema: Dina never sends a response-only member and refuses an answer carrying one responses must omit. A transition reads as optional. Each operation names where its payload and answer are typed (a $defs entry for catalog calls, the resource schema with its request form for carts and checkouts).
  • The merchant client opens a merchant (discovery, then its schemas), keeps it a minute, and never sends an operation it cannot validate or a payload that fails. MCP: a server that refuses initialize gets calls with no session headers; a network failure during initialize is retried on the next call; a 404 on a call that carried a session id starts a new session and resends the exact bytes once. REST: 401 and 403 bodies are read (they name the UCP code), and a success is the operation's status or 200.
  • Search and its guard (U1.4). Core runs the search (startSearch). It checks the query (§3.16), asks every merchant in parallel under one 8-second deadline (inside the 10 seconds a server's Brain waits for Core; a merchant still working is reported timed_out), stores each product, and gives Brain local handles (m1, p1, …, stable within a conversation) and the checked fields. Each merchant's outcome is one of ok, unreachable, timed_out, too_large, unavailable, request_invalid, rate_limited, refused, merchant_error, error_response, answer_invalid or malformed, with a count of products skipped (unreadable, an id the answer repeats, or past the caps: at most 100 kept from one answer and 200 from one search, taken in turn from the merchants). Brain sees at most 10 variants of a product. These caps bound Core's work after the merchants' deadline whatever the merchants send. Merchant text waits in ucp_guard_jobs, one job per product, at most 20 per answer and 40 per search, counted by place in the answer and taken from the merchants in turn; a job, origin included, stays within 8 KiB. A search's jobs share a 10-second budget: a claim lasts to its end, a verdict at or after it is refused as late, and once it ends both unstarted jobs and claims with no verdict are marked abandoned in the database. Claims take turns across searches by a counter that rises with each claim. A search needs a live owner turn in its session (within 30 minutes, as an A2A proposal does), or the owner's approved card for exactly it (the approval is the owner's presence, so a card stays usable for its hour); a session Core holds no record of searches nothing, and reads as uncovered. Raising the review card again returns the live card (one past its time is retired); its own text names the whole query and every merchant until U1.5 renders it; one past its time is expired as the sweeper would. Searches are kept a day, and a handle no search has used for a day goes too; a handle's number is never given again (a rising counter per kind, and per product for variants), so a stale handle resolves to nothing. What Core keeps about a conversation (taint, coverage, UCP handles and searches) is named in one place, forgetConversation, which runs when a thread's last message goes, when chat is reset, and when a forced restore replaces the chat history. The guard worker shares A2A's scan with its own system prompt and one model call per product (S19). The two workers share one limit of 4 calls (GuardSlots): a slot is taken before the claim and held until the model call itself settles, so a slow model never has more than 4 calls running (a call that never settles gives its slot back 60 seconds after its claim ends). The worker refills a slot as soon as one frees, and a kick looks at the queue again at once (one that lands as a pump ends starts another). stop() claims nothing more and does not wait for a slot, on either worker.
  • Coverage on a server. A server's Brain keeps its chat in memory, begun again with every process, and never writes it to Core, so Core's chat repository, which marks coverage on a phone, sees nothing there. The release log is told where chat lives (chatLivesIn: brain on the server, core on the phone); on a server it marks a chat session covered at its first recorded owner turn. Every restricted read since then is in the durable taint record.
  • The owner's shopping settings (U1.5). One row on the identity database (ucp_owner_settings, travelling in archives): the shops Dina may search, as origins (at most 50), and the context a search carries (country as two capitals, region, language, and a postal code only if the owner enters one). A search goes only to those shops; one that names none goes to all of them when there are at most ten; with more, Core refuses with choose_merchants and lists them, and the tool tells the model to choose up to ten. Saving needs no presence check because only the owner reaches the route (the owner capability, or a paired device whose DID is the node's own), as for the owner's other settings; Brain cannot. A save can widen what leaves the node (a new shop, a postal code), and the owner accepts that by saving it. The phone has a Shopping screen in Settings (edits are kept only on Save, and the screen says when some are unsaved; fields are trimmed; Android 9 and older are told of their TLS limit); the console has a Shopping section.
  • Products by handle (U1.5). POST /v1/ucp/products fetches up to ten products Brain saw, afresh: one with get_product, several from one shop with lookup_catalog. Both are the shop's lookup capability, so a shop without it is reported unavailable. Brain sends no text, only handles Core maps back; the answer is kept and guarded as a search's is, under the same handles. Core keeps only the products asked for, in the order asked (a shop may answer a lookup with others), and names the handles no shop answered (missing), including one Core could not keep (a price past fifteen digits). Each product is fetched with get_product, at once: lookup_catalog answers one featured variant per product, and a fetch wants each whole. The handles are marked used before the shops are asked (with their variants, their shop and its units), so a purge while they answer takes none of them and renumbers nothing. A product a shop no longer has comes back as the spec says: a UCP error status, read as error_response.
  • Brain's tools and the comparison card (U1.5). search_ucp_catalog, request_ucp_search_approval and get_ucp_product, offered to an ask that names its chat conversation (Core records owner turns only there, so a one-off ask could never search), on a host with a UCP client, while UCP runs (asked per ask: brain-server reads the same DINA_UCP_ENABLED as Core and runs the UCP guard only then; the phone asks whether its worker runs). The search tool kicks the guard and waits for it (up to 11 seconds; a failed read is tried again and the last good view kept), while it looks up each shop's PeerLens trust (by origin as an organization, three seconds at most). Trust has three states: rated (reviewed, or advised against even with no reviews), unrated (no reviews) and unavailable (the lookup failed, or a stand-in AppView had no data); the last two read differently and rank the same, above shops advised against. The model gets at most 30 products: those the guard checked first, then those past its caps (Core marks them unchecked, and the model sees checked: false), each part best-trusted shop first, then cheapest within a currency (currencies are never compared), so one shop's long answer cannot crowd out another's; prices read in the currency's own decimals (EUR 19.99, JPY 1200), with each variant's unit, scale, step and, for a unit Dina does not know, its guarded name. A held search raises nothing: the tool tells the model why and to ask the owner, and only when the owner says yes does request_ucp_search_approval raise the card. Once the owner declines any search in a conversation, Core refuses every new card there (a reworded query, other shops) until the owner speaks again (review_declined), and at most three cards may wait at once (too_many_reviews); Core notes each card it raises per conversation (ucp_review_cards) to tell. This holds the model to the owner's answer; on a server, Brain records the owner's turns (as for A2A), so it does not hold against compromised Brain code, which can still only raise a card the owner decides. A decline decided on the phone is dated when the server applies it (the next sync, about five seconds later), so an owner reply typed in those seconds reads as before it and the owner speaks once more: the safe side. A phone copy that lapses unanswered decides nothing: the card stays for the console. Naming more than ten shops is too_many_merchants. The card spec is the search id alone. The card reads products, prices, availability and each shop's outcome from Core, and each shop's trust from Core too (GET /v1/owner/ucp/searches/:id/trust, for the search's own shops only; the host installs a trusted AppView lookup, as for A2A's directory evidence), on the phone and on the web alike, so nothing Brain says reaches the owner's card (plan §3.7). The reading and the order (readMerchantTrust, bestFirst) live in Core, and Brain's tool uses them. A search read once is reused for five minutes, so a chat row drawn again does not ask again. A product priced past fifteen digits (UCP allows sixteen; Dina's money type holds fifteen) is skipped at intake, and every price formatter falls back to the plain amount rather than throw. A page opens only on a tap; one off the shop's host (or its subdomains) is shown whole and said so first, and links past 2 KiB are not offered (plan §3.8).
  • The review card on every surface (U1.5). The console renders ucp_search_review with every shop, the exact query, and Core's reasons in Core's words (REVIEW_REASON_WORDS, put into the page as JSON). A server's card is mirrored to the paired phone when it can be shown whole, bound to the card's binding; the phone's own card is built from the stored card by the same projection, and denying it cancels it directly. The card lives an hour, so an approval stays usable after the owner says yes; its phone copy lapses 14 minutes after the card was made (the phone takes 15 at most, less a minute for a node clock running ahead; mirrorExpiresAt, fixed per card so every resend matches), and the console still has the card after that. A mirrored card names its sender by the name its device was paired under, which Core stamps from its own registry, and the phone heads a mirrored search "A held shop search from a paired device", never "Dina held": any paired device may mirror a card, and the device chose its own name (this naming now holds for A2A mirrors too).
  • Where search runs. Core installs the search runtime only where UCP is on (DINA_UCP_ENABLED on a server, EXPO_PUBLIC_DINA_UCP_ENABLED on the phone), beside the profile publisher: a merchant reads the profile the publisher uploads. The runtime looks up the workflow service on each call, because a server replaces its first service when it wires the workflow plane. A server without a did:plc runs neither. On the phone, UCP starts once the node is up (never for a boot that fails or is dropped) and stops before the node is disposed and on seal, sign-out and erase, each before the database closes; one guard-call limit serves the whole process, and the worker reads the live model on each call, so a provider change in Settings applies at once.

Deviations

  • Schema limits count the merchant's documents, not the release's. Plan §3.6 step 4a caps a negotiation at 64 documents and 2 MiB. Dina's own capability set reaches 81 of the published release's documents (fulfillment alone reaches 71), so that cap would drop capabilities at every merchant. The cap exists to stop a merchant making Dina fetch without end; the release is a fixed set (116 documents, about 560 KiB), the same for every merchant and cached across them. So 64 documents and 2 MiB bound the merchant's own documents, and the release's are bounded apart (256 documents, 4 MiB); depth 16 and 256 KiB a document hold for both.
  • Closed enums are enforced (A16 as the spec writes it). Plan §3.6 says unknown enum values pass. The spec's own rule (schema-authoring.md, "Open Enumerations" and "Closed Enumerations") is that a value set that may grow is written as a plain string with examples, which passes any value, and a closed enum is kept for values that need integrators' code to change (checkout status, say). So the validator enforces closed enums, and an answer outside one is an answer Dina cannot act on (it hands off), which is what A16 asks for open sets and what the spec asks for closed ones.
  • One runtime dependency. Plan §5 says "no dependencies block"; the package has exactly one, @dina/a2a (in-repo, itself dependency-free). No third-party runtime code.
  • Publication envelope members. Plan §3.5 lists versions and hashes; the envelope carries one map, documents: {version → sha256 hex}, so a version cannot be paired with another's hash. It also carries v: 1 and a domain member (dina:ucp:profile-publication:v1), as every signed Dina contract does, and one member set per operation (upload: documents, keys; retire: retire; pause: neither).
  • The official Zod cross-check has two pinned exceptions. @ucp-js/sdk 0.5.1 (a) ignores the ucp_request annotations inside the fulfillment types (its create and update method schemas demand response-only id and line_item_ids) and merged the destination type with binding.json's reverse-domain pattern, so it rejects the spec's own fulfillment request examples; and (b) types ucp.map_order as a string where ucp.json makes it an object of arrays, so it rejects the spec's profile scaffold. Everything else Dina builds, Dina's profile, and every fixture Dina reads pass it; each exception is pinned by a test that fails if a later SDK fixes it.
  • The host catches up from its log label by label, not all at once. Plan §3.5 says a restored host "replays the log over its database before serving any profile or accepting any upload". A whole replay reads every record ever written (a label uploads daily, so 100,000 labels write some 36 million a year) before the host can answer anything. Instead, the first change to a label in a process, or the first read of a label with a stored row, lists that label's records newer than its stored revision (one listing) and applies them first; a label whose log cannot be read answers 503 and serves nothing, which is the plan's "serves nothing for a label whose log it cannot read" per label. A read of a label with no row answers 404 without asking the log (serving nothing is safe either way, and a stranger's guessed labels should not each cost a bucket call); a first claim always asks, so a lost row still refuses another DID. Every guarantee the plan tests for holds: a retired key is never served again, no counter goes back, a lost registry row stays bound.
  • The log record carries the keys a change registered (keys_set), beyond the plan's list (binding, revision, highest generation, retirements). Without it a key first registered after the backup was unknown to the restored host, and its node's next upload was refused (generation: a new thumbprint must exceed the highest generation, and it equals it), so the node could never publish again. Pinned by a test that fails without the field.
  • The plan was amended (2026-10-04, after the U0 review) where it described what was not built: §4.1 and §5 now allow the one dependency on @dina/a2a; §3.15 names it in AppView's packaging; §3.19 step 1 says which scaffolds are harvested.

Tradeoffs

  • Exact address match versus normalising. Comparing the merchant's echo field by field refuses a merchant that upper-cases a street name; normalising would accept it but could also accept a different address. Exact match, then hand off, keeps "only what the owner approved".
  • Hand-written readers plus runtime schemas rather than readers generated from the schemas: the readers stay small and typed for what Dina acts on, and the runtime schemas (U1) catch everything else; the SDK is a test oracle only.
  • aws4fetch (one small, dependency-free package) rather than the AWS SDK for the log bucket: the host needs PUT, GET and ListObjectsV2, and the SDK would bring dozens of packages into AppView's runtime image. The listing's XML is read with two patterns, safe because Dina names every object; anything in the label's folder that is not a log name fails the catch-up.
  • The label's state as one JSON text column rather than columns per field: the rules live in @dina/ucp and work on LabelState whole, and the row is read back through a strict reader (readLabelState). Text, not jsonb, because jsonb refuses \u0000 and the served bytes must come back exact. did and revision are also columns, for an operator's queries.
  • Refuse the whole resource on a bad acted-on field rather than read around it: a checkout Dina half-understands is a hand-off, never a card built on a guess.

Open questions (decided as below; confirm or revise)

  • Report the SDK defect upstream? It is outward-facing, so not done: the evidence is in packages/ucp/__tests__/official_schemas.test.ts if you want it filed.
  • Address match strictness (above): exact field equality. Revise if live merchants routinely normalise addresses and the hand-off rate is too high.

Migration 65 (ucp_checkout): ucp_checkouts, ucp_carts (each with a slot: holder, lease, fencing generation) and ucp_requests (with not_before for a merchant's Retry-After, and the MCP envelope's JSON-RPC id in rpc_id, so a resend never parses its own stored bytes). The transport prepares a call's exact bytes once (the REST body, or the whole MCP envelope with its JSON-RPC id) and sends them as they are, so a resend is byte-identical. UcpDispatcher.mutate takes the slot; if an earlier request is still open it sends nothing and returns earlier, and the caller resumes that request under its own operation's gate; otherwise it builds the body under the slot from the owner's row as it stands, writes the journal row and passes the gate in one transaction, marks the row "may have left" before the bytes go, and writes the answer only while its slot generation is current. Definite: a resource, a UCP error answer, a refusal the merchant decided. Resent after Retry-After: 429, 5xx, and an MCP internal error or one naming a retry even at HTTP 200. A 409 to bytes never sent before is Dina's own defect: abandoned at once. A 409 to resent bytes is waited out three times at most, then abandoned. Every abandoned row (deadline, gate closed, conflict) tells its owner in the same transaction, saying whether it may have reached the merchant (Gate.abandon). The lease covers the transport's worst case (two MCP session starts, two calls, a profile refresh). Rows go 48 hours after they end, on every use. Checkouts and carts do not travel in archives and are not forgotten with their conversation, since a handed-off session is still watched (U3).

UcpCartService: lines named by variant handle, mapped to the merchant's ids, at one allowed merchant; each line's product is fetched afresh (get_product) so the line sends the merchant's own unit identity (not its increment, which is the merchant's ordering policy) and a quantity must be a whole number of that increment; updates are full replacements built under the slot from the latest answer, reusing the merchant's line ids. A cart is gone on not_found, past expires_at, after a cancel, or when its create never settles. A change the merchant refuses returns refused with the spec's code and leaves the cart as it was. A read's answer is stored only if no change's answer landed while it ran. Brain reads handles, quantities, minor-unit amounts and only the spec's total types (a merchant's own label reads other).   • U2.4, the start card, the permit and one gate (built). UcpCheckoutService.propose builds the checkout intent from handles (each line's product read again, the negotiated version, transport, endpoint and capabilities, the owner-allowed context; no personal data, D3) and in one transaction writes the session (awaiting_approval) and raises the Core-minted ucp_checkout_start card bound to the intent's hash; at most three wait per conversation. The owner's yes mints the permit in one transaction (card still approved, card hash equal to the session's, permit not minted yet), settles the card, and starts the create; a no or a lapse declines the session; the sweep mints for an approval whose handler was missed. Every create, update and cancel passes one gate when sent: a live permit (minted, not void, inside six hours and the session's expiry), the state the operation is sent in, and for an update a body that fits the permit (a selection names only what the merchant offered, checked first by checkSelection). Before the first create, the negotiation is read again; a changed version, transport, endpoint or capability set voids the permit and declines the session.   • U4.2, Core's flow and store (built; migration 68, link_store.ts, links.ts).
    • Pending links. A pending link holds the state, verifier and exact redirect URI for 10 minutes, and is consumed once. A replay, a wrong state, a wrong iss or a late callback is refused.
    • Tokens. They live in the SQLCipher identity file and leave through one function; a view never carries them.
    • Refresh. One caller at a time, under a lease and a generation; other callers wait and use the winner's token. A lost answer is retried once with the same token, and invalid_grant means the owner must link again.
    • Unlink. The link moves to revoking at once and every token is queued. A refresh that answers afterwards queues its new tokens too, never storing them. Revocation retries from a minute up to an hour, for up to 7 days, and then the link goes.
    Decided (D6): a public client everywhere, whose client_id is Dina's own profile URL. U7 — key rotation (built)

  • One ring for both keys (crypto/key_rotation.ts, pure): active, staged, retiring, gone. A staged key signs only once the list naming it was published and seen served, and the list's cache life plus a minute has passed since the later of the two; the replaced key stays listed 7 days. The UCP request key and the A2A card key both use it; only what counts as "served" differs.
  • UCP (publisher.ts). The ring lives in the publisher's record. "Rotate my shopping key" stages the next generation above any the host has seen; the profile lists both. The upload that stages it is checked against the served copy in the same run (the plan's "hourly compare, run at once"), and the switch is due 360 s later (max-age 300 + 60). Requests are signed with the new key only after the host accepts the upload that makes it active. Past the overlap the upload that leaves the old key out retires it at the host (the host retires any key an upload drops). The schedule wakes at each step.
  • Restarts and restores. The identity derives any generation on demand (it keeps its own copy of the seed, so a phone that wipes its seed buffer still can); boot reads the record before any merchant call, and an identity installed later (a phone unlocked again) signs with the same generation. A node without a record (new, or restored: archives leave it out) adopts the host's ring: the active key, a staged key (which waits a full wait again from this node's own upload, and needs its own check), and retiring keys with their times. A stood-down device records the holder's ring and signs with its active key. Retired keys are never listed by the host, so a restore cannot bring one back; a stale record naming one is refused (retired_key) and replaced by the host's.

Dual review of the whole UCP change (2026-10-05)

Round 1 (Claude 1, Codex 6; all fixed, each with a test that fails without the fix):

  • A checkout approval now binds the linked account (plan §3.7): the intent carries the link's lifetime and an authorization revision that only a new authorization (a step-up) raises, never a token refresh. Linking, unlinking, relinking or a step-up after the yes voids the permit (credential_changed). U2 had left this for U4, and U4 had not come back to it.
  • Checkout dispatch keys used crypto.randomUUID, which the phone's Hermes lacks: every mutation would have failed on a phone. They use newUcpId, and a test refuses the call anywhere in UCP code.
  • Unlink during a link in progress: a code exchange (or a step-up) that answered after the owner unlinked made the link active again. Unlinking now cancels every open attempt at that merchant; its tokens, if they come, are revoked and nothing is linked.
  • An oversized signature header was dropped, and the answer then passed as unsigned. Signed or not is now read from what arrived; a signature too large to keep fails like any bad one.
  • A webhook before the first poll was dropped once it prompted the poll; if Get Order was then refused, the order lost its only snapshot. Verified bodies are kept on the open order until a poll settles them, used when the merchant will not share the order, dropped when Get Order answers after them.
  • A crash between taking a callback and finishing it lost the callback (and the phone was told to drop it). Taking is now a claim: one left without an outcome past the longest an exchange can take is finished on the next try; one still being finished is not acknowledged to the phone.
  • A stale pending owner action ("Use this device" or "Turn off" pressed offline) could undo a newer choice made on another device. The press itself always applies; a later retry that finds a newer claim than the device knew at the press is not applied, and the owner is told and may press again. A compromise retirement is always carried out.

Round 2 (Claude passed; Codex 4, three of them gaps in round-1 fixes; all fixed with tests that fail without them):

  • The approved account is checked at the moment of sending, not only before: a token fetch can wait on a refresh while the link is replaced. Every send carries the account the owner approved (first send, the retry after an invalid token, a journal resend) and goes only under that account; a resend that finds another voids the permit.
  • Webhook bodies are folded, not queued. Each verified body for an open order is folded into the order's record as it comes (the same rules as a webhook-only order), with the interruptions it raises and only the latest body kept raw: no cap, so no early dispute or failure can be pushed out. A Get Order answer drops it all (the order's record moved on, and a body during that read asked for another).
  • A link and its attempt's outcome are one commit, so a crash after the link can never spend the code a second time; what follows a link (cards, waiting orders) is safe to repeat and is done again by a repeated callback.
  • Raw merchant bodies never outlive the order: the kept body is cleared on close, by the owner's "done", and in archives, as the snapshot is.
  • A pending press set aside for another device's later choice now stands down fully (the holder's keys at once).

Round 3, the last (Codex 2, both in the webhook-body fix; Claude not run again since the user's limit was three rounds). Fixed after the round, with tests that fail without them, but not reviewed again:

  • A webhook during a read is kept. What webhooks said is kept as a plain union of events and adjustments (each adjustment remembering whether it was ever failed or completed) plus the latest body. A read that answers drops it only when nothing came after the read began; otherwise the next read decides. When the merchant will not share the order, the union is merged into the order's record as it is then, so a card is raised once for each thing the record did not have.
  • "Will not share" and the merge are one write, so no crash can leave the bodies stranded until the order ages out.
