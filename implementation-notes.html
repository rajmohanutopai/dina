Adapter Parity / Conformance Suite (ACTIVE GOAL — in-flight)

The mobile apps and the Home-Node-Lite servers share the same @dina/core|brain|protocol logic but run DIFFERENT native adapters: storage (op-sqlite on device vs better-sqlite3-multiple-ciphers on the server), crypto (react-native-argon2 vs node), keystore (react-native-keychain vs file), fs. The node adapters have ~15 test files; the expo adapters have zero direct tests (op-sqlite can't load in a Node jest process). Every divergence — e.g. the historical op-sqlite run() returning a constant instead of real rows-affected, silently breaking CAS — currently ships unguarded. This goal builds ONE behavioral contract suite run against BOTH sides to close that bug class systematically.

AP0 — Conformance-kit architecture (design)

A dedicated PURE package packages/adapter-conformance/ Zero runtime deps, no jest, no node-only imports — mirrors how @dina/protocol ships its pure conformance kit. It exports per-family arrays of contract cases (storage / crypto / keystore / fs). Why a new pure package, not test-harness or a -node/-expo package: the kit must load in BOTH a Node jest process AND the React Native bundle; anything carrying jest or a node-only/native import would break one of the two runners. Purity is the constraint, so it gets its own package.
Framework-agnostic case shape with a built-in assert interface Case { name: string; run(ctx): Promise<void> }, failures thrown via a tiny built-in assertEqual/assertBytesEqual/assertThrowsAsync (NOT jest expect, which doesn't exist in RN). The node runner wraps each case in it(c.name, () => c.run(ctx)); the RN runner loops and renders PASS/FAIL. One source of truth for behavior, executed identically on both platforms.
Runner-owned adapter lifecycle Cases receive a FRESH adapter per case from a makeAdapter() the runner supplies (storage needs a clean DB each time). Keeps cases pure and lets each platform construct its native adapter its own way (temp-file path / in-memory) without the kit importing either side.
Expo runner = in-app dev screen, not jest-on-device Considered jest-expo / Detox to run the kit headless on a sim, but op-sqlite/native modules still need the real RN runtime and a headless device-jest harness is heavy + flaky. We already drive the booted app with Maestro, so a dev-only screen that runs the kit against the REAL adapters and renders a Maestro-assertable PASS/FAIL (overall + per-case testIDs) is lower-infra and higher-fidelity (real op-sqlite, real keychain, real argon2). Chosen.
Sync-vs-async signatures are themselves a contract to assert If a -node method is sync (better-sqlite3 run(): number) but the -expo one is async (op-sqlite / react-native-argon2), that divergence is exactly what the kit should catch. The kit is written async throughout to accommodate; the declared sync/async contract per method is pinned once the interface mapping lands (3 explore agents in flight).
Branch — confirm before commit This is independent of the thin-client (web-thin-client-hold) and Contact Services (usability-fixes, the current branch). Building on usability-fixes for now; will confirm whether you want a dedicated branch before any commit.

Surface map (3 explore agents) — what the conformance suite must actually target

CRYPTO reframed — the only platform fork is the Argon2 backend; crypto-expo is NOT an adapter crypto-expo contains no port impl — it's a side-effect module that installs react-native-get-random-values and calls setKDFOverride(react-native-argon2). The crypto BOTH platforms actually run is @dina/core/src/crypto/* (bip39/slip0010/hkdf/aesgcm/nacl/ed25519) on the same hoisted @noble/* — so everything except the KDF is byte-identical by construction. The sole genuine fork is deriveKEK's Argon2id backend: server hash-wasm (WASM) vs mobile react-native-argon2 (native C), 128 MiB/t3/p4. It wraps the master seed — if the two disagree by one byte, a vault wrapped on iOS never unwraps on the server. It is completely unguarded in CI (the native module only runs on a device). KAT to pin: packages/fixtures/crypto/argon2id_kek.json (“correct horse battery staple” → bf64a106…cbc2f9). Consequence: the node crypto vector-gate already exists (core/__tests__/crypto/cross_language.test.ts runs all 12 Go fixtures + the KEK through hash-wasm); the NEW value is running the SAME vectors on a device where react-native-argon2 is live. The crypto conformance is therefore primarily a DEVICE deliverable, not a new node suite.
KEYSTORE has no shared interface; FS-expo is unbuilt keystore-node implements a real Keystore port (put/get/delete/list + name-validation); keystore-expo is three bare functions (getSecret/setSecret/deleteSecret) over react-native-keychain — no list, no validation. Only set/get round-trip + null-on-miss + delete-no-op are cross-platform assertable; list() and validation are node-only and stay out of the shared suite. fs-expo implements only documentDirectoryUri/cacheDirectoryUri — the FsAdapter port is unbuilt, so fs has NO conformance target yet (building it is a prerequisite, not part of this suite — recorded as an open item, not silently skipped).
STORAGE contract = DatabaseAdapter (sync), targeted via an injected makeAdapter() The live contract both impls satisfy is DatabaseAdapter (core/src/storage/db_adapter.ts): execute/query/run/transaction/close/isOpen, all SYNCHRONOUS. Node opens in its constructor; expo is new OpSQLiteAdapter() then .open(name,loc,dekHex,openFn) — so the runner injects a makeAdapter() factory and the cases stay construction-agnostic. Highest silent-divergence risks (the suite's targets): run() rows-affected (info.changes vs result.rowsAffected ?? 0 — the original bug), blob type coercion (Buffer vs ArrayBuffer/Uint8Array), query() aggregate aliasing + shape-fallback-to-[], execute() multi-statement, FTS5 build presence, NULL/number coercion, error .code on constraint/busy.
Known config divergences are surfaced, not baked into a failing green suite Several differences (SQLCipher cipher-params, foreign_keys default ON-expo/OFF-node, journal_mode configurability) have NO defined contract today and would require changing an adapter to unify. The conformance suite asserts the well-defined behaviors both satisfy (keeping node green) and the cross-impl cipher round-trip is inherently a DEVICE test (write-on-node / read-on-op-sqlite). The unify-the-config items are logged as findings + follow-ups rather than smuggled in as red node tests — honest about what catches a regression vs what needs a decision.
DEVICE runner = an env-gated in-app screen rendering a Maestro-assertable PASS/FAIL The native modules under test (op-sqlite SQLCipher cipher, react-native-keychain, react-native-argon2) exist ONLY in the RN runtime — jest mocks them (apps/mobile/__mocks__/op-sqlite.ts backs op-sqlite with better-sqlite3 and makes PRAGMA key a no-op; keychain is an in-memory Record). So the real-adapter run must execute IN the app and surface its verdict as rendered UI. Reuse the existing admin.tsx DevSendTestRow pattern (EXPO_PUBLIC_* env-gate + auto-run-on-mount + status <Text> + testID); Maestro polls via extendedWaitUntil on a conformance-overall-status testID whose text is exactly PASS/FAIL. The protocol conformance/suite.ts is node-only (uses node:crypto/fs) — reuse only its report SHAPE, inline the vectors so the kit stays RN-importable.

AP1 — Storage conformance suite (DONE on node)

What shipped New pure package packages/adapter-conformance/ (assert.ts tiny throwing asserts incl. assertBytesEqual that also asserts the value IS a Uint8Array; case.ts ConformanceCase<T> + a result-collecting runCases; types.ts structural ConformanceDatabaseAdapter + a assertExtends drift-guard; storage_cases.ts 22 cases). Node runner packages/storage-node/__tests__/conformance.test.ts runs every case against a fresh file-backed NodeSQLiteAdapter. The 22 cases target the catalogued silent-divergence classes: run() rows-affected incl. the exact stale-CAS pattern that broke, aggregate aliasing, blob Uint8Array round-trip (incl. empty + 1 MB), tx commit/rollback-and-rethrow, NULL/int/text coercion, UNIQUE-throws, FTS5 match+BM25-rank+diacritic-fold.
Kit is ZERO-dependency (no @dina/core import) — and why First cut imported DatabaseAdapter from @dina/core; that turned the kit's typecheck red with errors in @dina/test-harness. Root cause: 7 @dina/core SOURCE files import @dina/test-harness, so importing core's barrel (even @dina/core/storage, which re-exports vault/repository) drags test-harness into the kit's compile under the kit's stricter config. The fix is the architecturally-right one: define the ConformanceDatabaseAdapter shape LOCALLY so the kit has zero deps and loads cleanly in the RN bundle (the device runner needs that), and bind it to the REAL contract in each runner via assertExtends<DatabaseAdapter, ConformanceDatabaseAdapter>() — a compile-time drift-guard so the local type can't silently fork from @dina/core (if run() ever becomes async, storage-node fails to compile). This mirrors how @dina/protocol is a zero-dep conformance kit. (Pre-existing smell logged: core production source importing test-harness — not fixed here, out of scope.)
Tests / what they showed :memory: was rejected by SQLCipher (“Setting key not supported for in-memory…”) → switched the runner to a fresh file-backed temp DB per case with afterAll cleanup. Then 22/22 cases green on better-sqlite3; the base tsconfig's noUncheckedIndexedAccess surfaced real index-safety gaps in the cases (the runtime was fine) → added a first(rows,label) helper. Final: kit tsc 0, storage-node tsc 0, conformance 23/23, full storage-node 161/161, workspace tsc --build 0.
Deep review (AP1) — (1) correct? (2) smells? (3) test issues? (1) Correct: pure-kit + runner-side drift-guard is the right shape; cases are isolated (fresh adapter, own table), sync to match the contract, and assert the documented divergence classes (not impl internals). (2) No workarounds — the first() helper is proper strict-index handling, the UNIQUE check is tolerant on error PROSE by design (agent catalog: assert a constraint signal, not the message), file-backed DBs are required not a hack. (3) Tests clean — the post-close case closes inside the body and the runner's finally close is idempotent; the drift-guard compiles (so DatabaseAdapter ⊆ the kit shape is proven).
