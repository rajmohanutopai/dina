CardSpec + Services design-review — 6 findings fixed. A review of the provider-card path turned up six issues; all fixed (tests + typecheck green across protocol / core / brain / mobile / appview).

  1. Provider-authored cards now survive the normal response path. Core's response bridge (response_bridge_sender.deriveResponseBody) and POST /v1/service/respond both DROPPED the runner's card field, so only the requester-side deterministic mapper ever ran. Both now forward an optional provider card OPAQUELY (non-null object guard; the requester re-validates it untrusted before render). This is the generalized "marketplace seller controls the card" path.
  2. Unified the ServiceResponseBody wire contract. It was split three ways: the protocol type had card but no ttl_seconds; the protocol validator REQUIRED ttl_seconds; Core kept a divergent copy with ttl_seconds but no card/schema_hash. @dina/protocol is now the single source of truth (ttl_seconds required, card + schema_hash optional); Core re-exports it instead of redefining. The validator now also shape-checks the optional card (opaque object) and schema_hash.
  3. Open capability vocabulary (provider-namespaced capabilities). The closed registry stays for shared/promoted capabilities, but a provider can now publish a NAMESPACED custom capability (com.acme.widget_price — reverse-DNS, dotted). New classifyCapability / resolveSearchableCapability / isCustomCapability in the shared registry (byte-identical protocol + appview copies). The ingester admits custom capabilities (no longer dropped as "unknown"); service-search matches them; searchCapabilities surfaces them (domain: 'custom') AND now honours intent via a deterministic lexical-overlap ranking (embedding-based ranking still deferred — logged in code, not silently ignored).
  4. Multi-listing per DID. The ingester no longer deletes an operator's other profile rows on publish (that capped a DID at one listing). One indexed row per uri; each published service.profile record is its own listing; removal is per-record via handleDelete. The concurrency-safe onConflictDoUpdate-on-uri fix stays.
  5. Render-boundary re-validation. InlineServiceQueryCard rendered lc.cardSpec raw (readLifecycle only checks the discriminator then casts), so a corrupt / imported / legacy chat row could bypass the safety rules. It now re-runs validateCardSpec(lc.cardSpec, {trusted:false}) at render — a corrupt card falls back to the generic text card; a stray badge is dropped.
  6. Staleness now affects the UI. SafeCardRenderer used isCardStale nowhere — it only showed an "as of" label. Expired cards (past expiresAt, or generatedAt + ttlSeconds elapsed) are now dimmed and labelled "Expired". Matters for price/product cards.

CardSpec — service results as DATA, not hard-coded cards. Replaced the per-capability hard-coded card (EtaResultBody) with a fixed, safe declarative block vocabulary in @dina/protocol (card-spec.ts: 15 block kinds, fixed icon/tone enums, caps, validateCardSpec(v,{trusted})). Three producers: a deterministic result→CardSpec mapper that ships (packages/brain/.../result_card_mapper.ts), a provider-carried card threaded on ServiceResponseBody.card, and an LLM-authored card at response time (validated, falls back to deterministic). Rendered by the mobile SafeCardRenderer from theme tokens. Safety: no image URLs (blob-CID only, render deferred); map = structured coords/query never a URL; link = https-only hardened (rejects creds/localhost/private-IP/odd-port), host-only shown; badges Dina-owned (dropped on untrusted path); provider status → toned keyValue, not a badge; staleness fields; additive forward-compat (v1 permanent envelope, unknown blocks dropped). Commerce action policy: only open_url ships, no silent checkout (Cart Handover law). Catalogue: docs/CARD_SPEC_DESIGN.md (15 scenarios) + docs/CARD_SPEC_V2_DESIGN.md. Proven live across transit (eta), appointment, and commerce (price) shapes.

AppView ingester service-profile upsert race (FIXED, commit aa22b3b). Pre-existing concurrency bug surfaced while standing up price_check: service-profile.ts did delete-by-operator + plain INSERT with NO ON CONFLICT, assuming the DELETE guaranteed no row at the uri. False under the bounded parallel queue + Jetstream spool replay → services_pkey duplicate_key → requeue storm → row never landed → capability never discoverable. Fix: delete only the operator's OTHER uris, then insert().onConflictDoUpdate({target: uri}) preserving createdAt. 2 concurrency regression tests added (close the bug class). Deferred (post-launch, additive — not blockers)

Deferred

Dimension query-side weighting (Part 2, Layer 4). "Map user context → a canonical dimension to weight a PeerLens search" has no launch backend — there is no dimension-filtered search endpoint, and no dimension param on search_peerlens. The consumer-facing half is already satisfied (the resolve endpoint returns canonical-keyed averageDimensions). Adding a tool param with nothing behind it would be dead code, so it's deferred rather than stubbed. Upgrade is additive (server-side), no migration. L3 (read-side canonicalization) is the launch-critical layer for dimensions, not L4.

Deferred

search_capabilities intent ranking. The launch endpoint returns ALL covered capabilities (no intent-based ranking). The routing prompt + tool description compensate by telling the LLM the list is not pre-filtered and to pick only the matching capability. Real intent ranking (e.g. embedding similarity) is a server-side swap with no client change — the intent param is already in the contract.
