Item 1 — Persistent D2D outbox done

Design — semantic payload, not sealed wire bytes

The new d2d_outbox table (identity DB, migration v6) stores the semantic message — target_did + message_type + body_json — not the sealed envelope. The drainer (makeOutboxRedeliver) re-resolves the recipient's DID document (endpoint + X25519 key) and re-seals on each attempt. This is what the spec recommended, and it means a queued message survives a recipient key-rotation or MsgBox-endpoint move between enqueue and delivery — sealed bytes would have stranded it. State machine: pending → sending (leased) → sent | failed → dead.

Design — facade over a repository seam (SQL when installed, memory fallback)

transport/outbox.ts is now a thin facade that delegates to getD2DOutboxRepository() ?? memoryRepo. Production installs SQLiteD2DOutboxRepository in mobile + lite storage init; the in-memory InMemoryD2DOutboxRepository remains only as a dev/test fallback (per the spec). Both implement one interface, asserted byte-for-byte equal in a parity test. The repository methods are synchronous — this follows db_adapter.ts's documented "sync on purpose" decision (SQLite is CPU-bound; op-sqlite/better-sqlite3 are sync), and it lets the send path enqueue inline so a failed SQL write throws and the caller honestly reports queued:false rather than lying about durability.

Design — idempotency + the drainer's suppressEnqueue

Enqueue is idempotent on a stable key (deriveIdempotencyKey: service traffic keys on the body query_id, everything else on the per-send message id), enforced by a partial UNIQUE index over non-terminal rows (mirrors idx_workflow_idem). The drainer re-runs the real send pipeline via coreSendD2D({ suppressEnqueue: true }) — the flag stops a failed re-delivery from enqueueing a second row, since the drainer already owns the row's retry state (markSent / backoff recordFailure / dead-letter). Backoff is the Go policy: 30s·2ⁿ, dead-letter at 5 attempts or 24h TTL. A dead-letter writes an audit entry (body never logged).

Deviation — replaced the old sealed-bytes outbox API wholesale

The previous in-memory API (enqueueMessage(recipientDID, payloadBytes), getPendingForRetry, markDelivered, retryPendingOutbox, …) stored sealed bytes and was never wired into any production boot (the retry worker was test-only). It had no production consumers beyond d2d/send.ts + transport/retry.ts + the barrel, so it was replaced rather than wrapped. send.ts now enqueues the semantic body; the two old test files were rewritten against the durable model.

Tradeoffs considered

Semantic vs sealed payload: sealed avoids re-resolution cost per retry but strands on key rotation — rejected. Sync vs async repo: async would match the reminder repo's style but breaks the inline-throw "queued only if persisted" guarantee and contradicts db_adapter.ts — chose sync. Drainer re-uses the send pipeline (via suppressEnqueue) rather than a parallel deliver-only path, so all gate/seal/window logic stays in one place.

That's arguably correct (a stale ETA past its window shouldn't land), but confirm you're happy treating an expired-window response as a dead-letter rather than a silent drop. (2) Drainer interval is 30s with a 60s claim lease — fine for mobile foreground; confirm the cadence. (3) The lite drainer's timer is unref'd and not tracked for explicit stop (process-lifetime); mobile tracks a handle and restarts it per boot.

Deep review — (1) correct? (2) smells? (3) tests?

(1) Correct: durability is proven against the real NodeSQLiteAdapter (better-sqlite3-multiple-ciphers, the production identity engine), not just the Map — including a close+reopen-same-file restart that drains a survivor row, and the partial unique index enforced at the SQL layer. Item 2 — Locked-vault agent approval/resume done

Design — one deterministic gate at the Core vault boundary

requireAgentPersonaAccess({agentDID, persona, mode, scope}) is the single, non-LLM check the agent-facing vault read path calls before touching the vault. Decision tree: active durable grant → allow; free tier (default/standard) → allow; sensitive/locked + no grant → create an idempotent approval workflow task and return approval_required without reading the vault; no workflow service to record the request → denied (fail closed). The gate is wired into POST /v1/vault/query — the only agent-reachable vault path per authz.ts.

Design — caller-type seam (owner bypasses, only the agent is gated)

The router now threads the auth result's callerType + callerDID onto CoreRequest. The vault route gates only callerType === 'agent'; the owner's own app dispatches in-process (no callerType) and reads every persona freely — the user-vs-agent persona-access rule. So the lock protects against the dina-agent / OpenClaw, never against the human.

Design — durable grant = SQL row; approval object = the workflow task

On approval the workflow approve handler writes an agent_persona_grants row (schema v7) bound to the exact (agent_did, persona, mode) with a 1 h TTL. The out-of-process agent then retries (possibly after an app restart) and the gate finds the grant. The workflow task IS the durable approval object — we deliberately added no parallel agent_sessions store (issues.txt: avoid parallel trust stores); session_id is just a nullable tag on the grant. A write grant satisfies a read request, not the reverse.

Deviation — added 'agent' to AllowedOrigins

The workflow_tasks CHECK already permitted origin='agent' but the service-layer AllowedOrigins validator omitted it — a latent inconsistency. Aligned the validator to the DB constraint (the runtime schema is the source of truth) so an agent-originated approval task validates.

Open questions

(1) Locked (passphrase) tier: the gate returns approval_required for a locked persona, but approval alone doesn't put the persona DEK in RAM — the user must also unlock. Today: approve → grant + the user's unlock action → agent reads. Confirm the intended locked-tier UX (should approving the card also trigger the unlock?). (2) Grant TTL defaults to 1 h, approval card to 15 min — confirm. (3) Scope: the approval payload stores the agent's requested query (allowed by the spec as "requested scope/query") but never vault results; if even the request text is considered sensitive, we'd redact it.

Deep review — (1) correct? (2) smells? (3) tests?

(1) Correct: the check is deterministic + at the Core boundary (not LLM-mediated), and fails closed. Data cannot leave before approval (the route returns 403 and never calls queryVault); approval + grant survive restart (real-SQLite close+reopen test); deny/expire/restart-before-approval all leave no grant ⇒ no data. (2) No smells: reused the existing workflow-approval object + the staging persona-access pattern rather than a new subsystem; one grant interface, two parity-tested impls. (3) Tests sound: binding is proven negatively (wrong DID / wrong persona / expired / revoked all return null), and the route test proves the owner-vs-agent discrimination, not just the helper.

Item 3 — Real export/import done

Decision — implement real export/import (portability is a selling point)

Replaced the stub createArchive (which wrote persona_count:0 / empty manifest) with a real ArchivePayloadV1: { header, identity:{tables}, personas:[{name,tier,tables}] }. Rows are read through a registered ArchiveDataSource (the storage layer's identity adapter + open persona adapters). The wire format (DINA magic + Argon2id + AES-256-GCM) is unchanged, so it stays cross-compatible server↔mobile.

Design — secret exclusion by allowlist + kv denylist

Exported identity tables are an explicit allowlist (contacts / people / identities / surfaces / reminders / service_config / chat_messages); persona tables are vault_items / vault_item_subjects / topic_salience / topic_aliases. kv_store is exported with sensitive keys filtered (api_key / password / token / secret / seed / mnemonic / pds_ / passphrase). NEVER exported: paired_devices (device tokens), agent_persona_grants (active grants), master seed, and all volatile/transient tables (audit, workflow, staging, d2d_outbox, fts index).

Design — clean-install import, transactional, checksum-validated

V1 import is clean-install-only (avoids merge complexity): it refuses a target that already holds user data unless force is set, validates the manifest format + version + per-table SHA-256 checksums BEFORE writing, and restores each table inside a transaction (identity in one, each persona in its own). A data-bearing payload with no data source throws — import never silently succeeds in production. Empty archives (dry-run/no source) still import as a no-op.

Tradeoffs

Generic SELECT * dump + INSERT OR REPLACE restore (vs hand-mapped per-table DTOs): simpler, schema-evolution-tolerant, and the checksum guards integrity. Clean-install only (vs merge): the spec's V1 scope — merge/CRDT is deferred. Kept the legacy setImportHandler seam so older manifest-only callers/tests still run.

Item 5 — Paired-device revoke persistence done

Root cause + fix — revoke never wrote SQL; hydrate already skipped revoked

revokeDevice cut auth + set the in-memory revoked flag but never persisted to SQL, so hydrateDeviceRegistry (which already guards if (!d.revoked …)) reloaded the row as active on the next boot — a revoked OpenClaw/CLI device became trusted again. Added revokeDeviceDurable: it writes revoked=1 to SQL first, then cuts in-memory + auth access, and only reports durable: true when the write succeeded. The legacy sync revokeDevice also got a fail-safe fire-and-forget write-through so even it survives restart.

Design — persist-first, fail-safe, idempotent, with grant cascade

If the SQL write fails, access is still cut in-memory (fail-safe deny) but the result is durable: false + an error, so the UI shows "not fully saved — may not survive a restart" instead of claiming a durable revoke (the mobile paired-devices screen now does exactly this). Re-revoking a revoked device is a success no-op (idempotent); an unknown device returns a clean found:false. Revoke also cascades to the device DID's durable agent_persona_grants (§2) — a revoked agent immediately loses any locked-vault grant, even before it's re-paired.

Deep review — (1) correct? (2) smells? (3) tests?

(1) Correct: durability is persist-then-report; the restart test proves a revoked device stays revoked AND can't authenticate (resolveCallerType → 'unknown', so it can't claim workflow tasks) after a real close+reopen + re-hydrate. Fail-safe on persistence error. (2) No smells: extracted the shared cutDeviceAccess helper; reused the repo's existing revoke(); the sync path keeps back-compat. (3) Tests sound: restart uses a real SQLCipher file (not an in-memory map), and the repo-failure test injects a throwing repo to prove no phantom durable success.

The plan (§6) warns to update packages/fixtures/schema/*.sql "in lockstep." On inspection that is wrong for this change: identity_001.sql / persona_001.sql are a frozen architectural-reference schema that already diverges from the runtime schemas.ts (they contain no people-graph tables at all, and identity_schema.test.ts asserts "exactly 10 tables"). The runtime schema source is schemas.ts, consumed by every test harness via applyMigrations(). Touching the fixtures would break the fixture-parser tests, not satisfy them. Decision: leave the fixtures alone; treat schemas.ts as the single source the redesign edits.

Design decision — in-place schema edit (greenfield), not forward migrations

Per plan D7 (greenfield, no real installs), I edit the existing migration entries in place (identity v5 people_graph; persona v1 initial_persona_schema) rather than appending v6/v3 ALTER migrations. The migration runner (migration.ts) has no checksum guard and replays all migrations on a fresh DB, so every test and every wiped sim gets the final schema. This makes the initial schema read as if person-identities was always the design (no "added then dropped" cruft) — the right outcome for a pre-launch product.

Tradeoff — in-place edit requires a dev-DB wipe

The cost of editing v5 in place: any dev DB already at version 5 will not pick up the changes (the runner skips version <= current), and a column DROP can't be expressed by re-running an edited CREATE anyway. So existing sims/emulators must be wiped (already in the plan checklist). The alternative — a forward v6 migration with ALTER TABLE people DROP COLUMN contact_did + CREATE person_identities — would migrate dev DBs without a wipe but permanently bakes evolution cruft into a product that has never shipped. Chose the clean initial schema.

Open question — revisit before first real install

If/when Dina ships to real installs that hold data we can't wipe, the in-place-edit policy must flip to forward, append-only migrations. Flagging now so it isn't forgotten.

Design decision — Codex doc expansion trimmed to a disciplined middle path

Codex rewrote IDENTITY_HUB_REDESIGN.md with 7 categories of additions. They are correct about a mature identity system but most violate the plan's own discipline (D2/§3.7: avoid premature structure) and some carry costs Codex didn't weigh. Reconciled to: adopt now = entity_type column + cross-file integrity rule (skip-and-log dangling links) + two real tests (persona-scoped recall non-leakage; dangling subject-link safety). Defer (new §11) = lifecycle/revocation, verification evidence, perspective-scoped role phrases, source≠author≠subject raw columns, group/agent flows, canonicalizer, aggressive fuzzy linking, within-file FKs, typed facts. Everything deferred is documented so the spine can't regress to DID-only / name-FTS-only.

Deviation from Codex — three rejected as premature/risky

(1) Perspective-scoped role phrases (perspective_person_id on person_surfaces) collide with the frozen Go-parity contract that pins role-phrase exclusivity as global, and no current flow ingests third-parties' statements about third parties. (2) "verified+active required for admission" folds verification policy into the identity schema — the plan deliberately keeps admission separate (D6), and it risks the Quixote demo (a freshly-paired contact might not count as "verified"). (3) Raw author/source identity columns on vault_items partly re-introduce the DID-tagging the redesign moved away from; author_person_id (resolved person) is the linkage we actually need, and agent-relay paths are deprecated anyway.

Design decision — entity_type is a column, not domain plumbing

Added people.entity_type (human|org|service|device|agent|group, default 'human') — a one-column future-proofing hook for non-human counterparts (a clinic, a service DID). Deliberately not threaded through the Person domain type or row mappers: no consumer reads it yet, and adding an unused interface field is the same speculative plumbing the redesign avoids. INSERTs rely on the column DEFAULT, so no write-path change. The column exists so a future provider/org flow needs no migration.

Design decision — no SQL FKs (within or across files)

Codex proposed FKs within identity.sqlite (ON DELETE CASCADE to people). Rejected for now: the model never hard-deletes (lifecycle = a status flip, so cascade never fires), and FKs require auditing PRAGMA foreign_keys=ON across every adapter or they're silently inert — a "looks-enforced-but-isn't" footgun. Integrity stays repo-enforced (matches what's implemented). Cross-file (persona vault → identity DB) FKs are impossible anyway (separate SQLCipher files); recall skips-and-logs a dangling person_id.

Tradeoff — verified monotonicity on identity upsert

upsertIdentityRow uses verified = MAX(old, excluded) on conflict so a re-point never silently downgrades a previously-verified identity. Alternative (verified = excluded.verified) is simpler but could clear verification on an unrelated re-assert. In Phase A all identity writes are explicit (verified=1), so the choice is latent insurance, not load-bearing yet.

Phase B — establishContact() + contacts re-key in progress

Design decision — full re-key, DID-facing accessors retained (user-chosen)

User chose the full D3 re-key over the disciplined alternative. Implementation: the contacts SQL table + contact_aliases + the in-memory directory become person-keyed (policy stored once per person), but the public directory API stays DID-facing (getContact(did), isContact(did), …) and resolves did → person_identities → person_id internally. In-memory model: Map<personId, Contact> (truth) + Map<did, personId> index + Map<alias, personId>. Contact.did stays as the primary DID (every contact has exactly one DID today; multi-DID is deferred §11).

Consequence — contact directory now hard-depends on the people graph

Today the people-graph mirror in addContact is optional/fail-soft; with policy keyed by person_id, a contact cannot be stored without first resolving/creating its person. So the people repo becomes a required dependency of contact creation (routed through establishContact()), and the directory's standalone tests must wire a people repo. This is the intended direction (people = the hub; contacts derive from person_id), not a workaround — but it is a real coupling the DID-keyed design didn't have. No silent did-as-person_id fallback is introduced (that would be the workaround); missing-repo is a hard error.

Design decision — no separate `blocked` column; keep trust_level='blocked'

The doc draft (from Codex) added a blocked flag to contacts. Rejected: blocking already lives in the TrustLevel enum ('blocked'), and a second column is the exact "two competing blocked states" anti-pattern the doc itself warns against. Projection rule stays: a DID is in the gate iff its person's contact trust_level !== 'blocked'.

Whole-app security review — pre-first-release (5 findings fixed)

A multi-agent security audit of the shipping TS stack (apps/home-node-lite, apps/mobile, packages/*, appview/; Go/Python excluded as deprecated) surfaced 5 findings that survived an independent false-positive filtering pass at ≥8/10 confidence — 3 HIGH, 2 MEDIUM. #1 (HIGH) — agent self-approval of workflow tasks (privilege escalation)

The authz matrix let caller-type agent reach the whole /v1/workflow/tasks/ sub-tree and isAuthorized is method-agnostic, so an agent could POST /v1/workflow/tasks/:id/approve — which had no caller check — to APPROVE its OWN agent_persona_access request (writing a durable grant + unlocking the persona) and clear flagged intent_validation proposals, defeating both the persona gate and the Agent Gateway. FIX: ownerDecisionGuard in server/routes/workflow.ts refuses callerType === 'agent' on approve + cancel/deny (prefix authz can't carve out the dynamic /:id/approve suffix, so it's enforced in-handler, mirroring vault.ts's agentGate). brain (the user-driven /service_approve chat command) and device/admin (app UI) stay authorised; callerType comes from the verified auth result, not the body. Test: workflow_approval_authz.test.ts drives the full chain — agent self-approve → 403, no grant; owner approve → grant written, agent then reads.

#2 (HIGH) — D2D inner sender not bound to the authenticated envelope DID (impersonation)

Inbound D2D verified the signature against keys resolved from the outer MsgBox env.from_did, but every downstream use (trust gate, replay key, vault attribution origin_did/sender_did) took the sealed inner message.from with NO check the two matched — so an attacker could sign with their OWN key while putting a trusted peer's DID in from and inherit that peer's trust + attribution (amplified by safety.alert being an always-pass type for non-contacts). The RPC path already bound identity; the D2D path didn't. FIX: receiveD2D gained options.authenticatedFromDID; the production handleInboundD2D always passes env.from_did, and the pipeline drops + audits (d2d_recv_sender_mismatch) when message.from differs, before the replay cache is touched. It's a transport-layer property, so pure-pipeline unit tests (no envelope) are unaffected — zero churn across ~50 existing call sites. Tests: 3 binding cases in receive_pipeline.test.ts (match→staged, spoof→dropped, omitted→back-compat).

#3 (HIGH) — rehydrated PII embedded via cloud Gemini with no scrub (Law 3 breach)

Enrichment scrubbed PII before the cloud LLM call but REHYDRATED real PII into content_l1 and then embedded it via generateEmbedding with no scrub; in the shipping config the only embedder is cloud Gemini and the sweep covers every persona incl. health/financial — so raw PII (MRN, email, card #) left the device. A second instance lived in reminder_planner.ts (query built from names/relationships). FIX: new embedding/safe_embed.ts::embedMaybeSensitive — a local (on-device) provider embeds the real text; the cloud path (cloud-only, or a local-failure fallback) embeds a PII-SCRUBBED copy, and raw text is NEVER handed to the cloud fallback. Both call sites route through it; generateEmbedding's doc now warns it falls back to cloud. Test: safe_embed.test.ts asserts the cloud provider receives scrubbed text (raw email absent), local receives the real text, and local-fail still scrubs before cloud.

#4 (MEDIUM) — untrusted map_url opened via Linking.openURL (scheme abuse)

An ETA card opened result.map_url — opaque, attacker-controlled peer service.response data — with no scheme check, so a hostile provider could return tel:/sms: (premium dialer), javascript:, an https phishing page, or an app deep-link that Linking.openURL launches under "Open in Maps". FIX: extracted components/safe_url.ts::safeHttpsUrl — allows only https: (parsed via new URL), used by the card. Test: safe_url.test.ts (https accepted; tel/sms/javascript/http/file/deep-link + non-strings rejected).

#5 (MEDIUM) — mobile persona-name path traversal on archive import

The mobile + Expo DB providers built ${persona}.sqlite with NO name validation (the Node provider guards via assertPersonaName), so a crafted .dina archive whose manifest carries a persona named ../../evil (the AES-GCM tag only proves the importer's passphrase, not authenticity) could write a SQLCipher file outside the vault dir on restore. FIX (defence-in-depth): both providers' openPersonaDB now call validatePersonaName (canonical [a-z0-9_]+ rule — every legitimately-created persona passes), AND importArchive validates persona.name at the trust boundary before openPersonaForRestore. Test: archive_real.test.ts crafts an archive with a traversal persona name and asserts import rejects it before any file open.
